# 仕様レビュールール

新機能や今の動きを変える issue を起票する前に、**作るもの・作る形が、システムの目的とユーザーの目指す投資家像に合っているか**を、別の AI に読ませて確かめる。

コードの細部・実装方法は見ない。それは実装前のプランレビュー ([codex-plan-review.md](codex-plan-review.md)、Codex) と実装後の PR レビューが見る。作ったものが効いたかを振り返るのは四半期末の成果レビュー ([doc/開発方針.md](../../doc/開発方針.md) の「節目」)。

| いつ | レビュー | 問い |
|---|---|---|
| 起票の前 | 仕様レビュー (このファイル) | 何を、なぜ作るか |
| 実装の前 | プランレビュー | どう作るか |
| 実装の後 | PR レビュー | コード |
| 四半期末 | 成果レビュー | 作ったもので何が変わったか |

## いつやるか

- Claude が issue の草案を書いたら、起票の前に回す。草案とレビューの結果をそろえてユーザーに見せ、起票するか・どう直すかはユーザーが決める
- ユーザーが自分で書いた issue は、頼まれたら回す
- 回さないもの: バグ修正、不可逆データと日次運用の保全、日々の手作業を減らすもの、文書の変更 ([doc/開発方針.md](../../doc/開発方針.md) の「着手前の確認」と同じ線)
- **1回だけ**。目的から問い直す指摘が出たら、再レビューではなく grilling でユーザーと詰める

issue に書かせる項目は増やさない (求めるのは「なぜ今やるかの1行」だけ)。下の問いに答えるのはレビューする側。

## 見ること

| 観点 | 問い |
|---|---|
| システムの目的 | 買う・見送る・待つ・減らす・持つのどの判断が、どう変わるか。変わらないなら、情報を増やすだけ ([方向性メモ](../../doc/方向性メモ.md) §7 の避ける方向) ではないか |
| 目指す投資家像 | ユーザーの弱点 (衝動の売買、張りすぎ等) を補うか、強みを伸ばすか |
| アーキテクチャ | どのデータに置き、どの処理・画面が受け持つか。今ある機能・データ・画面・open な issue と重ならないか |
| 使い勝手 | いつ・どの画面で見て、次に何をするか。毎日の動線に入るか。表示や操作が増えすぎないか |
| 今やる理由 | いま強化する領域に当たるか。もっと小さい形で先に試せないか。効いたかを成果レビューで言えるか |

指摘は「**それで作るもの・作る形が変わるか**」で仕分ける。変わらない指摘は採らず、理由を1行添えてユーザーに見せる。

## 材料

文書の本文をプロンプトに入れて渡す (ツールで読ませるとコードを調べ回って遅い)。プロンプトは scratchpad に1ファイルで組み、両方の AI に同じものを渡す。

1. 下の依頼文
2. issue の草案
3. `doc/方向性メモ.md`、`doc/開発方針.md`、`doc/投資戦略.md`、`doc/AI投資活用戦略.md`、`doc/アーキテクチャ.md`
4. 直近の成果レビュー (いまは `doc/review/成果レビュー_1115_中間.md`)
5. open な issue の番号と題 (`gh issue list --state open --limit 200 --json number,title`)

各文書は `=== ファイル名 ===` の見出しで区切る。

依頼文:

```
あなたは、個人投資家 (私) の投資システム Shintakane の仕様レビュアーです。
下に、これから起票する issue の草案と、システムの目的・投資スタイル・開発方針・アーキテクチャの文書、open な issue の一覧を置きます。

この issue が「作るべきものか、この形でよいか」をレビューしてください。観点:
1. システムの目的: どの判断 (買う・見送る・待つ・減らす・持つ) がどう変わるか。方向性メモ §7 の避ける方向に寄っていないか
2. 目指す投資家像: 私の弱点を補うか、強みを伸ばすか (投資戦略・成果レビュー)
3. アーキテクチャ: データの置き場所と、処理・画面の受け持ちが今の構成に合うか。既存の機能・データ・画面・open な issue と重ならないか
4. 使い勝手: いつ・どの画面で見て、次に何をするか。毎日の動線に入るか
5. 今やる理由: いま強化する領域に当たるか。もっと小さい形で先に試せないか。効いたかを後で言えるか

守ること:
- コードの細部・実装方法・テストは指摘しない
- 些細な指摘は不要。作るもの・作る形が変わる重大な問題だけを、重い順に最大5点
- 各指摘に「どう変えるとよいか」を1行添える
- 問題がなければ「指摘なし」とだけ書く
- ファイルの読み書きやコマンドなどのツールは使わない。下の本文だけで判断する
```

## コマンド

2つを裏で同時に流し、両方の結果を待つ。

```bash
# agy (Gemini)
agy --mode plan --sandbox --model gemini-4-neon-xhigh -p "$(cat "$PROMPT")" > "$OUT_AGY" 2>&1
# Codex
codex exec -m gpt-6.1-sol -c model_reasoning_effort="high" -s read-only - < "$PROMPT" > "$OUT_CODEX" 2>&1
```

- agy の `-p` はプロンプトの直前に置く (前に置くと `--mode` がプロンプトに取られる)。effort はモデル名の末尾で決まり、`--effort` を重ねるとエラー
- Codex はリポジトリのルートから実行する (scratchpad で起動すると trusted directory エラーで止まる。プロンプトのファイルは scratchpad に置いたままでよい)
- Codex は `-` で stdin からプロンプトを読む。止まったときの扱いは [codex-plan-review.md](codex-plan-review.md) の「止まったとき」
- agy は途中経過を出さない。進んでいるかは `~/.gemini/antigravity-cli/cli.log` の `streamGenerateContent` の時刻で見る

## 試行: agy と Codex を比べる (2026-11-28 〜 2026年12月末の成果レビュー)

文章・構造・批判的な読みは agy (Gemini) が得意と聞いて試す。プランレビュー (コード) は Codex に固定。

- 試行の間は両方に回し、結果を並べてユーザーに見せる
- 1回ごとに、開発機の記憶 `project_spec_review_trial.md` に1行残す (issue、各 AI の指摘数・採った数・かかった時間、採らなかった主な理由)
- 12月末の成果レビューで、どちらに寄せるか (または両方続けるか) を決め、このファイルを書き換える
