# 実装プラン作成ルール

新機能追加や既存機能の挙動変更を伴うプランをユーザーに提示する前に、`codex` でレビューし、**指摘がなくなるまで修正→レビューのサイクルを繰り返すこと。**

プロンプトには必ず次の指示を含める: *「些細な指摘は不要。重大な問題のみ指摘してください。」*

## スキップ可能なケース

軽微な修正のみの場合はレビュー不要:

- 定数値の変更 (LOG_DAY, タイムアウト値など)
- バグ修正 (既存仕様通りに動作させる修正)
- ログ出力の追加・調整
- 既存機能の挙動を変えないリファクタリング
- コメント・docstring の修正

判断に迷う場合はレビューを通す。

## コマンド

### 初回レビュー

※ モデルは `-m` で必ず指定（gpt-5.6-terra 推奨。gpt-5.4 / gpt-5.5-terra は ChatGPT アカウント認証では 400 エラーになり使えない）

```bash
codex exec -m gpt-5.6-terra "Review this plan. Don't nitpick trivial things. Only point out critical issues: {plan_full_path} (ref: {CLAUDE.md full_path})"
```

### 修正後の再レビュー

※ 初回レビューのコンテキストを保持するため `resume --last` が必須

```bash
codex exec resume --last -m gpt-5.6-terra "I've updated the plan, please review again. Don't nitpick trivial things. Only point out critical issues: {plan_full_path} (ref: {CLAUDE.md full_path})"
```

## 指摘への対応可否の判断基準

レビュー指摘は「理論上の可能性」ではなく **このコードベースで実際に起きるか** で判断する。
対応する前に必ず確認すること:

1. **その経路を通るコードが実在するか** (grep で呼び出し元を数える)
2. **実際に再現するか** (推論だけで対応しない。プロセス並走などで実測する)
3. **起きたら気づけるか** (silent に壊れるなら優先度高。エラーで落ちるなら後追いでよい)

上記を満たさない指摘は **「発生してから対応する」で構わない**。
プランに「対象外とする理由」を1行残して次に進む。

### 打ち切りの目安

- **同じ論点で3巡以上**やり取りしている
- 指摘が「将来 X が追加されたら」「2つ同時に実行したら」など、**現存しない前提**に依存している
- 対策コストが、防ぐ事象の期待被害 (発生確率 × 損害) を明らかに上回る

該当したらレビューを打ち切り、ユーザーに「ここで線を引く」と報告する。
レビューを何巡も回すこと自体がコストであることを忘れない。

### 対策が効いているかは実測で確かめる

レビューを通した設計でも、実装してみると効かないことがある
(issue #174 では「read メソッド個別にロック」がロック無しと同一結果だった)。
ロック・排他・競合対策のように**推論を間違えやすい領域**では、
実装後に必ず「対策前は壊れ、対策後は壊れない」ことを実プロセスで確認する。

## 計測結果の扱い

実測した数字は推論より強い根拠に見えるため、**間違っていても誰も疑わない**。
計測そのものを誤ると、判断が大きく狂ったまま進む。以下を必ず守る。

### 計測コードと実装を混ぜない

競合・破損率・性能を測るスクリプトは、**その時点の main か、対策を意図的に外した版**に対して実行する。
作業ツリーの書きかけコードを通して測らない (`git stash` してから測れば足りる)。

対策の要否を測るのに、書きかけの対策実装を通すと、**汚染された計測器で計測器自身の必要性を測る**ことになる。

### ベースラインとセットでしか報告しない

「対策後 X%」を単独で出さない。必ず **「対策前 Y% → 対策後 X%」の対**で出す。
片方しかない数字は判断材料にしない。置く先がなければ、出た値が異常かどうか判定できない。

### 計測結果がスコープを広げるときは測り直す

計測結果には2種類ある。

- **スコープ内の判断** (この対策は効いているか) → 一度測れば足りる
- **スコープを広げる判断** (設計・基盤ごと変えるべきか) → **条件を変えて2回測る**

「この数字のせいで、依頼されていない大きな変更を始めようとしている」と気づいたら、
それは再計測のトリガー。ユーザーに提案する前に、自分で足元を疑う。

**実例 (issue #174):** 「日次バッチ中の読み取りが52%破損」と報告し、それが SQLite 移行 (#450) の
検討理由になった。実際は実装途中のロック付きコードを通して測っており、ロック実装のバグ由来の数字。
正しく測ると **11,100件読んで破損0** で、移行の必要はなかった。
ベースライン (ロック無し) を先に取っていれば、52% は即座に異常と分かった。
