# 月次の売買振り返り (/trade-review)

`/trade-review 2026-09` で、その月の振り返りを1回の対話で終える (issue #448)。翌月の初めに、前月分を対象に実行する。

目的は、数字を眺めることではなく **「翌月変えるルール1つ」を決めること**。利用者は自分を責めやすく、振り返りが続かない性質だと自己分析している (`doc/投資戦略.md` の認知プロファイル)。だからレポートは短く、問いは選ぶだけにし、損益の大きさではなく「決めたルールどおりに動けたか」を見る。

役割分担: 数字は Python が出す。あなたは照合と問いかけをする。ルールを決めるのは利用者。

## 手順

### 1. 数字を取る

実行環境を確かめる (リポジトリのルートから)。

```bash
cd scripts && ../.venv/bin/python -c "import ks_util; print(ks_util.is_dev_data_dir())"
```

- `False` (運用機): `cd scripts && ../.venv/bin/python trade_review.py json YYYY-MM`
- `True` (開発機): 開発用コピーは古いので、運用機に問い合わせる。`deploy/macmini.sh run python trade_review.py json YYYY-MM`

標準出力の JSON をスクラッチパッドに保存して読む。数字はこの JSON だけから取り、自分で DB を読んだり計算し直したりしない (不変条件「数値は Shintakane から取り、LLM は解釈に使う」)。JSON に無い数字が要るときは、無いと書く。

対象月がまだ終わっていないときは、その旨を伝えて続けるかを聞く。

### 2. 判定基準と前月分を読む

- `doc/投資戦略.md` — 判定基準。特に「売買ルール」(買いルール A・B・C、売りの4分類、損切り・利確)、「ポートフォリオ構造」、「感情スコアとレバレッジ」、末尾の「ルール変更履歴」
- 前月のレポート — 保存先の `trade_review/` にある前月の `.md` (運用機なら `$KS_DATA_DIR/trade_review/`、開発機からは `deploy/macmini.sh run cat` で読む)。無ければ初回として §0 を省く

### 3. 当月の投資日記を読む

Google Drive の「投資メモ」フォルダにある当年分のドキュメント「投資メモ」から、対象月の記述を読む。売買の理由は、振り返りメモの1行より日記のほうに詳しく書かれている。

- 日記は私的な文書。レポートには **日付と短い引用だけ** を残し、本文を写さない。リポジトリのファイルには一切書かない
- Drive のコネクタが使えないときは飛ばし、レポートの冒頭に「日記は読んでいない」と書く
- 「投資メモ教訓Top10」との照合はしない

### 4. レポートを書いて見せる

下の「レポートの構成」の §0〜§4 と §6 を書き、会話に表示する。

### 5. 問いを聞く

§5 の問い3件を AskUserQuestion で、選択肢つきで聞く。回答をレポートの §5 に書き込む。

### 6. ルールを選んでもらう

§6 の候補から1つ選んでもらう (「今月は変えない」も選べるようにする)。選択をレポートの §6 に書き込む。

### 7. 保存する

完成したレポートをスクラッチパッドに `.md` で書き、保存する。JSON は保存時に作り直されるので、**手順1と同じ日のうちに保存する** (日次バッチをまたぐと、分析した数字と保存される JSON がずれる)。

- 運用機: `cd scripts && ../.venv/bin/python trade_review.py save YYYY-MM < report.md`
- 開発機: `deploy/macmini.sh run python trade_review.py save YYYY-MM < report.md`

「既に保存済みです」と出たら上書きしない。利用者に伝え、消すかどうかは利用者が決める。

ルールを選んだときは、`doc/投資戦略.md` の「ルール変更履歴」の表に1行足す (決めた月 / 変えたルール / きっかけ)。本文のルールと食い違うなら本文も直す。コミットは利用者に確認してから行う。

## レポートの構成

見出しは `# 売買の振り返り YYYY年M月` とし、直後に作成日と、読んだもの (JSON の `generated_at`、日記を読んだか) を1行で書く。

### §0 前月に決めたルールの結果 (2回目以降)

前月のレポートの §6 で選んだルールと「翌月の確かめ方」を引き、当月の JSON の数字で **守れた / 守れなかった** を答える。前月の §4 で名指しした銘柄がどうなったか (決済した、まだ保有、含み損益の変化) を1行ずつ書く。

### §1 数字サマリー

`summary` から、次の5つをこの順に書く。

| ブロック | 元の項目 | 書き方 |
|---|---|---|
| 月の結果 | `closed` | 決済 n件、x勝y敗、実現損益。`no_pl_count` が 0 でなければ「損益不明 n件を除く」と添える |
| 戦略宣言なしの決済 | `undeclared` | 件数と損益。0件なら「0件」の1行 |
| 保有日数帯別 | `hold_bands` | 0〜3日 / 4〜90日 / 91日以上の件数と損益 |
| 市場局面別の売買額 | `by_state` | 局面ごとの買い・売りの額と約定数、差。`unknown` は「ログなし」。`short_fill_count` が 0 でなければ「空売りの約定 n件を除く」と添える |
| 運用比率 | `exposure` | `margin_rate_min` があれば (#480 以後): 推定維持率の月間の最小〜最大、記録日数 (`logged_days`) のうち適正エリアより多い・内・少ない日数 (`over_days`・`within_days`・`under_days`)、段が 0 以外の日数 (`nonneutral_days`)。無ければ旧方式: 運用比率の最小〜最大、調整判定 (`correction_days`) の日数と、うち目安の上限を超えた日数 (`correction_days_over`) |

局面の表示名: `confirmed_uptrend` = 上昇、`uptrend_under_pressure` = 上昇・圧力あり、`market_in_correction` = 調整。

戦略別の集計と指数との比較は書かない。月に十件前後では傾向が読めず、実現損益は決済した月に計上されるのでその月の指数と対応しないため。

### §2 取引ごとの照合

`trades.closed` (当月に完全決済) と `trades.opened` (当月に新規建て) を **全件、表に1行ずつ** 載せる。そのうえで、逸脱のあった取引だけ根拠を2〜4行で書く。ルールどおりだった取引に文章は付けない。

決済の表:

| 取引 | 時間軸 | 売りの分類 (推定) | 損切り・利確の幅 | 判断 × 結果 |
|---|---|---|---|---|

新規建ての表:

| 取引 | 建てた日の局面 | 再INか | 入口の理由 |
|---|---|---|---|

列の埋め方:

- **取引**: 銘柄コードと名前、戦略、保有日数と損益率 (新規建ては建てた日、株数と単価)
- **時間軸**: `hold_days_consistent` が false なら「短すぎる」「長すぎる」。`time_horizon` が空なら「—」
- **損切り・利確の幅**: 損失なら `return_pct` をその取引の `stop_loss_pct` (宣言した戦略の損切り幅) と比べる。`stop_loss_pct` が無い取引 (戦略の宣言なし、夢枠・大型高配当、戦略のひもづけが要再確認、ロットに別の戦略が付いている) は「幅なし」と書き、超えたかどうかを判定しない。利益なら `fills` の途中の売りを見て、+15〜20% で一部を利確したかを書く
- **建てた日の局面**: `open_state` と、`open_position` が `over` なら「運用総額は適正エリア超え」(#480 より前の日は「運用比率は上限超え」)
- **再INか**: `reentry` があれば、何日前にいくらの損益率で決済したか、前回の最大株数 (`prev_qty_peak`) と今回の株数
- **売りの分類 / 入口の理由 / 判断 × 結果**: あなたの推定。下の「推定の書き方」に従う

`strategy_drift` が true の取引は「戦略のひもづけが要再確認」と添え、戦略に基づく判定をしない。`split_suspect_count` が 0 でなければ、除いた件数を表の下に書く。

#### 推定の書き方

- 売りの分類は、売りの4分類 (仮説崩れ / 需給崩れ / 時間切れ / 期待先行の過熱) のどれか、またはどれにも当たらない「分類なし」
- 入口は、買いルール A (ファンダ)・B (モメンタム)・C (タイミング) のどれを満たしていそうか
- 判断 × 結果は「良い判断 × 良い結果」のように2軸で書く。**ルールどおりに売って、その後に上がったのは良い判断**。結果だけで判断を悪く言わない
- 根拠は `review_memo`・`action_notes`・日記の文言に限る。列の見出しに「(推定)」と付け、根拠にした文言を引用する
- **メモも日記の記述も無い取引は「判定不能」と書く。** 値動きや保有日数だけから動機を作らない。「感情で売った」のような断定は、本人がそう書いているときだけ

### §3 弱点仮説の検証 (年初来の累計)

`hypotheses` から2行の表にする。期間は `period`、母数は `closed_count` (除いた件数 `excluded_count` を添える)。

| 仮説 | 書くこと |
|---|---|
| 損切りの幅 | 損失 `loss_count` 件のうち、戦略の損切り幅を超えたのが `over_count` 件で `over_pl`。幅の内側の損失は `within_pl`。幅の無い損失は `no_width_count` 件で `no_width_pl`。うち当月の超過 `month_over_count` 件 |
| 売ってすぐ買い直す | 決済から30日以内の再INが `count` 件。決済済み `settled_count` 件は `settled_wins` 勝、合計 `settled_pl`。うち当月 `month_count` 件 |

前月のレポートがあれば、累計が前月からどう動いたかを一言添える。

### §4 保有PFの点検

`portfolio` から書く。**過去の月末の保有は復元できないので、レポートを作った日の状態である** ことを節の最初に書く (`exposure.date`)。

| 項目 | 元の項目 | 目安 |
|---|---|---|
| 運用総額と目標 | `exposure` の `total_value`・`margin_rate_pct` (推定維持率)・`target_rate` (目標の維持率) と段の決まり方 `step_parts`・`area_lower`〜`area_upper` (適正エリア)・`position`。`target_rate` が無い旧ログなら `ratio_pct`・`state`・`range_lower`〜`range_upper` | 適正エリア (#480) |
| 銘柄数 | `holding_count` | 実保有10 + 打診5 程度 |
| 小口 | `small` (建玉合計の3%未満の銘柄数と合計額) | — |
| 損切り幅を超えた含み損 | `over_stop_loss` を全件、名指しで。各行の `stop_loss_pct` を添える | 戦略ごとの損切り幅 |

指摘まで。「売るべき」「減らすべき」とは書かない (不変条件「最終投資判断は人が決める」)。テーマの集中、防衛線、記録の不備は書かない。`holdings` は記録用で、レポートには使わない。

### §5 問い (3件)

情報量の大きいものを3件選び、取引や銘柄を指名して聞く。優先順は、損切り値より高く・前回より大きく建て直した再IN、損切り幅を超えたまま保有している銘柄、局面の目安と逆向きの売買、時間軸と大きく食い違う決済。

- 選択肢を3つ用意し、どれも責める言い方にしない (「切るタイミングを逃した」は可、「また損切りできなかった」は不可)。選択肢に無い答えは自由記述で受ける
- 問いは事実 (日付・値段・株数) から始める
- レポートには 問い / 選んだ答え を書く

### §6 翌月変えるルールの候補 (2〜3個)

| 候補 | 根拠 | 翌月の確かめ方 |
|---|---|---|

- 根拠は §1〜§4 の数字
- **翌月の JSON の項目で守れたかを確かめられるものだけ** を候補にする。「衝動で買わない」のような心構えは出さない。確かめ方には、どの項目を見るかまで書く (例: `trades.opened` の再INで、今回の株数が `prev_qty_peak` を超えた件数)
- すでに `doc/投資戦略.md` にあるルールが守れていないなら、新しいルールを足さず、そのルールを守る手順を候補にする
- 表の下に「選んだルール: …」または「今月は変えない」を書く

## してはいけないこと

- 銘柄の推奨、売買の提案
- メモも日記も無い取引の動機の断定
- 月次の損益の大きさで人を評価すること (良い月を褒める、悪い月を責める、のどちらも)
- JSON に無い数字を作ること
- 日記の本文を、引用を超えて写すこと
