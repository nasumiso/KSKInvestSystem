# 保有ポートフォリオの点検 (/portfolio-review)

`/portfolio-review` で、いま持っている建玉の点検を1回の対話で終える (issue #589)。

月次の `/trade-review` は **終わった売買** を見る。こちらは **いま持っている建玉** を見て、1銘柄ずつ扱いを決め、**次の回にその約束が実行されたかを約定で照合する**。

**いつやるか**: 日を決めない。平時はやらなくてよい。前回の点検より後に「防」や損切り幅を超えたロットが増えた、市場ステートが悪化した、推定維持率が下がった、のどれかが起きると、トップの「今日のアクション」に「保有の点検」の行が出る。それが出たとき、または相場のイベントが起きそうなときに実行する。

市場ステートが**調整**に入ったことがきっかけのとき (`triggers.state_worse.to` が `market_in_correction`) は、§5 の「調整入りの点検」も行う。市場ステートで運用総額は動かさない代わりに、傷が広がる経路 (逆指値の漏れ・線の引き直し・下落中の買い増し) を先に塞ぐのが目的 (2026-11-27 の判断)。

役割分担: 数字は Python が出す。あなたは照合と問いかけをする。扱いを決めるのは利用者。利用者は自分を責めやすく、振り返りが続かない性質だと自己分析している (`doc/投資戦略.md` の認知プロファイル)。問いは選ぶだけにし、損益の大きさではなく「決めたルール・前回の約束どおりに動けたか」を見る。

## 手順

### 1. 数字を取る

実行環境を確かめる (リポジトリのルートから)。

```bash
cd scripts && ../.venv/bin/python -c "import ks_util; print(ks_util.is_dev_data_dir())"
```

- `False` (運用機): `cd scripts && ../.venv/bin/python portfolio_review.py json`
- `True` (開発機): `deploy/macmini.sh run python portfolio_review.py json`

標準出力の JSON をスクラッチパッドに保存して読む。数字はこの JSON だけから取り、自分で DB を読んだり計算し直したりしない。JSON に無い数字が要るときは、無いと書く。

### 2. 判定基準と前回分を読む

- `doc/投資戦略.md` — 特に「損切り・利確」(ファンダで買い、値段で降りる / 信用は線で切る玉にだけ / 短期は20日目に決済)、「手続き化すべき3ルール」(買い増しも当日に逆指値)、「レバレッジ別の1銘柄ウェイトと逆指値幅」、「逆張りでレバを上げてよいのは幅超えが0件のときだけ」、「売りの4分類」
- 前回の点検の md — 保存先の `portfolio_review/` にある最新の `.md` (開発機からは `deploy/macmini.sh run ls ../../shintakane_data/portfolio_review` などで探し、`cat` で読む)。無ければ初回

### 3. レポートを書いて見せる

見出しは `# 保有の点検 YYYY-MM-DD`。直後に、JSON の `generated_at` と、なぜ今点検するか (`triggers` を `trigger_text` と同じ言い方で1行) を書く。

#### §0 前回の約束の結果

`previous` があれば、`holdings` を1銘柄1行で書く。

| status | 書き方 |
|---|---|
| `done` / `partial` / `not_done` | 切る・減らすを、売った株数 (`sold_qty`) と今の株数 (`held_qty`) で。`qty` が無い約束は「株数は未定」と添える |
| `held_after_break` / `sold_after_break` | 価格の線を割った日 (`low_date`・`low_close`) と、その後に売ったか |
| `within_line` | 線の内側。1行で済ませる |
| `earnings_passed` | 決算日と、前回書いた `after_earnings`。そのとおりに動いたかは約定 (`sold_qty`) で答える |
| `deadline_passed` | 期限が過ぎた。いまの扱いを §2 で聞く |

`sell_order` があれば、推定維持率が `trigger_margin_rate` を割った日 (`triggered_date`) と、順番の銘柄を売ったか。前回の決定に `buy_limits` (調整入りの点検で決めた新しい買いの約束) があれば、`additions.lots` (前回以降の新規建て・買い増し) と照らし合わせ、約束に反する買いがあったかを書く (例: 「買い増ししない」なのに `is_addition` のロットがある)。最後に、実行すべきだった約束 `due` 件のうち実行 `done` 件 (`rate`) を書く。`exit` に `"proposed": true` がある約束 (11/15 の仕分け) は「線は案のまま未確定だった」と添える (線を割っても `due` には数えない)。

#### §1 ずれの表

ずれのある項目だけを1つの表にする。0件の項目は書かない。

| 観点 | 元の項目 | ずれ |
|---|---|---|
| ① 防衛ライン | `defense.lot_over` | 損切り幅を超えたロット。銘柄、ロットの戦略 (`trade_idea`、エピソードの戦略 `episode_trade_idea` と違えば両方)、建てた日・株数・建単価、損益率と幅 |
| | `defense.lit` | 「防」が点いている銘柄と初点灯日 (`first_defense`)、理由 |
| | `defense.over_horizon` | 戦略の時間軸を超えたロット (短期は20日) |
| | `defense.no_width` / `defense.widened` | 幅の当たっていない建玉、前回以降の戦略の変更で幅が広がった件 |
| 買い増し | `additions.lots` | `additions.since` 以降の新規建て・買い増し。`is_addition` (買い増し)、`below_earlier` (前のロットより安い = 下落中の買い増し)、そのロットの幅と線 (`line_price`) |
| ② 銘柄数 | `count` | 保有数と目安 `target` の差、小口、台帳に無い・Active でない保有 |
| ③ エクスポージャー | `exposure` | 推定維持率 `margin_rate_pct` と目標 (#593 以後は今週の目標の倍率 `week_target`・いまの倍率 `multiple`・張れる量 `cap`・買い向かいの期間 `boost_until`。旧ログは `target_rate`)・判定 `position`、追証までの下落率 `falls`、1銘柄の上限 `weight_cap_pct` を超えた銘柄 (`weights` の `equity_weight_pct`。自己資本 `equity` で割った値。旧ログでは受入保証金で代える。#593 以後は上限が None で出ない)、テーマの偏り `themes` (上位3つ)、幅なしの戦略を信用で持つ建玉 `margin_no_width`。`contrarian_with_over` が true なら「買い向かいの期間 (旧ログは段が恐怖側) なのに幅超えがある」と書く |
| ④ 仮説 | `hypothesis.stale_ratings` | 台帳の更新日が直近の決算より古い保有 |
| ⑦ 決算 | `upcoming` | 14日以内の決算、ウェイト、信用の株数、事前見通しが未記入 (`has_outlook` false) |

全観点で0件なら、表に「ずれなし」と書いて §2〜§4 を飛ばし、手順5で保存する (決定は `{"holdings": []}`)。

指摘まで。「売るべき」「減らすべき」とは書かない (不変条件「最終投資判断は人が決める」)。

### 4. 1銘柄ずつ聞く

#### §2 扱いの問い

対象は、①に出た銘柄 (幅超えのロット・「防」・時間軸超え)、④に出た銘柄、前回以降の買い増しのロット、前回の期限が過ぎた銘柄。1回の AskUserQuestion に4問まで。多ければ、幅超えの大きい順に回を分ける。

- 問いは事実 (日付・株数・値段・幅・損益率) から始める
- 台帳の文言 (`hypothesis.materials` の `thesis`・`risks`・`checkpoints`・`fair_price`) から、持つ材料と切る材料を **同じ数だけ** 並べる。持つ材料だけ・切る材料だけにしない。台帳が無い銘柄はそう書く。台帳の仮説を決算資料で精査し直すことはしない (別のフロー。必要なら「台帳の見直し」を期限つきの約束にする)
- **線を割った建玉** (幅超えのロット・損切りライン割れの「防」): 投資戦略.md の「ファンダで買い、値段で降りる」に従い、選択肢は「全部売る / 半分売る / 持つ (ルールの例外)」。信用の建玉には「信用は線で切る玉にだけ使う」を添える
- **線の内側で①の時間軸・④だけに触れた銘柄**: 「今日ゼロからこの値段で買うか」(切る / 減らす / 持つ)
- **前回以降の買い増しのロット**: 「買い増した当日に、そのロットの戦略の幅で逆指値を入れたか」も聞く (逆指値は Shintakane から見えないので自己申告)
- 選択肢は責める言い方にしない (「切るタイミングを逃した」は可、「また損切りできなかった」は不可)

#### 「持つ」を選んだら

その場で、持つ理由と、**売る条件を1つ** 聞く。書かないと先に進まない。売る条件は次から選ぶ。

| 種類 (`exit.type`) | 中身 |
|---|---|
| `price` | 価格の線。参考に、そのロットの `line_price` と、今の値段から戦略の幅を当てた値、それぞれの取得値からの下落率を見せ、値段は本人が決める。前回までに価格の線で持った銘柄 (線の引き直しが2回目以降) は、期限 (`exit.date`) も聞く |
| `margin_order` | 推定維持率が下がったら売る (§4 の順番に入れる) |
| `earnings` | 次の決算で判断する (§3 で決算後の行動を書く) |
| `deadline` | 期限 (`exit.date`) までに数字が出なければ売る (売りの4分類の「時間切れ」) |

ルールの例外として持つ (線を割ったのに持つ) ときは、レポートにその旨を書く。

#### §3 決算前の行動

`upcoming` に入っている「持つ」銘柄は、決算後の行動 (`after_earnings`、例:「売上が会社計画を下回ったら半分売る」) を先に書いてもらう。

#### §4 維持率で売る順番

推定維持率 `margin_rate_pct`、目標 (`week_target`。旧ログは `target_rate`)、追証までの下落率 `falls` を見せ、「推定維持率が何%を割ったら、どの銘柄を何株、どの順で売るか」を決めてもらう。落ち着いている今のうちに決めておくのが目的。下がり切ってから売る銘柄を選ぶと、底で投げることになる。

#### §5 調整入りの点検

市場ステートが調整に入ったのがきっかけのときだけ行う。量は動かさず、次の4つを決めてもらう。

1. **逆指値**: 全部の建玉に、そのロットの戦略の幅で逆指値が入っているか (自己申告)。前回以降の買い増しのロット (`additions.lots` の `is_addition`) は名前を挙げて聞く
2. **線に近い玉**: 損切りの線 (`line_price`) まで残り数%の玉を挙げ、線を割ったらどうするかを割る前に決める。§2 と同じく「持つ」なら売る条件を1つ
3. **新しい買いの約束**: 調整が解けるまで (市場ステートが上昇確定に戻るまで)、新しい買いをどう絞るかを選んでもらう。複数選んでよい。選択肢の例: 買い増しはしない / 新規は損切り幅の狭い戦略 (短期・中期) だけ / 新規の建玉は1件あたり小さめ (金額を本人が決める) / 絞らない。決めたことは決定の `buy_limits` に入れ、次の点検で `additions.lots` と照らし合わせる
4. **維持率で売る順番**: §4 を、今の保有で引き直す (いつもの §4 と同じ。調整入りのときは必ず聞く)

### 5. 保存する

決定をスクラッチパッドに JSON で書く。

```json
{
  "holdings": [
    {"code_s": "6264", "stock_name": "マルマエ", "action": "cut", "qty": 200},
    {"code_s": "7729", "stock_name": "東京精密", "action": "hold", "reason": "HBM向けの受注が残る",
     "exit": {"type": "price", "price": 9800, "date": "2027-02-10"}, "after_earnings": "受注が前期を下回ったら全部売る"}
  ],
  "sell_order": {"trigger_margin_rate": 50, "codes": [{"code_s": "285A", "qty": 135}]},
  "buy_limits": {"until": "市場ステートが上昇確定に戻るまで", "rules": ["no_addition", "narrow_only"],
                 "note": "新規は1件50万円まで"}
}
```

- `action` は `cut` (切る) / `reduce` (減らす) / `hold` (持つ)。`qty` は売る株数で、決まっていなければ省く
- 決まらなかった銘柄は入れない (レポートに「保留」と書く)
- `buy_limits` は §5 を行ったときだけ入れる。`rules` は `no_addition` (買い増ししない) / `narrow_only` (新規は損切り幅の狭い戦略だけ) / `small_size` (新規は小さめ。金額は `note`) / `none` (絞らない)

完成したレポートを `.md` で書き、保存する。JSON は保存時に作り直されるので、**手順1と同じ日のうちに保存する**。

- 運用機: `cd scripts && ../.venv/bin/python portfolio_review.py save --decisions decisions.json < report.md`
- 開発機: 決定とレポートを運用機に送ってから保存する (`scp decisions.json report.md macmini:/tmp/` のあと `deploy/macmini.sh run python portfolio_review.py save --decisions /tmp/decisions.json < report.md`)

「決定が足りません」と出たら、足りない項目を利用者に聞いて書き足す。「既に保存済みです」と出たら上書きしない。利用者に伝え、消すかどうかは利用者が決める。

## してはいけないこと

- 銘柄の推奨、売買の提案 (選択肢を並べるのは可、どれを選ぶべきかは言わない)
- JSON に無い数字を作ること
- 台帳の仮説を一次資料で精査すること (別のフロー)
- 損益の大きさで人を評価すること
