# shelve を使い続け、SQLite 移行は保留する

- Status: Accepted
- Date: 2026-09-21
- Related: #174, #194, #450, #451, #452

## Context

運用機 (MacMini) への移行を前に、shelve (`dbm.dumb`) の同時アクセスで DB が壊れるかを確かめる必要があった。日次バッチ (約3,900銘柄を1時間半〜2時間強) と WebApp が同じ DB を読み書きし、stocks_shelve は1日100〜120MB 肥大するので定期的な compact が要る。

実運用と同じ条件で実測した結果:

| 状況 | 結果 |
|---|---|
| 日次バッチの書き込み中に読む | 11,100件読んで破損0 |
| writer 2本の並走 (バッチ + WebApp の再取得ボタン) | 1,001件検証して破損0 |
| compact 中の読み書き | 読み手177回中176回・書き手401件中100件が破損 |

壊れるのは compact のときだけだった。バッチは1銘柄ごとに open → 書き込み → close し、書き込みは一瞬なので実質衝突しない。

## Decision

- shelve を使い続ける。**SQLite (WAL) への移行 (#450) は保留**し、priority:low とする
- compact 中の破損は、`ShelveDB` の open〜close 全区間のロック (書き込み EX / 読み取り SH、compact は全工程 EX) で防ぐ (#451)。これで compact を週1回、日次バッチの末尾で自動実行できる
- ロックファイルは `<db>.dbm.lock`。research / portfolio の `<db>.lock` と同名にすると自己デッドロックする

## Rationale

- 実害が確認できたのは compact だけで、ロックで潰せた。書き込みを open 全体で EX にしても、並行する一覧表示300銘柄の待ちは中央値10ms・最大18ms
- 移行はいつでもできる。shelve の直接利用は無く、全85箇所が `ShelveDB` 経由 (使用 API 8種類)
- ホスト変更 (MacMini 移行) とバックエンド変更を同時にやると、問題が起きたときに切り分けられない

採用しなかった案:

- **ロックを read メソッド単位や一部区間だけにかける** — 実測でロック無しと同じ結果になり、効果が無かった
- **運用機移行と同時に SQLite へ移す** — 上記の切り分けの理由で見送った

## Consequences

- 次のどれかが起きたら SQLite 移行を再検討する
  - compact 以外での破損が観測された
  - writer が増えた
  - 複数ホストからの同時アクセスが要るようになった (flock はホスト内でしか効かない)
  - compact の運用自体が負担になった
  - バッチが DB を開いている区間が長くなる実装変更をした (上の待ち時間は1銘柄ごとに open/close する実装に依存している)
