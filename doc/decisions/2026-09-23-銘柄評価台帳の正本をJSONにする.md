# 銘柄評価台帳の正本を JSON 1ファイルにし、書き込みは Shintakane 経由に限る

- Status: Accepted
- Date: 2026-09-23
- Related: #465, #466, #467, #456

## Context

ChatGPT との銘柄分析の最後に、Google スプレッドシート「投資PJ_銘柄評価台帳」を差分更新していた。
シート経由の更新は手順が多く (検索 → 構造解析 → 行・列特定 → セル更新)、手入力で値が崩れ、前回値の履歴も文章頼みだった。
機能追加は凍結中だが、日々の手動ルーチンの運用コストを下げるため例外として進めた。

## Decision

- 正本は `KS_DATA_DIR/stock_ratings/stock_ratings.json` (現在値)、履歴は `stock_ratings_history.jsonl` (追記のみ)
- **書き込みは `stock_ratings.py` (と、それを使う MCP の `update_stock_rating`) からだけ**。Drive アプリ等で JSON を直接編集しない
- スプレッドシートは 2026-09-23 に凍結。JSON → シートの表示用出力は一方向で、双方向同期はしない
- 仮説まわりの項目は配列にせず文字列のまま持つ
- research_shelve や code_rank とは統合しない (#456)

## Rationale

保存形式の比較で採用しなかった案:

- **JSONL で現在値を持つ** — 現在値は読み直して全体を書き戻すので追記向けの利点が効かず、長い日本語が1行に詰まって読めない
- **research_shelve に同居** — Drive・スマホから読めない。MCP サーバーのプロセスから shelve へ書く経路を増やしたくない
- **SQLite** — 新規導入のコストに見合わない。将来 #450 と合わせて検討する (`stock_ratings.py` の API を保てば呼び出し側は変わらない)
- **仮説を配列に分ける** — 現シートは散文で、機械的に分けると内容が崩れる。更新は項目全体の置き換えなので、配列にしても粒度は変わらない

## Consequences

- 評価の更新は必ず履歴が残る。前回値との比較は履歴から出せる
- ChatGPT の Drive コネクタから読む経路は、JSON が Drive 同期下にあることに依存する (運用機での配置は OPERATIONS.md を参照)
