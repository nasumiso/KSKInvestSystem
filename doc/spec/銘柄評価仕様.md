# 銘柄評価仕様

銘柄の点数は2系統ある。日次バッチが全銘柄に付ける **code_rank (総合PT)** と、ChatGPT との分析で付ける **銘柄評価台帳 (stock_ratings)** である。この文書は、それぞれの役割と、各軸が何を測り何を測らないかを定める。同じ言葉 (ファンダ・モメンタム) が別の意味で使われている点は [用語集と不変条件.md](../用語集と不変条件.md) の「評価とスコア」を参照。

配点・閾値・レンジ表の数字はここに書き写さない。正本は次のとおり。

| 対象 | 正本 |
|---|---|
| code_rank の重み | `make_stock_db.compute_total_pt` |
| code_rank の各列の閾値 | 下の表の各関数 |
| 台帳の採点ルール (配点・内訳・レンジ表・原則) | `scripts/mcp/shikiho_server.py` の `UPDATE_STOCK_RATING_DESCRIPTION`。ChatGPT が読むのはここなので、文書と二重に持たない。変えたら `stock_ratings.RUBRIC_VERSION` を上げる |

見直しの検討経緯と進行中の変更は [plan/issue456-採点仕様の見直し.md](../plan/issue456-採点仕様の見直し.md) にある。

## 役割

| | code_rank | 評価台帳 |
|---|---|---|
| 扱う情報 | 定量 | 定性 (一次資料の読解と判断) |
| 対象 | 全銘柄 (約3600) | 自分のユニバース (保有・準保有・監視のうち調べた銘柄、50前後) |
| 基準 | 全銘柄に同じ式 | 同じ採点ルールで ChatGPT が付ける |
| 使い道 | 広域の絞り込み、保有銘柄の相対的な品質の監視 | ユニバース内の入替え・サイズ判断の順位付け |
| 使わない用途 | 上位を機械的に買う | Active / Watch を総合点で自動で決める。保有の継続を総合点だけで決める |

両者は統合しない。配点をそろえる、code_rank を台帳のベース値にする、といった統合は、対象範囲が違う (全銘柄と50銘柄) ので前提にしない。関連付けは、台帳の銘柄について両方を並べて見る程度に留める。

自分の手動評価 (S〜E) は code_rank に入れない。定性情報で、ユニバースにしか付かないため。台帳の原則3 (保有状況や仮説を総合点に足さない) と同じ理由。

## code_rank の各列

| 列 (code_rank.csv の見出し) | 測るもの | 測らないもの | 実装 |
|---|---|---|---|
| 業績 (プロフィット/クォリティ) | オニール型の成長株らしさ。通期・四半期の売上と利益の成長 | 将来の数字の確からしさ、受注残・中計 | `gyoseki.calc_gyoseki_score` |
| 指標 (バリュー/サイズ) | 時価総額 (小型・中小型ほど高い山型)、有利子負債、はっしゃん式理論株価との乖離 | 成長率に対する割安さ | `shihyou.calc_shihyo_pt`、`rironkabuka.calc_theory_pt` |
| モメンタム | 対 TOPIX の相対強度の分布上の位置 (RSスコア) | 決算後の反応、出来高 | `price.calc_momentum_pt_value` |
| テーマ人気 (旧「ファンダメンタル」、#546) | 株探テーマの人気順位 (旬のテーマに属しているか) | 事業の質 | `master.calc_fundamental` |

- 指標は、成長株の割安さの物差しとしては相性が悪い。はっしゃん式理論株価は予想 EPS と ROE で決まり、成長率の項が無い。全銘柄に一律で使える成長株向けの物差しは作れていないので、割安さの判断は台帳の Valuation に任せる
- PER・PBR・PSR は使わない。業態・セクターで水準が違い、全銘柄に同じ閾値を当てられないため
- 実効的な効き方 (2026-11-01 の計測): 総合PTはほぼ業績の順位で、テーマ人気は 44% の銘柄が0点。数字は計画書を参照

## 評価台帳の各軸

軸の境界は次の並びで考える。隣り合う2つの間だけを1つの軸が受け持ち、他の軸の領分を見ない。

```
株価 ─(Valuation)─ 今わかっている数字 ─(未織込)─ これから出る数字 ─(ファンダ)─ 事業の質と持続性
```

| 軸 | 測るもの | 測らないもの |
|---|---|---|
| ファンダ | 業績加速、将来利益の可視性、構造成長、質とリスク。受注残・中計・構造変化を含む | 株価、市場がどう見ているか |
| 未織込 | 今わかっている数字 (会社予想・四季報予想) と、これから出る数字の差 | 株価の水準・PER・騰落・決算後の株価反応 |
| Valuation | 適正株価 (AI) に対して、基準日の終値に余白があるか (システムが換算) | 事業の良し悪し |
| モメンタム | 個別の相対強度と業態テーマの勢い (システムが算出)。急騰自体は減点しない | 割高さ (Valuation の領分) |

- **採点ルール Ver3 (#544)**: AI (ChatGPT) が付けるのはファンダ・未織込と適正株価だけ。株価で変わる Valuation とモメンタムは、システムが基準日の終値から毎日出す。AI は株価で変わらないものを判断し、株価で変わるものはシステムが出す (Ver2 では Valuation とモメンタムが AI の採点日の株価に固定され、総合点の中で時点が食い違っていた)
- 総合点 = ファンダ + 未織込 + Valuation + モメンタム。保存せず読み出すたびに計算する (`stock_ratings._with_system`)。意味は企業価値の順位ではなく、**現在価格からの中期投資魅力度**
- Confidence (A/B/C) は総合点に入れず、ポジションサイズの判断に使う
- 書き込みは `update_stock_rating` (MCP) と `stock_ratings.py` からだけ。変更前後の値は変更履歴に残る ([判断記録](../decisions/2026-09-23-銘柄評価台帳の正本をJSONにする.md))

## Status (評価台帳)

台帳に載せるのは、`投資戦略.md` の層でいう**深掘り候補 + 実保有**、つまり一次資料で調べた銘柄だけ。監視の層は載せず、code_rank と保有銘柄画面で見る。

| Status | 意味 | 空にできない項目 |
|---|---|---|
| Active | 仮説が生きていて、持っている / 入る準備ができている。買いルールの A (ファンダ) を満たし、残るのは B (モメンタム)・C (タイミング) の判断だけ | thesis・risks・checkpoints |
| Watch | 仮説はあるが確認待ち。何を待っているかを checkpoints に書く | thesis・risks・checkpoints |
| Archive | 仮説崩れ・時間切れ・見送り。Archive にする更新で、外す理由を note に書く (見送りの記録) | note |

- Archive は消さずに残し、比較の対象から外す。既定の一覧 (`list_ratings`、MCP の `list_stock_ratings`)・HTML の順位・一括の付け直しに入れない。HTML では末尾に畳む
- 保有ステータス (1保/2準/3監) とは連動させない。台帳の Status は銘柄への判断で、保有ステータスはポジションの状態なので、売っただけで判断が変わったことにしない。代わりに次の制約を置く
  - 1保 ⇒ Active。ただし売買戦略が 大型高配当・短期イベント・短期底値リバ のものは除く (ファンダの仮説で持たない)
  - Active ⇒ 1保 か 2準
  - Active / Watch ⇒ ポートフォリオに登録されている (業態テーマなどはポートフォリオ側にある)
- 上限は Active 20 / Watch 30 (実保有15 + 次に買う5、深掘り候補の残り。一次資料でファンダを追い続けられるのは合計50銘柄までとみた、2026-11)。上限超過は決算シーズン明けの月 (3・6・9・12月) にだけ知らせ、整理はその月にまとめて行う
- 古くなった評価: Active は直近の決算発表日から14日を過ぎても更新されていないとき、Watch は最後の更新から決算を2回またいだとき (売りの4分類の「時間切れ」)。決算発表日は `gyoseki.load_kessan_dates`
- 決算直後の未更新: 直近の決算発表日の当日から14日までの間に台帳が更新されていないもの。決算の分析し忘れに早く気づくため。Active は銘柄名と決算日を本文に出し、14日を過ぎたら「古くなった評価」に移る。Watch は件数を出して銘柄はポップアップにし、14日を過ぎたら消す (Watch が古くなったことは、決算を2回またいだ判定で知らせる)
- 制約・上限・決算直後の未更新・古くなった評価は、トップの「今日のアクション」に「台帳と保有のずれ」「台帳の整理」「決算後の台帳更新」「台帳の更新待ち」の4行で知らせるだけで、Status は自動で変えない (変えるのは判断なので人が台帳を更新する)。空にできない項目は `update_stock_rating` の検証で守る
- これらは点数の付け方を変えないので、`RUBRIC_VERSION` は上げない

### 運用

台帳を更新するのは人の判断で、手を動かすのは ChatGPT (MCP の `update_stock_rating`) が主な経路。Claude Code からも同じ MCP ツールで、運用機では CLI (`stock_ratings.py set <コード> --status … --reason …`) でも更新できる。WebApp の台帳ページ (`/stock-ratings`) は表示だけ。

- **決算のたび**: 「今日のアクション」の「決算後の台帳更新」に出た銘柄を、決算資料を読んで ChatGPT と更新する。Active はその決算で仮説が生きているか、Watch は checkpoints の待っていたことが起きたか (Active に上げるか、Archive にするか) を見る
- **外すとき**: 「Archive にして、理由は …」と頼む。Archive にする更新では note (外す理由) が必須で、空だと検証で弾かれる。売っただけでは Archive にしない (保有ステータスと台帳の Status は別の判断)
- **銘柄数の整理 (3・6・9・12月)**: 決算が出そろった翌月にまとめて行う。「台帳の整理」に上限超過が出たら、ChatGPT で `list_stock_ratings` を出して外す銘柄を決め、Archive にする。システムは外す候補 (`stock_ratings.archive_candidates`) を理由つきで示す。理由は3つで、ポートフォリオとの食い違い (Watch なのにポートフォリオに無い / Active なのに 1保・2準でない)、決算の後に未更新の Watch、最後の更新から90日以上。候補は「台帳の整理」の行のポップアップと、`list_stock_ratings` の `archive_candidates` に同じものが出る。候補は材料で、外すかどうかは人が決める

## データの出どころ

| 軸 | いま | 出どころ |
|---|---|---|
| ファンダ・未織込 | ChatGPT が採点 | MCP の四季報・決算資料・中計・IR回答 ([MCP連携.md](MCP連携.md)) |
| Valuation | 適正株価は ChatGPT が付け、点はシステムが換算 | 下の「システムが出す2軸」。理論株価・PER は参考として MCP で渡す |
| モメンタム | システムが算出 | 下の「システムが出す2軸」 |

## システムが出す2軸 (評価台帳)

`stock_ratings.compute_system_scores`。

**基準日**: 業態テーマ順位の最新記録日 (日次バッチが記録する)。RS と終値は、その銘柄の最新の株価の日付が基準日と一致するときだけ使う。全銘柄が同じ日の終値で比べられることを仕組みで保証するため。基準日は台帳の HTML の見出しと MCP の get / list に出す。基準日そのものが古いこと (日次バッチの停止) は判定しない (祝日の判定が要り、バッチの失敗は /dev と日次レポートで分かる)。

**Valuation** (0〜20): 上昇余地 = 適正株価 ÷ 基準日の終値 − 1 を、−20% → 0点・+20% → 10点・+60% → 20点の直線で換算する (範囲外は切り詰め)。適正株価が無い・終値が基準日のものでないときは中央の10点で `missing` (`fair_price` / `price_stale`)。理論株価 (はっしゃん式、先行も) と株探の PER は、点数には使わず `reference` として並べる (理論株価は成長率の項が無く、成長株を系統的に安く出すため、AI がどれだけ成長を上乗せしたかを見る比較の物差しにする)。

**モメンタム** (0〜20) = 個別の相対強度 0〜10 + 業態テーマの勢い 0〜10。

- 相対強度: RSスコア (`momentum_pt`) ÷ 10 を四捨五入
- 業態テーマ: ポートフォリオのレコードの業態テーマについて、日次バッチが記録した最新のテーマ順位 (6ヶ月相対、[判断記録](../decisions/2026-10-26-業態テーマの順位は6ヶ月相対で日次に記録する.md)) を、1位 = 10点・最下位 = 0点で線形に割り当てる。テーマが2つなら平均。RSスコア平均を使わないのは、個別の要素と同じ物差しを2回使うことになるため
- 欠けた要素 (価格データが無い `rs`、株価が基準日のものでない `rs_stale`、ポートフォリオに無い・業態テーマが無い・順位の付いたテーマが2未満 `theme`) は 5点で埋め、`missing` に要素名を入れる
- 決算後の反応・出来高は入れていない (#545 で検討)

**2軸に共通**

- 欠けた値のある点は、HTML で「欠」を付ける。読み出し自体に失敗したときも全銘柄を欠けた扱いにして、総合点は必ず出す
- 出すところ: MCP の `get_stock_rating` (内訳と参考値) と `list_stock_ratings` (点と欠けた値)、台帳の HTML、Drive に出す JSON の写し (`system`)。**正本の JSON には保存しない** (読むたびに計算する)
- 作り直すタイミング: 台帳の更新時と、日次バッチ (`list_all_db`) でテーマ順位を記録した直後 (`stock_ratings.refresh_outputs`)
- 台帳を更新したときは、その時点の値 (基準日・終値・適正株価からの換算を含む) と採点ルールの版を変更履歴に残す。前向き検証で採点時の値を使い、採点時からの値動きと、AI が当時の株価にどれだけ引っ張られたかを見るため (`rs_rank_log` は250日で消え、銘柄DBは揮発DB)
- Ver2 → Ver3 の移行は `stock_ratings.py migrate_v3` (一度きり)。全銘柄から AI のモメンタムと Valuation の点数を外し、値は変更履歴に残す
