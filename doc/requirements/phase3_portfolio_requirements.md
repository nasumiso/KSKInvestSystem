# Phase 3 要件定義：保有銘柄管理ダッシュボード

> 保有銘柄の日次モニタリングと執行弱点補強のための管理機能

---

## 1. 背景

### 既存システムの現状

- **Phase 1完了**: research_shelveに849銘柄分の時系列スナップショットと手動メモが蓄積
- **Phase 2完了**: Shintakane Research Webアプリで銘柄の深掘り分析・比較が可能
- スプレッドシート「銘柄調査シート」の内容はresearch_shelveへ移行済み

### 残る課題

スプレッドシート「保有銘柄シート」（139銘柄 × 36列）が未移行のまま残っている。このシートの目的は**保有銘柄の日次モニタリング**であり、銘柄調査シート（深掘り用）とは明確に異なる用途：

| | 銘柄調査（Phase 1/2で対応済） | 保有銘柄（Phase 3で対応） |
|---|---|---|
| 主目的 | 深掘り分析・判断材料の蓄積 | 一覧モニタリング・売買判断 |
| 見る頻度 | 決算時・新規検討時 | 毎日（寄り前/引け後） |
| 表示方向 | 1銘柄を縦に展開（時系列） | 多銘柄を横並び（ダッシュボード） |
| データの時間軸 | 時系列の蓄積 | 現在のスナップショット中心 |

### 認知プロファイルからの最重要視点

MY_INVESTER_STRATEGY.mdで繰り返し指摘されている通り、こすうけさんの認知プロファイル（決断性31・自責87・悲観傾向75）の最大の急所は「イグジット（売り）の判断」。保有銘柄管理は単なる一覧表示ではなく、**この執行弱点を外部システムで補うための最重要機能**として設計する。

## 2. ゴール

1. **保有ステータスの一元管理**: 1保（保有中）/ 2準（準保有：直近売却 or もうすぐ買いたい）/ 3監（監視のみ）のステータス管理
2. **日次モニタリング用ダッシュボード**: 3ステータス別タブで、毎日の状態確認が効率的にできる
3. **執行弱点補強のアラート**: 保有銘柄に警告シグナルが出た時にダッシュボード上で強調表示
4. **行動記録の蓄積**: アクションログ（自分の判断）とイベントログ（システム検知）による振り返り基盤の構築

## 3. アーキテクチャ方針

### DB分離の原則

既存3種のDBに加えて新たに `portfolio_shelve` を作成。データの性質で明確に分離する。

| DB | 性質 | 更新方式 |
|---|---|---|
| stocks_shelve（既存） | 揮発性キャッシュ（最新値のみ） | Shintakane日次バッチで自動更新 |
| research_shelve（Phase 1） | 時系列スナップショット＋調査メモ | 決算検知で半自動＋手動メモ |
| **portfolio_shelve（新規）** | **保有状態＋売買判断に関する手動メモ** | **手動中心＋日次バッチでイベント検知** |

**依存関係は一方向**: portfolio_shelve が他の2DBを参照する形。既存DB側のコードは変更しない。

### ファイル配置

```
data/stock_data/stocks_shelve       ← 既存
data/stock_data/research_shelve     ← Phase 1
data/stock_data/portfolio_shelve    ← 新規
```

### データフロー

```
[ブラウザ]
    ↓↑ HTTP
[Phase 2のWebアプリに機能追加]
    ├─ portfolio_shelve（読み書き）: ステータス・メモ・ログ
    ├─ research_shelve（読み取り）: 調査メモ・時系列
    └─ stocks_shelve（読み取り）: 最新指標・シグナル

[Shintakane日次バッチ]
    └─ portfolio_shelve（書き込み）: 保有銘柄のイベントログ自動記録
```

### 既存アプリへの統合

Phase 2で実装済みのShintakane Research Webアプリに機能追加する形で実装。新規アプリは作らない。

## 4. portfolio_shelve 基本設計

### レコード構造の概要

キーは `code_s`（stocks_shelve/research_shelveと同一）。保有銘柄のみがレコードを持つ（全銘柄のレコードは持たない）。

1レコードは大きく3つのブロックから成る：

**ステータス管理**:
- 現在の保有ステータス（1保 / 2準 / 3監）
- 初回登録日、最終更新日

**手動メモ群**（保有判断に関わるもの）:
- 業態・テーマ
- ウォッチ・IN理由
- 投資売買アイデア
- イナゴ元・きっかけ
- 高市感応度（政策テーマ感応度の自己評価）

**ログ参照**:
- このレコードに紐づくアクションログ・イベントログへの参照（後述）

### ステータス遷移の扱い

ステータスは時系列で遷移する（例: `3監 → 2準 → 1保 → 2準（売却）→ 1保 → 2準 → 3監 → 削除`）。遷移のたびにアクションログへ記録する。

「売却」は 1保 → 2準 のステータス変更として扱う（§5-5）。アクションログ種別「売却」で別途記録し、純粋なステータス変更と区別する。
「削除」は 3監 からのみ可能で、portfolio_shelve からレコードを物理削除する操作（§5-5）。アクションログ・イベントログは独立 store（§6）に残るため、銘柄単位の過去ログは削除後も code_s 指定で参照可能。

### 表示する指標データの扱い

PER・時価総額・RS・シグナル等の定量データはportfolio_shelveには保存せず、表示時に stocks_shelve から都度参照する。これにより：
- リアルタイム性が保たれる
- 同期処理が不要になる
- portfolio_shelveは手動管理データのみを持ち、構造がシンプルに保たれる

## 5. ダッシュボード画面構成

### 5-1. 3ステータス別タブ

- **保有中（1保）** : 実際にポジションを持っている銘柄
- **準保有（2準）**: 直近売却 or もうすぐ買いたい、保有との往復頻度が高い銘柄
- **監視（3監）** : 興味はあるがポジションは持たない銘柄

タブごとに同じ構造の一覧を表示。

### 5-2. 一覧表の表示内容

保有銘柄ダッシュボードで毎回必ず確認する6カテゴリをすべて表示：

| カテゴリ | 主な内容 | データソース |
|---------|---------|------------|
| 最新指標 | PER、時価総額、配当 | stocks_shelve |
| 業績 | 売上・利益成長率、進捗率 | stocks_shelve |
| テクニカル | RS、ステージ、トレンドテンプレート | stocks_shelve |
| シグナル | 新高値、警、売、買い集め等 | stocks_shelve |
| 理論株価乖離率 | 現在値と上限/下限 | stocks_shelve |
| 手動メモ | IN理由、売買アイデア | portfolio_shelve |

情報密度が高くなるため、重要度に応じた視覚階層（常時表示／開閉式サブセクション）の整理は実装時に判断する。

### 5-3. 警告シグナルの視覚的強調

保有中（1保）・準保有（2準）の銘柄に以下のシグナルが発生した場合、赤バッジ等で目立たせる：

- 「警」シグナル（弱含み形成中）
- 「売」シグナル（RS弱＋レシオ悪化）
- トレンドテンプレート崩れ（前回との差分が大きい）
- 業績下方修正
- 順位大幅下落

**これが執行弱点補強の核心**。毎日見る動機の大部分は「今日、何かアクションを検討すべきか」の確認であり、見逃しを防ぐ設計が最優先。

監視（3監）銘柄のポジティブシグナル（新高値等）の強調表示については、準保有への格上げ判断を促す目的で実装するかどうかを実装時に判断する。

### 5-4. ステータス変更UI

一覧から銘柄を選択し、ステータス変更ダイアログで以下を入力：
- 変更後のステータス
- 変更理由（この入力がアクションログになる）

変更時に自動でアクションログへ記録される。

### 5-5. 銘柄の追加・売却・削除

ライフサイクル全体の操作を以下のように定義する。3 タブ構造（1保 / 2準 / 3監）を崩さず、ステータス遷移とは別軸で「追加（新規登録）」と「削除（物理削除）」を持たせる。

#### 追加（新規登録）

- 銘柄調査ページ（`/stock/<code_s>`）または検索ページから「3監に追加」ボタンで portfolio_shelve に新規登録
- デフォルトステータスは **3監** 固定（いきなり 1保 / 2準 では登録しない。誤登録防止と運用の単純化のため）
- 1保 / 2準 への遷移は登録後に §5-4 のステータス変更UIで行う
- 同時にアクションログへ「初回登録」種別で 1 件記録

#### 売却（1保 → 2準）

- ステータス変更ダイアログから「1保 → 2準」遷移を選んだ場合、これは概念上「売却」を意味する
- アクションログには「売却」種別を別途定義し、単なるステータス変更（理由メモ付き）と区別して記録する
  - 後の振り返りで「いつ売ったか」「警シグナルから何日後に売ったか」を抽出できるようにするため
- ポジションを完全に手放すが、再エントリー候補として残すケース（こすうけさんの取引パターンの大半）を 2準 で表現する

#### 削除（物理削除）

- **3監からのみ削除可能**。1保 / 2準 の銘柄を削除するには一度 3監 へ戻す必要がある
  - 誤って保有中銘柄を消す事故を防ぐためのガード
  - 「もう監視もしない」という明確な意思決定を 3監 への遷移として可視化する効果もある
- 削除時はアクションログに「削除」種別で記録（理由必須）
- レコード本体は portfolio_shelve から物理削除する
- アクションログ・イベントログは独立 store（§6）に残るため、削除後も code_s 指定で過去ログを参照することは技術的には可能。振り返りビュー側で削除済み銘柄をどう扱うかは §6-3 とあわせて実装時に判断する

## 6. ログ設計

アクションログとイベントログは**別管理**とする。混在させず、それぞれ独立したコレクションとして設計する。

### 6-1. アクションログ（手動・自分の判断記録）

**何を記録するか**:
- ステータス変更（IN/OUT/格上げ/格下げ）
- 売買実行（買い/売り/見送り）
- その他の判断メモ（「今日は動かない」等も含めて任意で記録可能）

**アクション種別**（最低限、§5-5 で定義した以下を区別する。それ以外の細分は実装時に判断）:
- `初回登録` — portfolio_shelve への新規追加（§5-5 追加）
- `売却` — 1保 → 2準 のステータス変更時（§5-5 売却）
- `削除` — 3監 からの物理削除（§5-5 削除）
- `ステータス変更` — 上記以外のステータス遷移
- `買い実行` / `見送り` / `メモ` 等 — 任意の判断記録

**スキーマの要素**:
- 日時
- 対象code_s
- アクション種別
- 変更前後（ステータス変更の場合）
- 理由・メモ
- 関連イベントへの参照（任意）

レコード本体（portfolio_shelve）が削除されてもアクションログは独立 store として残る。これにより削除済み銘柄も code_s 指定で過去ログを参照可能（振り返りビューでの扱いは §6-3 / 実装時判断）。

### 6-2. イベントログ（自動・システム検知記録）

**何を記録するか**:
- 保有銘柄で警告シグナルが発生した日時と内容
- トレンドテンプレート崩れ等の重要な指標変化
- 決算発表の検知

**スキーマの要素**:
- 日時
- 対象code_s
- イベント種別
- 詳細（シグナル名、変化内容等）

**記録対象の銘柄**:
- portfolio_shelveに登録済みの銘柄のみ（全銘柄ではない）
- Shintakaneの日次バッチで自動記録

### 6-3. 振り返りビュー

個別銘柄のページで、アクションログとイベントログを時系列に並べて俯瞰できる。

これにより「警シグナルが出てから自分が何日後に売却を決めたか」「シグナルを見逃した時はどういう局面だったか」という**自己の行動パターンの検証**が可能になる。これが売り判断の弱点補強における振り返り機能として機能する。

## 7. 既存データ源からの移行

現状、保有・ウォッチ情報は以下 2 箇所に分散している。Phase 3 では両方を `portfolio_shelve` に統合する。

- **スプレッドシート「保有銘柄シート」** (139銘柄 × 36列): 業態・IN理由・売買アイデア等の手動メモを含む詳細データ
- **`my_watch_list.txt`** (DATA_DIR 直下): 日次バッチ・WebApp の現実の真実源。`H` 接頭辞付き = 保有、接頭辞なし = ウォッチ

### 7-1. スプレッドシート「保有銘柄シート」からの移行

#### 移行対象（139銘柄）

36列のうち、移行が必要なのは以下のみ：

| 移行する列 | 移行先 |
|-----------|-------|
| 銘柄コード、銘柄名 | レコード識別情報 |
| 保有リスト（1保/2〇/3監） → (1保/2準/3監) | 保有ステータス |
| 業態・テーマ | 手動メモ |
| ウォッチ・IN理由 | 手動メモ |
| 投資売買アイデア | 手動メモ |
| イナゴ元・きっかけ | 手動メモ |
| 高市感応度 | 手動メモ |

他の指標系列（指標、理論株価、順位、業績等）は stocks_shelve から表示時に自動参照されるため、移行不要。

#### 移行方針

- 一括移行スクリプトを作成（Phase 1の移行スクリプトと同じパターン）
- アクションログ/イベントログの過去分は復元不可能なため、移行時は記録なしで開始する
- 移行時点のステータスで「初回登録」のアクションログを1件記録するかは実装時判断

### 7-2. `my_watch_list.txt` からの移行・並行運用

`my_watch_list.txt` は現状以下の場所で「保有 + ウォッチ」の真実源となっている。Phase 3 ではこれらの参照先を `portfolio_shelve` に置き換える。

| 参照箇所 | 用途 |
|---|---|
| `portfolio.parse_my_portforio()` | 既存銘柄絞り込みの単一源 |
| `webapp/helpers.is_possess_now()` | 保有判定 |
| `make_stock_db.py` (auto-snapshot) | スナップショット自動追記対象の絞り込み |
| `kessan.py` / `disclosure.py` | 決算カレンダー / 適時開示の対象絞り込み |

#### 移行ステップ

1. **初期取り込み**: `my_watch_list.txt` を読み取り、以下のマッピングで `portfolio_shelve` へ一括登録
   - `H` 接頭辞付き → **1保**（保有中）
   - 接頭辞なし → **3監**（監視のみ）
   - **2準（準保有）の指定は txt には存在しない**ため、移行直後は 1保 / 3監 のみ。準保有への昇格・降格は WebApp 側で個別に実施する
   - スプシ「保有銘柄シート」の手動メモ（§7-1）が既に shelve に入っている場合はマージ。コンフリクト時は txt のステータスを優先（実運用上の真実源は txt のため）
2. **インターフェース置換**: `portfolio.parse_my_portforio()` は API シグネチャを維持したまま、内部実装を `portfolio_shelve` 参照に置き換える。これにより呼び出し側（kessan.py / disclosure.py / make_stock_db.py / webapp/helpers.py）は無修正で動く
3. **WebApp UI 提供**: §5-4 / §5-5 のステータス変更・追加・削除 UI を実装し、すべての操作を `portfolio_shelve` に対して行う
4. **txt 廃止**: 並行運用期間後、`my_watch_list.txt` を read-only バックアップとして残すか、完全削除する

#### 並行運用期間（1〜2週間）

移行直後の安全マージンとして、以下を 1〜2 週間運用する:

- WebApp 操作は `portfolio_shelve` を更新する（正）
- 同操作で `my_watch_list.txt` も一方向同期で書き出す（副。`shelve → txt` のみ。txt の手編集は推奨しない）
- 期間中、txt と shelve の内容に違和感がないことを目視確認
- 期間終了後、txt 書き出しを停止し、ファイルを廃止 or read-only バックアップ化

> **二重管理の注意**: 並行運用は最小期間に留める。長引かせると「どちらが正か」が曖昧になり、誤りの温床になる。期間中に txt を手編集するのは禁止し、すべての追加・削除・ステータス変更は WebApp 経由で行う。

## 8. スコープ外

- **チャート表示**: 別タスクで専用の一覧ページを作成予定
- **外部通知**（メール/LINE/Slack等）: ダッシュボード内の視覚的強調で対応。外部通知が必要になった時点で別issueで検討
- **損益管理・ポジションサイジング**: 本件は保有状態の管理のみを扱う
- **複数ポートフォリオ管理**（NISA/特定口座の分離等）: 現状は単一ポートフォリオ前提

---

## 9. 既存Phaseとの依存関係

- **Phase 1（research_shelve）**: code_sを共通キーとして相互参照。研究メモへのリンクなど
- **Phase 2（Webアプリ）**: 同一アプリに機能追加。独立した新規アプリは作らない
- **Shintakane日次バッチ**: イベントログの自動記録処理を日次実行に組み込む

## 10. 実装順序

1. portfolio_shelve 基盤モジュール
2. スプレッドシート移行スクリプト＋移行実施（§7-1）
3. `my_watch_list.txt` 取り込みスクリプト＋`portfolio.parse_my_portforio()` の内部実装置換（§7-2 ステップ 1〜2）
4. ダッシュボード画面（3タブ・一覧表示）
5. ステータス変更UI＋アクションログ記録（追加・売却・削除を含む、§5-4 / §5-5）
6. `my_watch_list.txt` 並行運用（shelve → txt 一方向同期、1〜2 週間）→ txt 廃止
7. Shintakane日次バッチへのイベントログ自動記録組込み
8. 警告シグナルの視覚的強調表示
9. 振り返りビュー（アクションログ＋イベントログの時系列表示）
