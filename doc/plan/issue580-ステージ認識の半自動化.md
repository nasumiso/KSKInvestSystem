# issue #580 Phase 1: ステージ変更履歴の記録と LLM の第二意見

issue: #580 (2026-Q4)。この計画書は Phase 1 だけを扱う。Phase 2 (矛盾の検知)、Phase 3 (遷移の候補) は Phase 1 を使ってから別に計画する。

## なぜ今やるのか

ステージ認識は保有の出口判断 (リスク管理) の土台だが、すべて手入力で、急落局面ではラベルが古いまま残る。#218 のルールベース案は実測で使えなかった (下表)。LLM に週足チャートを読ませると、人のラベルとほぼ重なった。

## 実測 (2026-11-11〜12、36件、各1回)

直近1か月にステージを付けた保有・準保有から無作為に36件。ステージを付けた日までで切った週足チャート (銘柄名を消し、左端の終値を100とした指数) を読ませた。

| 比べ方 | #218 ルール | Sonnet 5.5 基準なし | Sonnet 5.5 基準を規則として追加 | Sonnet 5.5 基準を参考として追加 | Fable 5.2 |
|---|---|---|---|---|---|
| select の値が完全に一致 | — | 10 | 18 | 11 | 15 |
| 主ステージが一致 | 11 | 20 | 22 | 20 | 22 |
| ステージが重なる | 12 | 34 | 30 | 34 | 34 |

- 「重なる」は、ステージ番号の集合に共通があること (3S と 3S~4S、1S と 1Sor3S)
- 「規則として追加」は「迷ったら遷移に逃げない」の1行も足した版。遷移を一切使わなくなり、言い切って外す例が増えた
- 人のラベルも見直すと変わる (6134 は 4S → 3S)。**完全一致を上げる調整はしない。見るのは「重なる」**

## ねらいと方針

- ステージを決めるのは人のまま。機械はラベルを書き換えない
- LLM の読み取りは、根拠つきの第二意見として人のラベルの隣に出す
- 人のラベルと重ならない銘柄だけを知らせる
- LLM には人のラベルを見せない (引きずられないようにする)

## 1. ステージ変更履歴

今は `memo.stage` を上書きするだけで、いつ何から何へ変えたかが残らない。後から復元できないので、まず記録を始める。戦略の変更履歴 (#492、`strategy_history:`) と同じ作りにする。

- 保存先: `portfolio_shelve` の `stage_history:<code_s>` (追記のみのリスト)
- 書く場所: `portfolio_shelve.update_memo()` の中。メモの更新と同じトランザクションで追記する
- 書く条件:
  - `stage` が変わった → `kind: "change"`
  - `stage` は同じで `last_research_update` だけ変わった → `kind: "confirm"` (見直したが変えなかった)
- 1件の中身: `{"date": 実際の日付, "recorded_at": now_iso(), "kind", "old", "new"}`
- 読み出し: `list_stage_history(code_s)`
- 既存ラベルの基準値は作らない (最初の変更の `old` に入る)
- Phase 1 では画面に出さない。Phase 3 の検証と月次の振り返りで使う

`confirm` を残す理由: 「LLM は 3S と言ったが、人は 2S のままにした」を後から数えるため。

`confirm` を残す操作: チャート一覧のステージ select は値が変わったときしか保存しない (同じ値を選び直しても何も起きない)。そこで、不一致の表示の隣に「据え置き」ボタンを置く (3. 画面)。押すと既存のメモ保存 (`/portfolio/<code_s>/memo`) に `last_research_update` を当日で送る。更新日セルを手で当日に直しても同じ結果になる。

## 2. LLM の読み取り (`scripts/stage_llm.py` 新規)

作りは `run_theme_news.py` / `theme_suggest.py` に合わせる (API キー不要、`claude -p`)。

### 流れ

1. 対象銘柄を決める (下記「対象とタイミング」)
2. 週足キャッシュ (`price._load_yfinance_cache(YFINANCE_WEEKLY_CACHE_FNAME % code_s)`) を読む。44週に満たない銘柄は読ませない
3. 一時フォルダに `chart.png` を描く。実測と同じ描き方に固定する: 週足ローソク足、10・30・40週線、出来高、終値は左端を100とした指数、縦軸は対数、横軸は週の番号。銘柄コード・銘柄名は画像にもファイル名にも入れない
4. 一時フォルダを cwd にして `claude -p <プロンプト> --model claude-sonnet-5-5 --allowed-tools Read --output-format json` を起動する。タイムアウト120秒
5. stdout の JSON を読み、`result` フィールド (モデルの本文) から `STAGE: <値>` の行を取り出す。JSON として読めない、`STAGE` 行が無い、値が `STAGE_OPTIONS` に無い、のどれかなら失敗として捨てる (実測の36枚×3回はこの方法で全件取れた)
6. `portfolio_shelve` の `stage_llm:<code_s>` に追記する (`claude -p` の実行中はロックを持たない。書くときだけ `_flock`)
7. 一時フォルダを消す

cwd をリポジトリにしないのは、CLAUDE.md を読み込ませないため (費用と時間が増える) と、Read で他のファイルを開かせないため。

### 保存する中身

`stage_llm:<code_s>` (追記のみのリスト。蓄積資産。LLM の出力は再現できないので `portfolio_shelve` に置き、日次バックアップに乗せる)

```
{"week": "2026-11-02",        # 読んだチャートの最新の週 (週足キャッシュの先頭)
 "run_date": "2026-11-12",    # 実行した実際の日付
 "stage": "3S~4S",
 "rationale": "...",          # STAGE 行を除いた本文
 "model": "claude-sonnet-5-5",
 "human_stage": "2S(3B)"}     # その時点の人のラベル (後で突き合わせるため)
```

### プロンプト

「基準を参考として追加」の版を使う。重なりは基準なしと同じ 34/36 で、聞き取った3つの基準 (issue 本文) が根拠の文章に反映される。「迷ったら遷移に逃げない」の行は入れない。

- 渡すもの: チャートの見方、9つの選択肢、境目の見方の参考 (3つ)、出力の形 (根拠2〜3行と、最終行に `STAGE: <値>`)
- 渡さないもの: 銘柄コード・銘柄名、人のラベル、前回の読み取り
- プロンプトの文面は `stage_llm.py` の定数に置く

外した2件は読むたびに入れ替わった (基準なしでは 6134 と 7080、この版では 4390 と 4434)。1回の読み取りには揺れがあるので、不一致の表示は「見直しの候補」として扱い、断定の言い方をしない。

### 対象とタイミング

- **対象: 保有 (1保) のみ**。2026-11-12 時点で23件
- **タイミング: 新しい週足が確定したら1回**。日次バッチで毎日呼ぶが、銘柄ごとに「保存済みの最新の `week` が、週足キャッシュの先頭と同じなら読まない」とする。結果として週1回になる。同じ日に2回走っても読み直さない。バッチが止まった週があっても、次に動いた日に追いつく
- 初回は23件すべてを読む
- 費用の目安: 1枚 約0.06ドル・約6秒。週に約1.4ドル相当、4並列で約1分 (サブスクの利用枠を使う)
- 準保有 (85件) は Phase 1 では自動で読まない。必要なら CLI で銘柄を指定する。Phase 2 で、矛盾の検知に当たった銘柄を対象に足す
- バッチでの位置: `shintakane_cron.sh` の theme-news の後、`offsite_backup.py` の前。失敗しても後段を止めない (theme-news と同じ扱い)
- 失敗 (タイムアウト、429、`STAGE` 行なし) はその銘柄を飛ばして `log_warning`。次の日のバッチで同じ週をもう一度試す

### CLI

- `python stage_llm.py run` — 対象を自動で選んで読む (バッチが呼ぶ)
- `python stage_llm.py run 6134 2681` — 銘柄を指定して読む (準保有・監視でも可。同じ週でも読み直す)

`doc/spec/コマンド一覧.md` に追記する。

### 依存

`requirements.txt` に `matplotlib` を足す。運用機の venv にも入れる (反映手順に書く)。ラベルは英数字だけなので日本語フォントは要らない。

## 3. 画面

### チャート一覧 (`portfolio_charts.html`)

ステージの select の隣に、LLM の最新の読み取りを出す。

- 表示: `LLM 3S~4S`。マウスを載せると、読んだ週と根拠が読める (title)。見出しの幅が足りないので週は title に入れる
- 人のラベルと**重ならず、かつ人がその後に見直していない**ときは、警告色にする
- 不一致のときだけ、隣に「据え置き」ボタンを出す。押すと更新日が当日になり (`confirm` が残る)、警告色とボタンが消える。ラベルを変える場合は、これまでどおり select を選ぶ
- 人のラベルが空のときは、参考として出すだけで色は付けない
- 読み取りが無い銘柄 (準保有など) は何も出さない

### 今日のアクション (`action_queue.py` のステージ行)

既存の「ステージ未更新: 決算後 保有 2、防の後 保有 1」に、「LLM と不一致 保有 N」を足す。リンク先は既存と同じチャート一覧 (`codes` で銘柄を絞る)。

### 「不一致」の判定

次の両方を満たすとき。

- LLM の最新の `stage` と、人の `memo.stage` のステージ番号の集合に共通が無い (`1Sor3S` は {1S, 3S}、`2S(3B)~3S` は {2S, 3S})
- 人のステージ更新日 (`last_research_update`) が、LLM の `run_date` より前

人がチャート一覧でステージを変えるか、「据え置き」を押すと、更新日が当日になり、不一致の表示は消える。次の週の読み取りでまた重ならなければ、また出る。

判定は `stage_llm.py` に関数を1つ置き、チャート一覧とアクション行の両方から呼ぶ。

## 4. 起きうる状況の確認

| 状況 | 動き |
|---|---|
| 同じ日にバッチが2回走る | `week` が同じなので読み直さない |
| 初回 | 保有すべてを読む。履歴は空から始まる |
| 週の途中で新しく保有になった | 次のバッチで読む (保存済みの `week` が無いため) |
| 売却して保有でなくなった | 読まなくなる。過去の読み取りは残る |
| 週足が44週に満たない (上場直後) | 読ませない。画面には何も出ない |
| `claude` が見つからない・利用枠切れ | その日は全銘柄を飛ばし、`log_warning`。バッチは続く |
| 人がラベルを直した直後 | 更新日が `run_date` 以降になり、不一致から外れる |
| 更新日が年をまたぐ | `last_research_update` は M/D で年が無い。既存の `_parse_research_update_md` (アクション行と同じ解釈) を使う |

## 5. 対象外とすること

- ステージの自動書き換え、ベース番号の自動判定
- チャート一覧からその場で LLM に読ませるボタン (まず週1回の自動で使ってみる)
- 準保有の自動読み取り、矛盾の検知 (Phase 2)
- 遷移の候補 (Phase 3)
- 履歴を画面に出すこと

## 6. テスト (5本以内)

1. `update_memo` の履歴: ステージ変更 → `change`、更新日だけ変更 → `confirm`、どちらも同じ → 追記なし (parametrize)
2. `STAGE:` 行の取り出し: 正常、選択肢に無い値、行なし (parametrize)
3. 不一致の判定: 重なる/重ならない、`1Sor3S`、ベース番号つき、人のラベルが空、人が後から見直した (parametrize)
4. 対象の選び方: 同じ週は読まない、新しい週は読む、週足不足は読まない (`claude` の起動は差し替える)
5. アクション行: 不一致があれば件数が出て、無ければ出ない

実行: `pytest tests/test_portfolio_shelve.py tests/test_webapp_routes.py tests/test_stage_llm.py -v`、最後に `pytest tests/ -v -m "not local_db and not live_html"`。

## 7. 検証

- 開発用コピーで `python stage_llm.py run <銘柄>` を実行し、`stage_llm:` に1件入ること、チャート一覧に出ることを確かめる
- 開発用コピーでチャート一覧からステージを変え、別の銘柄で「据え置き」を押し、`stage_history:` に `change` と `confirm` が入ること、不一致の表示が消えることを確かめる (書き込み系の検証は開発用コピーで行う)
- 運用機に反映した最初のバッチのログで、23件を読んだこと、所要時間、失敗件数を確かめる
