## 背景

楽天証券・SBI証券の保有残高CSVおよび約定履歴CSVは、既存のCSV取込処理で portfolio_shelve に反映できる。一方、証券会社サイトへのログイン後にCSVをダウンロードする操作は手動で残っている。

関連: #397（保有残高CSVの取込）、#383（売買履歴CSVの取込）、#321（開発ページ）

## 目的

ログイン済みの専用ブラウザプロファイルを用い、**WebApp のボタンから**楽天・SBIの国内株CSVをダウンロードし、既存の取込コマンドまで連携できる状態にする。

## スケジュール実行を採らない理由

当初はスケジュール実行（平日・引け後）を想定していたが、以下の理由で**手動実行に一本化**する。

1. **セッションの有効期間が短く、ログインが手動**。定時に走らせてもセッション切れで失敗する確率が高い
2. **失敗が沈黙する**。深夜に失敗すると気づくのは翌朝。#397 でCSVを真実源とした以上、「取込に失敗したのに気づかず古いデータで判断する」が最も避けたい事故
3. ボタン実行なら**押した本人がその場で結果を確認する**ため、この事故が構造的に起きない

CSVダウンロード処理は関数として切り出しておき、将来スケジュール実行に戻す場合は呼び出し元を足せば済む形にする（先回りした抽象化はしない）。

## スコープ

- 楽天証券・SBI証券の国内株
  - 現物・信用の保有残高CSV
  - 約定履歴CSV
- **WebApp（開発ページ）からの手動実行**
- ダウンロード完了・CSV形式・取込結果の検証
- 失敗時の画面表示とログ出力
- 成功時に既存の `import_portfolio_csv.py`、`import_rakuten_fills.py`、`import_sbi_fills.py` を呼び出す連携

## 非スコープ

- **スケジュール実行**（上記の理由により）
- ID・パスワード・ワンタイムパスワードの保存
- 二要素認証、CAPTCHA、端末認証などの回避・自動突破
- 注文、入出金、口座設定などCSV取得以外の操作

## 想定フロー

1. 専用ブラウザプロファイルでユーザーが初回ログインする。
2. WebApp の開発ページでボタンを押す。ログイン済みセッションを使いCSV画面へ遷移してダウンロードする。
3. ファイル名・更新日時・CSVヘッダを確認する。
4. 画面上に取込プレビュー（差分）を表示する。
5. ユーザーが確認して「取込」ボタンを押す → 既存CLIでDBへ取込む。
6. セッション切れや追加認証、画面変更で失敗した場合は、取込を行わず画面に理由を表示して停止する。ユーザーが手動ログイン後に再実行する。

## UI 設計

**#321 の開発ページ (`/dev`) に同居させる。**新規ページは作らない。

#321 が確立する非同期実行パターン（Popen fire-and-forget + status ポーリング + `threading.Lock` による多重起動防止 + pid 生存確認）をそのまま踏襲する。

ボタン構成:

| ボタン | 動作 |
|---|---|
| CSVダウンロード | 楽天・SBIのCSVを取得し、**全ファイルを検証**して結果を表示 |
| 取込プレビュー | 全CSVを `--dry-run` で通し、差分を表示（DBは変更しない） |
| 取込実行 | 検証通過済みの全CSVをDBへ反映 |

ダウンロードと取込を分けるのは、`import_portfolio_csv.py` が `--dry-run` / `--apply` / `--apply-records` の段階を持っており、**差分を見てから適用する運用が既にできる**ため。自動実行より安全側に倒す。

### 既存CLIとの段階の差異（実装方針）

3本のCLIは preview の粒度が揃っていない。

| CLI | 持っている段階 |
|---|---|
| `import_portfolio_csv.py` | `--dry-run` / `--apply` / `--apply-records` |
| `import_rakuten_fills.py` | `--dry-run` / 即書き込み |
| `import_sbi_fills.py` | `--dry-run` / 即書き込み |

fills 側に preview/apply の2段階を**新設しない**。理由:

- fills は `dedup_key` により冪等な**追記**であり、残高取込のような「qty上書き・自動OUT/IN」といった破壊的更新を伴わない
- `--dry-run` で件数（`rows` / `imported` / `skipped_dup` / `skipped_invalid`）は取れるため、
  プレビューとしては十分
- 既存CLIの改造は #429 のスコープ外（CLAUDE.md: 隣接コードの"改善"をしない）

→ **「取込プレビュー」は3本すべて `--dry-run` で実行し、fills は件数、残高は差分を表示する。**
   粒度が違うことを画面上でも明示する。

### 部分更新を避ける実行順序（重要）

3本のCLIは独立にDBへ書くため、素朴に順番に実行すると
「1本目は成功、2本目で失敗」で**DBが部分更新された状態**になりうる。
受入条件「不完全なダウンロードや未知のCSV形式では既存DBを変更しない」を満たすため、
以下の順序を必須とする。

1. **全CSVをダウンロードし、全ファイルの形式検証を先に完了させる**
   （ヘッダ・ソース判別・行パースまで。1つでも失敗したらここで停止し、DBには一切書かない）
2. 検証を全通過した場合のみ、取込を実行する
3. 取込は **fills → 残高** の順で行う
   - fills は冪等な追記なので、途中で失敗しても再実行で回復できる
   - 残高取込（qty上書き・自動OUT/IN）は破壊的なので**最後に単独で**実行する

shelve にトランザクションは無いため完全な原子性は保証できない。
**「書き始める前に全部検証する」ことで、失敗の大半を書き込み前に落とす**方針とする。
残高取込の実行中に落ちた場合は #365 の日次バックアップから復旧する。

## 依存

- **Playwright が未導入**（`requirements.txt` に無い）。本 issue で新規に追加する必要がある
- ブラウザプロファイルは専用のものを用意し、通常使用の Chrome と分離する

### プロファイル競合の扱い（設計上の制約）

Playwright の persistent profile は、**同じプロファイルディレクトリを別プロセスが掴んでいる間は起動できない**（ロックされる）。したがって競合は2種類に分けて考える必要がある。

| 競合 | 対処 |
|---|---|
| 通常使用の Chrome と専用プロファイル | **プロファイルディレクトリを分けることで解決する**。通常の Chrome を開いたままボタンを押しても問題ない |
| 専用プロファイル自身の二重起動<br>（手動ログイン用に開いたウィンドウが残っている） | **分離では解決しない**。実行前にロックを検出し、「専用ブラウザを閉じてから再実行してください」と画面に表示して停止する |

手動ログインは専用プロファイルで行うため、**ログイン直後にそのウィンドウを閉じ忘れた状態でボタンを押す**のが現実に最も起きやすい競合。これを「失敗しない」ようにするのではなく、**原因が分かる形で停止させる**方針とする（認証失敗時と同じ扱い）。
- 保存先は `$KS_DATA_DIR` 配下とし、リポジトリには置かない

## 受入条件

- 楽天・SBIそれぞれについて、ログイン済みならボタン操作で対象CSVを指定フォルダへ保存できる。
- 認証が追加で必要な場合、認証を試行・回避せず、理由を画面に表示して停止する。
- 不完全なダウンロードや未知のCSV形式では既存DBを変更しない
  （**全CSVの検証完了後に取込を開始する**ことで担保する。上記「部分更新を避ける実行順序」参照）。
- 同日再実行しても重複データが生じない
  （fills 取込は `dedup_key` により冪等。残高取込は position の上書き。既存実装で担保済み）。
- **通常使用の Chrome を開いたまま**ボタンを押しても、プロファイル分離により失敗しない。
- **専用プロファイルのウィンドウが開いたまま**ボタンを押した場合は、ロックを検出して
  「専用ブラウザを閉じてから再実行」と表示し、DBを変更せずに停止する。
- 手動実行手順をドキュメント化する。
