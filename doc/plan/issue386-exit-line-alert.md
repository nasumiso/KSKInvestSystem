## 背景 (issue #386 より)

半導体銘柄を保有し続けて急落を被った反省から、保有銘柄の出口を事前に明確化し、終値が防衛線を割れた事実を日次で見逃さないようにする。銘柄選定ではなく執行弱点の補強。portfolio の IN戦略 (memo.trade_idea) を「主たる出口ルールの宣言」として扱い、その戦略から価格ベースの防衛線を機械算出する。

対象は 1保 のみ。判定は日次バッチ後の最新確定終値 (場中値・逆指値は扱わない)。防衛線割れは全売却判断の最優先アラートとし、表示は既存の「シグナル」列に合成する (新規列は作らない)。

## 事前調査で判明した既存資産・制約

### 平均取得単価は既存ロジックを再利用する (素朴な再実装は破綻する)

`_episode_open_pl(rnd, current_price)` (`scripts/webapp/helpers.py:4466`) が未クローズ建玉ラウンドについて、fill を買い増し順に加重平均する `avg_cost` を既に計算している。

```
avg_cost = (avg_cost * held_qty + price * qty) / new_qty   # 買い増し時
```

この fills は `build_fill_episodes()` (helpers.py:4942) 内で issue #398 の分割・併合換算 (`_apply_split_adjustments`) 済みのものが渡されるため、**分割銘柄でも avg_cost は正しい基準で計算済み**。

**素朴な再実装は実データで破綻することを確認済み**: `list_fills()` の生 fill を順に加重平均する簡易実装を1保銘柄で試したところ、取込期間より前に買った現物を売った銘柄 (4377, 402A) で残高がマイナスになり、`avg_cost` が **-5,226 / 0.0** という無意味な値になった。`build_fill_episodes()` は同じ銘柄を正しく処理する (4377=未クローズ現物なし、402A=`first_seq=10` で `avg_cost=765.2`)。**必ず `build_fill_episodes()` の `open_pl.avg_cost` を使い、独自に再計算しない。**

### 【重要】対象は現物だけでなく信用買建も含める

**実データ確認: 1保 29銘柄のうち、未クローズ現物エピソードを持つのは 11銘柄のみ。残り 18銘柄 (62%) は信用建玉のみ。** 現物だけを対象にすると保有銘柄の6割で防衛線が機能せず、issue の目的 (保有全体の出口管理) を達成できない。

- 信用建玉にも `open_pl.avg_cost` (平均建単価) が正しく算出されている (実測: 3496=4,260円/100株, 3697=686.4円/1,100株 等)
- 保有中の信用建玉は**すべて買建** (`is_short=False`、売建0件)。売建は損切り方向が逆になるため、**本 issue のスコープ外**とし判定をスキップする (将来 `is_short=True` が現れたら安全側で判定しない)
- 同一銘柄で現物と信用を両建てする銘柄が4件あり (402A: 信用900株+現物600株、`record["qty"]`=1500 と一致)。issue は「1銘柄につき主戦略は一つ。保有全体に適用する」と明記しているため、**銘柄単位で現物・信用買建の未クローズエピソードを数量加重して1つの平均取得単価に統合する**:

```
avg_cost_total = Σ(avg_cost_i × held_qty_i) / Σ(held_qty_i)   # i = 未クローズかつ買建のエピソード
```

- `split_suspect=True` のエピソード (分割・併合の疑いで数値が信頼できない) が含まれる場合は、その銘柄の防衛線判定をスキップする (誤った avg_cost で誤警告を出さない)

### データ取得の拡張は不要 (violation 方式を採る場合)

**結論: 日足・週足とも、取得範囲もDB保存件数も一切変更しない。**

判断の根拠 (実データ検証済み):

| | DB保存 (`price_log`/`price_week_log`) | 生キャッシュ (取得時に手元にある) | 必要本数 |
|---|---|---|---|
| 日足 | 30本 (`LOG_DAY=30`) | **中央値63本** (`period="3mo"`) | 50MA = 50本 |
| 週足 | 25本 (`[:25]`) | **中央値105本** (`period="2y"`) | 40WMA = 40本 |

- DB保存分だけを見ると足りない (全2,460銘柄で30WMA/40WMA算出不能、50MAも不能)
- しかし **violation 方式では `price.py` の取得直後に生データ上で判定する**ため、DB保存件数は関係ない。既存の `ma10_break_confirmed` とまったく同じ流儀
- **保有中の1保29銘柄は全銘柄で日足50本・週足40本を満たす** (実測、不足0件)
- 全銘柄でも週足は3,442/3,523件が40本以上。日足で50本未満の1,145件は**分析対象外で更新が止まった古いキャッシュ** (最終更新が5〜6月) であり、現役銘柄の問題ではない
- 不足銘柄は `calc_ma_violation` が `None` を返して判定スキップ → 誤警告を出さない (安全側)

**もし表示層 (helpers.py) でMAを計算する旧設計を採るなら**、`LOG_DAY: 30→60` と `price_week_log: [:25]→[:45]` の拡張 + DB全周更新が必要だった。violation 方式はこれを丸ごと回避できる。

補足:

- 週足MA (30WMA/40WMA) の算出関数は既に `_calc_weekly_indicators` (price.py:868-869) にある (`ma30`, `ma40`)。日足50MAは無いため新規だが、`ma_at` の中身は `sum(closes[i:i+50])/50` の1行で済む。
- **Kabutanフォールバック経路の制約**: 日足は yfinance 優先だが失敗時に Kabutan HTML へフォールバックする。Kabutan 日足HTMLは1ページ固定取得で約30件しか返らない (price.py:711 のコメント「Kabutan HTML は元々 30 件返す」、実測20件)。**フォールバックした銘柄では日足50MAが算出できない**ため、`calc_ma_violation` が判定不能を返して「判定スキップ」になる設計にする (誤った短い窓での代替計算はしない)。
- 週足の未確定当週足は `_convert_weekly_df_to_kabutan_format` (price.py:1230) が取得段階で既に除外済み (1252-1255行)。**確定週のみが入る**ため、週足MA算出側で追加の除外判定は不要。

### 防/防歴の発動事実の永続化

`fill_memo:`/`split_adj:` と同じ命名パターンで新設する。

**キーは `episode_key` ではなく `code_s` 単位にする。** 防衛線は現物・信用買建を統合した「銘柄単位の1ポジション」に対して引く設計 (前述) なので、エピソード単位のキーでは信用のみ保有の銘柄 (1保の62%) でキーを組めず、現物+信用の混在銘柄でもどの state を読むか定義できない。

```python
KEY_EXIT_ALERT_PREFIX = "exit_alert:"  # exit_alert:{code_s} -> state

def get_exit_alert_state(code_s, cycle_id, *, db_path=None) -> dict:
    """防/防歴の状態を返す。保存された cycle_id が引数と一致しなければ
    別サイクルの残骸とみなし、空の state {"triggered": False, "events": []} を返す。"""

def record_exit_alert_event(code_s, cycle_id, event, *, db_path=None) -> dict:
    """防発動イベント (date, reasons) を1件追記する。

    保存済み state の cycle_id が引数と異なれば、**state ごと新しい cycle_id で作り直す**
    (追記ではなく置換)。dedup は (cycle_id, date) の組で行う — date だけで判定すると、
    旧サイクルの同日イベントが残っているときに新サイクルの発動を取りこぼす。"""

def reset_exit_alert_state(code_s, *, db_path=None) -> None:
    """全売却時に呼び、状態をクリアする (次の保有サイクルは真っさらから開始)。"""
```

`code_s` 単位にすることで `fill_episode_key` への依存が消え、`portfolio_shelve.py` が `build_fill_episodes()` (webapp層) を参照する必要もなくなる。レイヤーの一方向依存を保てる。

**状態リセットは2経路で行う (status だけに依存させない)**。本システムは status (手動更新) と fill/qty (CSV取込) が別レイヤーで動くため、片方だけを見ると取りこぼす。

**(a) status 経路**: `transition_status` (portfolio_shelve.py:1639) の 1保→2準 遷移時に `reset_exit_alert_state(code_s)` を呼ぶ。呼び出し口は route 層に複数ある (portfolio.py:446/532/814) ため、route ではなく `transition_status` 内部 (既存の「1保→2準 は action_type=売却」判定と同じ位置、portfolio_shelve.py:1691) に置いて全経路をカバーする。

**(b) 保有サイクル経路 (stale 防止)**: state に**発動時点のエピソード識別子を添えて保存**し、読み出し時に現在のエピソードと一致しなければ state を無視する (遅延リセット)。

```python
# state に持たせる: {"triggered": bool, "events": [...], "cycle_id": str}
# cycle_id = 現在の未クローズエピソード群から決まる識別子
#            (例: min(first_seq) と kind の組を連結したもの)
```

これにより「fill 上は全売却済みだが status を落としていない」「2準 を経由せず同じ銘柄を買い直した」場合でも、`cycle_id` が変わるため旧サイクルの防歴が新ポジションへ漏れない。判定は表示層 (`build_fill_episodes()` の結果を持っている場所) で行い、`portfolio_shelve.py` 側は `cycle_id` を単に保存・比較するだけに留める (レイヤーの一方向依存を維持)。

(a) だけでも通常運用はカバーできるが、(b) を入れることで「issue の全売却リセット要件」を fill という事実ベースでも担保できる。

保存する最小限のデータ: 発動日・発動理由 (MA/損切り)・発動時終値・MA値。「防歴」のtooltipに必要な情報のみ (売却後分析やユーザー行動ログではない、と issue 本文が明記)。

## 計算モジュール: 新規の純粋関数群

新規ファイル `scripts/exit_line.py` に価格系列・fill から防衛線状態を計算する純粋関数を置く (webapp/helpers.py に直接書くと肥大化するため分離、CLAUDE.mdのシンプルさ原則に沿い依存は最小限)。

```python
def calc_sma_at(closes: List[float], window: int, offset: int = 0) -> Optional[float]:
    """closes (新しい順) の offset 本目を最新とみなした時点の単純移動平均。
    offset=0 が当日基準、offset=1 が前日基準。データ不足 (offset+window 本未満) なら None。
    防衛線判定は『あるだけ平均』で代替すると誤警告になるため、不足時は厳格に None を返す。
    """

def calc_ma_violation(
    closes: List[float],  # **日足**終値、新しい日が先頭
    lows: List[float],    # **日足**安値、新しい日が先頭。前日安値方式の確定判定に必須
    ma_at,                # Callable[[int], Optional[float]]: index i の営業日が
                          # 「その時点で参照すべき」MA 値。算出不能なら None。
                          #   日足MA: sum(closes[i:i+w])/w
                          #   週足MA: i 日が属する週の1つ前の確定週を末尾とする WMA
                          #           (同一週内の日は同値だが、週をまたぐと変わる)
) -> dict:
    """既存の「早売」(calc_ma10_kairi_indicators) と同じ violation / porosity ルールで
    MA割れ状態を判定する。MA の求め方を ma_at に外出しした汎用版。

    **判定系列は日足に固定する。** 週足MAでも週足 closes/lows で判定してはいけない
    (確定が最大1週間以上遅れ、日次アラートとして機能しなくなる)。

    Returns: {
      "breached": bool,       # 現在 MA を割っている (porosity 救済後も維持できていない)
      "confirmed": bool,      # A日安値を下抜いて violation 確定 → 「防」
      "pending": bool,        # 割れたが未確定 (翌日未到来 or A日安値未割れ) → 「防予」
      "a_day_low": float|None,
      "ma_value": float|None,
    }
    データ不足・lows 欠損時は全て False / None (誤警告を出さない)。
    """

def calc_stop_loss_line(
    exit_rule: dict,
    fills: List[dict],  # **1エピソード分**の全 fill (買い・売り両方) を時系列昇順で
) -> Optional[float]:
    """1エピソードの損切り線を返す。全 fill を時系列に再生し、買い時点ごとの avg_cost からラチェット計算する。

    **売り fill も必ず渡すこと。** 売却で保有数量が変わると、その後の買い増しで算出される
    avg_cost が変わるため、買い fill だけを並べると再現できない (実データで最大1,849円の差)。

    **複数エピソード (現物+信用) をまたぐ銘柄では、fill をマージせずエピソードごとに呼び、
    結果を held_qty で加重平均する** (マージすると実データで最大1,523円ずれる)。

    allow_dca_lower=True (中長期ファンダ) : 最後の avg_cost × (1 - pct)。買い増しで下がってよい。
    allow_dca_lower=False (その他)        : max(各買い時点の avg_cost × (1 - pct))。下げない。
    stop_loss_pct が None (夢枠・大型高配当) なら None。
    """

def calc_exit_line(
    exit_rule: dict,
    fills: List[dict],            # 全 fill (買い・売り両方) 時系列昇順
    price_log: List[tuple],       # (date, close) 降順
    price_week_log: List[tuple],  # (date, close) 降順、確定週のみ
) -> Optional[dict]:
    """現在の防衛線水準を返す。
    Returns: {"ma_value": float|None, "stop_loss_value": float|None} / exit_rule が
    全て None (夢枠等) なら None。
    """

def evaluate_exit_signal(
    exit_rule: dict,
    fills: List[dict],  # 損切り線のラチェット計算に使う (現在の avg_cost だけでは不足)
    price_log: List[tuple],
    price_week_log: List[tuple],
    prev_state: dict,  # get_exit_alert_state の戻り値 (「防歴」判定に使う)
) -> dict:
    """当日時点のシグナル状態を判定する。
    Returns: {"level": "防予"|"防"|"防歴"|None, "reasons": [str, ...], "ma_value": ..., "stop_loss_value": ...}
    """
```

### 【重要】損切り線は履歴依存 (ラチェット)。現在の avg_cost だけでは出せない

issue 本文の「その他の損切り対象戦略」は次の式を指定している:

```
新しい損切り線 = max(既存の損切り線, 買い増し後の平均取得単価 × (1 - 損切り率))
```

つまり損切り線は**過去の買い増し時点の値を引き継ぐラチェット**であり、「現在の avg_cost × (1 - pct)」では再現できない。**実データで差を確認済み**: 285A (買い15回) はラチェット線 61,890円に対し単純計算 56,043円で **5,847円の差**、6227 は 7,533円 vs 6,264円 で 1,269円の差。単純計算では損切り線が低すぎて、割れを見逃す。

ただしこのラチェットは**fill 履歴から決定論的に再計算できる**ため、損切り線そのものを永続化する必要はない (状態の二重管理を避けられる)。`build_fill_episodes()` が返すエピソードの `fills` を**買い・売り両方とも**時系列に走査し、買い fill のたびに更新される avg_cost から候補線を出してラチェットを取る。

**売り fill を落としてはならない**: 加重平均法では売却時に avg_cost 自体は変わらないが、**保有数量が減る**ため、その後の買い増しで計算される avg_cost が変わる。実データで検証したところ、買い fill だけを並べた場合と全 fill を再生した場合で損切り線に差が出た:

| 銘柄 | 全fill再生 | 買いのみ | 差 |
|---|---:|---:|---:|
| 285A (現物) | 61,890 | 60,041 | **1,849** |
| 4258 (信用) | 3,632 | 3,111 | **521** |
| 4413 (信用) | 2,187 | 1,993 | **194** |
| 6227 (信用) | 6,548 | 6,548 | 0 |

買いのみでは線が低すぎて割れを見逃す。「売り→買い増し」の順序が混在するエピソードは実在する (285A, 4413, 4258 等)。

- 一部売却それ自体では avg_cost が変わらない (加重平均法) ため線も動かない = issue の「一部売却で損切り線を下げない」と一致する
- 全売却でエピソードがクローズし、次の新規INは新しいエピソード (別 `first_seq`) になるため、線は自然にリセットされる = issue の「全売却で状態をリセット」と一致する
- 中長期ファンダ (`allow_dca_lower=True`) は最新の avg_cost をそのまま使う。ただし issue は「買い増しは 防 発動前までに限る」と条件を付けているが、これは**運用ルールであってシステムが強制する対象ではない** (非スコープの「防発動後に保有を続ける際の理由入力・必須化」に準じる)。システムは事実として現在の avg_cost から線を引き直すだけとする

### 【重要】MA割れ判定は既存の「早売」ルール (violation 方式) に統一する

issue 本文は「終値で2営業日連続割れ」と書いているが、**本システムには既に確立した MA 割れ判定が実装されており、そちらに統一すべき** (ユーザー要望)。既存ルールは単純な2日連続割れより騙し (shakeout) に強い。

**既存実装** — `calc_ma10_kairi_indicators` (`scripts/price.py:460-585`)、Morales/Kacher の violation / porosity 準拠:

1. **維持判定 (`_streak_holds`, porosity 救済)**
   - 終値 > MA なら維持
   - 終値が MA を割っても、**翌営業日の終値が (その日の) MA 上に回復すれば維持**。一時的な潜りは shakeout として救済する
   - 翌営業日も MA 以下なら violation 成立 → 切断
   - 最新日の割れは翌営業日が未到来のため **violation 未確定**として維持側に倒さない (先取り誤判定の防止)

2. **確定判定 (`ma10_break_confirmed`, 前日安値方式)**
   - **A日** = 最初に MA を割った日 (前日は MA 上、当日は MA 以下) を新しい順に走査して特定
   - **A日より後の日で、安値が A日の安値を下回ったら確定** (`lows[j] < a_day_low`)
   - MA を回復したらリセット。`lows` が無ければ判定不可 (False)

**防衛線への適用**: 「防」の MA 条件は、この violation + 前日安値方式を MA 窓だけ差し替えて再利用する (10MA → 戦略ごとの 50MA / 30WMA / 40WMA)。`price.py` の既存関数はロジックが `closes`/`lows` に対して閉じているため、**窓を引数化した汎用版を `exit_line.py` に切り出すか、`calc_ma10_kairi_indicators` を窓引数対応にする**。既存の10MA呼び出し側の挙動は変えない (デフォルト引数で現状維持)。

これにより:
- 「防予」= violation 判定中 (割れたが翌日未到来 or A日安値未割れ) の状態に対応させられる
- 「防」= violation 確定 (A日安値を下抜いた) に対応
- 既存の「早売」タグ (10MA) と「防」(50MA/週足MA) が**同じ考え方の別窓**として一貫し、ユーザーの判断基準がぶれない

### 【重要】violation 方式にすると計算層が price.py 側に移る

**日足の安値系列は DB に保存されていない。** `lows` は取得時の `daily_price_list` (生データ) からのみ得られ、DB には判定結果の bool (`ma10_break_confirmed`, `ma10_streak_ever` 等) だけが保存される。`price_log` は `(date, close)` のみで安値を持たない (実DB確認済み)。

したがって、防衛線の MA 判定を violation 方式にする場合、**表示層 (helpers.py) では計算できない**。設計を次のように変える:

- **MA violation の判定は `price.py` の `_calc_daily_indicators` 内で行い、結果を stocks_shelve に保存する** (既存の `ma10_break_confirmed` と同じ置き場所・同じ流儀)
- 保存するフィールド例: `ma50_violation` = `{"breached": bool, "confirmed": bool, "pending": bool, "ma_value": float, "a_day_low": float}`。週足版は `wma30_violation` / `wma40_violation`

**【重要】週足MAの violation も「日足の終値・安値」で判定する。** 週足 closes/lows に対して既存ロジックをそのまま適用すると、確定条件が「翌**週**の週足安値がA週の安値を下回る」になり、**最大1週間以上遅れて**しか「防」が出ない。これは日次アラートという目的を損なう。正しくは:

- **MA値**: `weekly_price_list` (確定週のみ) から 30WMA / 40WMA を算出する。**ただし「全日同じ値」にしてはいけない** — violation 判定はA日特定・porosity 救済のため過去数営業日を遡るので、**前週にまたがる日には『その日の時点で参照すべき確定週WMA』**(= その日が属する週の1つ前の週を末尾とするWMA) を使う。同一週内の日は同値だが、週をまたぐと値が変わる
- **割れ判定の系列**: 日足の `closes` / `lows` を使う。「日足終値がその日時点の確定週WMAを割った日」がA日、「その後の日足安値がA日安値を下回ったら確定」
- porosity 救済も日足ベース (割れ翌**営業日**の終値がその日のWMA上に回復すれば維持)

つまり `calc_ma_violation` は `closes`/`lows` (常に日足) と `ma_at` (その日に参照すべきMA値を返す関数) を分離して受け取る形にする:

```python
def calc_ma_violation(
    closes: List[float],           # 日足終値、新しい日が先頭
    lows: List[float],             # 日足安値、新しい日が先頭
    ma_at,                         # Callable[[int], Optional[float]]
                                   #   日足MA: lambda i: sum(closes[i:i+w])/w
                                   #   週足MA: lambda i: 確定週WMA (i に依らず固定)
) -> dict:
```

これにより日足50MAと週足30/40WMAが同じ violation ロジックを共有しつつ、週足でも日次の解像度でアラートが出る。`_calc_weekly_indicators` 側では WMA値の算出のみ行い、violation 判定は日足側に集約する。
- **表示層は保存済みの判定結果を読むだけ**にする。これにより helpers.py 側は「損切り線 (fill 由来) + MA violation (stocks_shelve 由来) を合成して防/防予/防歴を出す」だけの薄い層で済む

副次的な利点として、**`LOG_DAY` / `price_week_log` の保存件数を拡張する必要がなくなる** — MA計算が取得時の生データ (`daily_price_list` ≒60営業日、`weekly_price_list` ≒105週) 上で完結し、DBには判定結果だけを保存するため。前述の「データ拡張が前提条件」という制約は violation 方式で解消する (Phase 1 の日足50MA、Phase 2 の週足30/40WMA とも)。

戦略ごとに窓が違う (50MA / 30WMA / 40WMA) ため、**3種類すべてを毎回計算して保存する**か保有銘柄のみに絞るかは実装時に決める (全銘柄3種でも計算コストは小さいので、まず素直に全部保存する案を推す)。

この変更により、実装の主戦場は「helpers.py の表示合成」から「price.py の指標計算 + stocks_shelve への保存」へ移る。テストも `tests/test_price.py` が主戦場になる。

**参考: 既存の「売」「警」タグは別系統** (`make_stock_db.py:1360-1378`) — 50MA ではなく `price_kairi_wma10` (**週足**10MA乖離) < 0 と売り圧力レシオ < 45 の2条件で、RS が高い (rs_raw >= 1.2) 銘柄だけに出る。防衛線とは目的が異なるため統合しない。

### MA基準日を取り違えない (violation 方式なら既存実装が正しく処理済み)

MAは日々動くため、過去日の割れ判定には**その日時点のMA**を使う必要がある。当日基準のMAで前日を判定すると誤る — 実データ (stocks_shelve 2,415銘柄、25日MAで検証) で **44銘柄 (1.8%) が逆転**した。

既存の `calc_ma10_kairi_indicators` は `_ma10(i)` として日ごとにMAを算出しており、この点は既に正しい。**窓を引数化して流用する限りこの罠は自動的に回避される**が、独自にMA比較を書く場合 (損切り線側など) は注意すること。

### 週足MAと日足の時間軸のズレ

週足MAは「先週までの確定値」で、日足最新との間に**中央値7日のラグ**がある (実データ確認済み: 週足は月曜ラベルかつ未確定当週を除外するため)。

violation 判定を日足解像度で行う設計 (前述) では、この非対称性は次のように扱う:

- **MA値**: `weekly_price_list` から確定週の 30WMA/40WMA を算出。`ma_at(i)` は **i 日が属する週の1つ前の確定週を末尾とする WMA** を返す (同一週内は同値、週をまたぐと変わる)
- **判定系列**: 日足の終値・安値。A日特定・porosity 救済・A日安値割れ確定はすべて営業日単位

日足MAは日ごとに動き、週足MAは週ごとに階段状に動く — この差 (とくに**週境界をまたぐ判定**) をテストで固定すること。

## 表示層: helpers.py

`avg_cost` は分割・併合換算済みでなければならないため、軽量再実装はしない。`build_fill_episodes()` (helpers.py:4942) を1保銘柄に限定して呼び、`open_pl.avg_cost` をそのまま使う。全銘柄分のフル実行は重いが、`build_fill_episodes()` は `code_s` によるフィルタを持たないため、以下いずれかで対応する:

- (a) `build_fill_episodes()` に `code_s` 引数を追加し、`by_code` を1銘柄分に絞ってから既存ロジックに通す (fill取得・分割イベント取得は該当銘柄分のみで済み、N銘柄ループでもN+1にならない)
- (b) portfolio 一覧表示の前に1回だけ `build_fill_episodes()` を全銘柄分実行し、`code_s -> avg_cost` の map を作って1保行の合成時に引く (`list_portfolio_with_indicators` は元々 `stock_map`/`name_map` を一括構築するパターンを踏襲しており、こちらの方が既存コードの流儀に合う)

(b) を採用する。`list_portfolio_with_indicators` の冒頭 (helpers.py:2009付近、`stock_map`/`name_map` 構築と同じ位置) で `build_fill_episodes()` を1回呼び、`code_s` ごとに以下を集約した map を作る:

- **未クローズかつ買建** (現物、および `is_short=False` の信用) のエピソードを対象にする
- 複数エピソードがある銘柄は `avg_cost` を `held_qty` で加重平均して統合する (上記「対象は現物だけでなく信用買建も含める」参照)
- 損切り線は**エピソードごとに `calc_stop_loss_line` を計算し、`held_qty` で加重平均して銘柄の線にする**。エピソードの fill をマージして1本の時系列にしてはいけない (下記参照)
- `split_suspect=True` を含む銘柄は map に入れない (判定スキップ)

**エピソードの fill をマージしてはいけない理由**: 売り/返済は「どのエピソードの建玉を減らしたか」に依存するが、マージするとその所属情報が失われ、avg_cost 推移を一意に再現できない。実データで両方式を比較すると差が出た:

| 銘柄 | マージ | エピソード別加重 | 差 | 内訳 (線, 株数) |
|---|---:|---:|---:|---|
| 4970 | 9,970 | 8,448 | **1,523** | 信用 11,027×100 / 現物 5,868×100 |
| 6268 | 3,774 | 3,429 | 345 | 4,059×100 / 2,799×100 |
| 402A | 690 | 672 | 18 | 660×900 / 690×600 |

4970 は現物と信用で建値が倍近く違うため、マージすると実在しない中間値になる。**エピソード別に計算してから加重平均する。**

表示合成のステップ:

1. 上記 map から `avg_cost` (エピソード別を数量加重統合) と、エピソードごとの損切り線を引く (無ければ防衛線判定をスキップ)
2. `evaluate_exit_signal(...)` を呼ぶ
3. `level` に応じて `row["signal_mark"]`/`row["signal_full"]`/`row["signal_display"]["style"]` を合成:
   - `"防"`: 既存シグナル (ポ/ブ/週ブ) より前に "防" を連結し、style は最優先の赤枠 (太字・太枠、既存の `bg_with_white("赤")` とは別トーンにするか要検討)
   - `"防予"`: 黄色、"防" より弱いトーン
   - `"防歴"`: 薄橙/グレー、全売却まで残す
4. `"出口未宣言"` (未分類または旧自由記述の1保) は別途警告表示 (issue 受入条件の一部)

### 防/防歴イベントの書き込み経路

webapp の表示読み込み (`GET /portfolio`) 内で判定と同時に `record_exit_alert_event` を書き込む。理由:

- 日次バッチ (`make_stock_db.py list_all_db`) は stocks_shelve 側の指標更新が責務で、portfolio_shelve の1保銘柄・戦略・fillsを横断参照する経路を持たない。バッチ側に新設するとportfolio_shelveへの依存を逆方向に増やし、モジュール分離の設計 (portfolio_shelve が他DBを参照する一方向) に反する。
- 「防」判定はその日の最新確定終値のみに依存する冪等な計算 (同じ入力なら同じ `level` を返す) なので、1日に何度webapp表示を叩いても実質的な重複書き込みにしかならない。`record_exit_alert_event` の dedup は **`(cycle_id, date)` の組**で行う (前述)。`date` だけで判定すると、同日中に全売却→再IN した場合に新サイクルの発動を取りこぼす。
- 実装は `cycle_id` を算出 → `get_exit_alert_state(code_s, cycle_id)` → `evaluate_exit_signal(..., prev_state=state)` → `level` が新規に "防" になった当日分だけ `record_exit_alert_event(code_s, cycle_id, event)` で追記、という flow。cycle 不一致時は state ごと置換される。

**提案**: issue の表をハードコードせず、`exit_rule` は戦略マスターの編集画面から設定する運用にする。シードは現存10戦略に対して与え、「中期底値リバ」には中期系の値 (日足50MA / -10%) を割り当てる。これにより issue の表と実DBの差分を実装時に吸収する必要がなくなる。

### 2. 説明文には既にユーザー自身の出口ルールが書かれている → それを構造化の出発点にする

現在の description には出口ルールが自然言語で入っている:

- 中期テーマ: 「物色が他テーマへ移ったら売る**(50MA割れ、10MA割れ早売り)**」
- 中期モメンタム: 「トレンドが崩れたら**(50MA割れ、10MA割れ早売り)**売る」
- 中長期ファンダ: 「**上昇トレンド(ステージ２コア)毀損**、ファンダ前提崩れで売る」
- 短期底値リバ: 「**10,20等MAタッチ/10%で機械的利確**。サイズ小・損切り事前設定」

issue の表 (中長期ファンダ=40WMA) は、**ユーザー自身が書いた「ステージ2コア毀損」とは別物**。ステージ2コアの判定は `trend_template` として既に実装済み (`_STAGE2_CORE_MISSES`, helpers.py:3996)。

**決定 (ユーザー判断済み)**: **40WMA を採用する**。ステージ2コア毀損を流用する案も検討したが、全戦略を「MA + violation ルール」という単一の枠組みに揃えるシンプルさを優先する。ステージ2コア毀損は `trend_template` 列で引き続き別途表示されるため、情報としては失われない。

### 3. 「10MA割れ早売り」は既に実装済み → 二重実装しない

description が2戦略で言及している「早売り」は、**既に `早売` タグとして実装されている** (`make_stock_db.py:1379`「30日10ma維持実績ありで10ma割れ後、翌日以降にA日安値を安値で下回った」)。portfolio 一覧のタグ列にも表示され、tooltip も用意されている (`_format_tags_tooltip`, helpers.py:2183)。

**提案 (ユーザー合意済み)**: issue の「終値で2営業日連続割れ」を捨て、**既存「早売」の violation / porosity + 前日安値ルールを窓だけ変えて流用する** (詳細は前述「MA割れ判定は既存の『早売』ルールに統一する」)。これにより:

- 判定思想が10MA (早売) と 50MA/週足MA (防) で一貫し、ユーザーの判断基準がぶれない
- 単純な2日連続割れより shakeout に強い (porosity 救済)
- 実装も既存関数の一般化で済み、新規のMA判定ロジックを書き起こさない

タグ列の「早売」(10MA) とシグナル列の「防」(50MA/週足MA) は**同じルールの別窓**として共存させ、tooltip で窓を明示する。

### 4. 「1保の62%が信用建玉」→ 現物限定の設計は目的を達成できない

(前述「対象は現物だけでなく信用買建も含める」参照。29銘柄中18銘柄が信用のみ。)
issue 本文は現物/信用の区別に一切言及していないが、これを見落とすと**保有の6割が無防備なまま**になり、issue の動機 (半導体銘柄を持ち続けた反省) に対して機能しない。

### 5. 損切り線のラチェットは fill から再計算できる → 永続化を減らせる

(前述「損切り線は履歴依存」参照。) issue は「防が発動した事実」の保存を求めているが、**損切り線そのものは保存不要**。保存するのは「防が発動した事実 (日付・理由)」だけでよく、issue の「最小限保存する」という意図とも合致する。

### 6. 「防予」の実効性を再考する

「防予」は MA を初めて割った日だけ出る1日限りの表示。しかし本システムは**日次バッチ後に画面を見る運用**であり、防予の日に画面を見なければ気付かないまま翌日「防」になる。防予単独の価値は「明日 防 になるかもしれない」という予告のみ。

**提案**: 防予は実装するが優先度を下げ、**Phase 1 では「防」と「防歴」だけを実装する**案を検討したい。理由は (a) 防予は1日で消えるため見逃しやすく、(b) 状態遷移のテスト・実装コストが「防」の2倍近くになり、(c) 実害 (割れたのに気付かない) を防ぐ主目的は「防」だけで達成できるため。

### 7. 段階実装 (ユーザー承認済み)

**この段階実装を採用する。** Phase 1 を先に完成させ、動作を確認してから Phase 2 へ進む:

- **Phase 1 (実害を止める)**: 損切り線 (ラチェット) + 日足50MA の violation (既存「早売」ルールの窓違い) → 「防」「防歴」。現物+信用買建を統合。対象は既存10戦略のうち MA/損切り率が定義できるもの。
- **Phase 2 (精度を上げる)**: 週足MA (**30WMA / 40WMA で確定**。ステージ2コア毀損案は不採用)、「防予」。
- **Phase 3 (運用を楽にする)**: 戦略マスター編集画面での exit_rule 編集UI。

Phase 1 だけで「保有中の銘柄が損切り線・50MAを割ったのに気付かない」という主要リスクは解消できる。violation 方式なら `price.py` 側で計算が完結するため、`LOG_DAY` / `price_week_log` の拡張もDB全周更新の待ちも不要 (指標が増えるので通常のDB更新1周で反映される)。

## 決定事項 (ユーザー合意済み)

- **MA判定は既存「早売」の violation / porosity + 前日安値ルールに統一** (issue の「2営業日連続割れ」は不採用)
- **中長期ファンダの MA 防衛線は 40WMA** (ステージ2コア毀損は不採用、シンプルさ優先)
- **段階実装を採用** (Phase 1 = 損切り線 + 日足50MA → 防/防歴)
- **データ取得・保存の拡張は不要** (violation 方式により生データ上で計算が完結)
- **対象は現物 + 信用買建を統合した銘柄単位のポジション** (売建はスコープ外)

### 追記 (2026-09-03): 損切りラインはエピソード単位に戻した

PR #428 で `_current_hold_cycle()` を導入した際、`cycle_id` (防歴の同一性判定) だけでなく
**損切りラインの入力までサイクル全 fill に差し替わっていた**。本ファイル §「損切り線は履歴依存」

実害: 3496 (アズーム) で、2025年に決済済みの高値建玉 (@8,470) の線 6,056円が
`allow_dca_lower=False` のラチェットで残り続け、**証券会社の損益 +12% の建玉に「防」が出ていた**。

- `_build_exit_position_map()` の返り値から `"fills"` キーを削除 (消費者はこの1箇所だけだった)
