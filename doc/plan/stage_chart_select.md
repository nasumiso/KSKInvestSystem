# 実装プラン: portfolio ステージ列・チャートパターン列のリスト選択式化

## 背景

portfolio (保有銘柄一覧) ページのメモページ (data-page="2") の列のうち、
「売買戦略」列は issue #327 で **定型リストからの単一選択式** (`<select>`) になった。
一方、**ステージ列・チャートパターン列は今も自由記述** (text/textarea inline 編集) で、
表記揺れが多く、集計・着色・将来の自動判定の入力に使いづらい。

売買戦略と同じ「選択式」の体験に揃えたい (CLAUDE.md: ページ/機能間で仕様を揃える)。

### 参照実装 (売買戦略, issue #327)

- 候補定義: `portfolio_shelve.py:123-132` `TRADE_IDEA_OPTIONS` (8値の定数 tuple)
- UI: `portfolio_list.html:463-480` `<select class="trade-idea-select">`。空=未分類、
  リスト外既存値は `⚠️` 付きで救済表示
- 保存: `portfolio.py` `update_memo` → `trade_idea` フィールド。
  バリデーション: 空 or リスト内 or 既存値 (旧自由記述の救済)。新規のリスト外値は ValueError
- inline JS: `portfolio_list.html:1033-1070` change で即 POST、失敗時ロールバック

## 現状の保存形式と実データ (DB 318件から集計)

### ステージ (`memo.stage`, 入力 175件)

`2S(3T)` のように **S (ステージ) と T (ベース)** が1つの文字列に同居。実値の構造:

- **S 本体**: `1S` `2S` `3S` `4S` (色付けは helpers.py:3606-3622 で 2S=濃黄/3S=水色/4S=青)
- **T (括弧内)**: `(1T)`〜`(5T)`。例 `2S(3T)`
- **推移**: `~` 区切り。例 `2S~3S` `3S~4S` `4S~1S`
- **不確定**: `or` (`1Sor3S`)、`?` (`2S(1T)?`)
- 表記揺れ: `4~1S` (S抜け)、`2S(4T)~3S始？` など自由記述ゆえのノイズ

主な実値: 4S(32) 1S(28) 2S(19) 2S(3T)(13) 3S(12) 2S~3S(11) 2S(2T)(10) ...

### チャートパターン (`memo.jukyu_chart`, 入力 50件)

複数行可の自由記述。実値の構造:

- **場**: `月足` `週足` `週足月足` (複合)
- **パターン**: `CWH` `VCP` `低位`(月足低位) `高値`
- **状態**: `形成` `ブレイク` `ブレイク済み` `ブレイク失敗` `再ブレイク`

主な実値: 月足低位(18) 月足VCP(4) CWH形成(4) CWHブレイク(3) 月足低位ブレイク済み(2) ...

## ゴール

1. ステージ列の **S 部分** をリスト選択式にする (単一 + 推移)
2. ステージの **T 部分** は、別フィールドを新設せず `stage` 文字列内に統合表示したまま、
   **入力だけ分離**できるようにする (S 選択 + T 入力 → `2S(3T)` 形に合成保存)
3. チャートパターン列を、**パターン軸と状態軸を別 select** で選び、合成保存する
4. 既存の自由記述値は破壊せず救済表示する (売買戦略と同じ方針)
5. ステージ色付け (helpers.py:3606-3622) は現状ロジックのまま動く (合成結果が `\d+S` を含む)
6. **一覧ページとチャート画面で仕様を揃える** (codex 指摘1 / 必須): 同じ stage/jukyu_chart は
   チャート画面 `portfolio_charts.html` にも独自 inline 編集がある
   (`edit-stage`/`edit-jukyu`, portfolio_charts.html:116-327。stage 変更時の
   last_research_update 自動補完も保持)。一覧だけ選択式にすると二重仕様になり、
   保存契約変更でチャート画面が壊れる。**両画面を同時に選択式へ移行**する
   (CLAUDE.md: ページ/機能間で仕様を揃える)

## 確定した設計方針 (ユーザー合意済み)

- **S 候補**: 単一 (1S/2S/3S/4S) + 隣接推移 (1S~2S/2S~3S/3S~4S/4S~1S)
- **S/T の扱い**: T 専用フィールドは新設しない (大げさ)。`stage` フィールドは現状のまま 1 本。
  **UI で S 選択と T 入力を分け、保存時に `{S}({T}T)` 形へ合成して `stage` に格納**。
  T 空なら括弧なし (`2S`)。→ 表示は統合 (`2S(3T)`)、入力は分離、スキーマ変更なし
- **チャートパターン**: **場軸 + パターン軸 + 状態軸** の3 select で選択 → 合成して
  `jukyu_chart` に保存 (例: 月足 + CWH + ブレイク → `月足CWHブレイク`)
- **推移選択時の T**: S で推移 (`2S~3S` 等) を選んだ場合、T は**推移の左側 S に付ける**。
  例: `2S~3S` + T=3 → `2S(3T)~3S`

## 設計詳細

### A. ステージ列 (S 選択 + T 入力 → stage に合成)

1. **候補定数の新設** (`portfolio_shelve.py`):
   - `STAGE_OPTIONS = ("1S","2S","3S","4S","1S~2S","2S~3S","3S~4S","4S~1S")`
2. **UI** (`portfolio_list.html` data-page="2" **および** `portfolio_charts.html`):
   - S: `<select class="stage-select">` (STAGE_OPTIONS、空=未設定、リスト外既存値は ⚠️ 救済)
   - T: 小さな `<input>` または select (1T〜5T、空可)。S と同じセル内に並べる
   - 既存の「ステージ編集で last_research_update を当日に自動更新」(data-touch-update) は維持
   - Ctrl+クリックで株探チャート、の挙動も維持 (一覧側)
   - 両画面で同じ select コンポーネント/POST 契約を使う (重複実装を避ける)
3. **合成ロジック**: S 選択 + T 入力 → `stage` 文字列を組み立てる
   - 合成は **サーバ側** (`portfolio.py` の form 抽出層) で行い、UI は S/T を別々に POST する
     (クライアント合成だと表記ゆれ防止が効きにくいため)
   - T 空 → `2S`、T あり → `2S(3T)`、推移+T → `2S(3T)~3S` (T は推移の左側 S に付与)
   - **既存の推移/不確定/ノイズ値の救済**: パース不能な既存値はそのまま保持し、
     select では ⚠️ 付き option として選択状態にする (売買戦略と同方針)
   - **新規 POST キーの受け口** (codex 指摘2 / 必須): 現状 `_extract_memo_fields_from_form`
     (`portfolio.py:357`) は `for field in ps.MEMO_FIELDS` で回り、**MEMO_FIELDS 外のキーを
     黙って無視**する。`stage_s`/`stage_t`/`chart_place` 等の新規分割キーはこのままでは
     `update_memo` に届かない。→ この関数に新規キーを受けて `stage`/`jukyu_chart` へ
     **畳み込む専用処理を追加**する。先例として `gyoutai_themes_0/_1` のスロット展開
     (issue #187) が同関数内にあり、同じパターンで実装できる
   - **畳み込みの送信契約** (codex 指摘3 / 必須): 現行保存 API は部分更新セマンティクス
     (`request.form` に来たキーだけ更新)。1軸だけ change して送ると、サーバは他軸の現在値を
     知らず完全な文字列を再構築できず、**他軸を消す事故**が起きる。
     → **クライアントは、ある軸を change したら同セルの全サブ値 (S+T / 場+パターン+状態) を
     まとめて POST する**契約とする。サーバは届いた全サブ値だけで合成する (現行 DB 値の
     読み戻しマージはしない = 単純・冪等)。`gyoutai_themes` の全スロット送信と同方針。
     - サブ値が1つも来ない場合は当該フィールド据え置き (部分更新セマンティクス維持)
     - 全サブ値が空文字で来た場合は当該フィールドを `""` (クリア意図) とする
4. **既存値の S/T 分解 (表示時)**: `stage` から S 部分と `(nT)` 部分を正規表現で分離して
   2つの UI 要素の初期値にする。分解不能なら S 側に丸ごと入れて ⚠️ 救済
5. **救済値セルの保全** (codex 指摘 / 必須): `2S(4T)~3S始？` 等の分解不能な救済値が入った
   セルでは、「サブ値のみで再合成」契約と「壊さない」目標が衝突する (元文字列を捨てて
   合成し直すとノイズ情報を失う / 合成不能で失敗する)。→ 以下で両立させる:
   - 救済値セルは S select を ⚠️ option 選択状態で表示し、**T 入力等の補助軸は disabled**
     (構造化編集を一旦ロック)
   - ユーザーが ⚠️ 以外の **正規候補を選び直して初めて** 構造化保存モードに切替わり、
     以降は通常の「全サブ値まとめて POST → 合成」になる
   - それまでは元の自由記述文字列を温存 (= POST しない / 変更なし)
   - チャートパターン側も同様: 救済値セルは場/パターン/状態の補助軸を disabled にし、
     いずれかを正規候補に選び直した時点で構造化保存に切替える
6. **色付け非回帰**: helpers.py:3606-3622 は `stage` 文字列に `2S/3S/4S` が含まれるかで判定。
   合成結果は従来と同形式なので**変更不要** (検証ポイントで担保)

### B. チャートパターン列 (パターン軸 + 状態軸 → jukyu_chart に合成)

1. **候補定数の新設** (`portfolio_shelve.py`) — 3軸:
   - `CHART_PLACE_OPTIONS = ("月足","週足","週足月足")` (場。実値から)
   - `CHART_PATTERN_OPTIONS = ("低位","CWH","VCP","高値")` (パターン)
   - `CHART_STATE_OPTIONS = ("形成","ブレイク","ブレイク済み","ブレイク失敗","再ブレイク")`
2. **UI**: 場 select + パターン select + 状態 select を同セルに並べる。各軸とも空可。
   3 select が狭いセルに収まるか CSS 調整 (折返し or コンパクト表示) が要る → 検証ポイント
3. **合成**: `{場}{パターン}{状態}` (例: 月足+CWH+ブレイク → `月足CWHブレイク`)。
   サーバ側合成。空軸はスキップ (場のみ → `月足`、場+パターン → `月足低位`)
4. **既存自由記述の救済**: パース不能な既存値はそのまま保持し ⚠️ 表示
   (複数行値・「下げすぎ・・」等のノイズは救済対象)

### C. 保存・バリデーション (`portfolio.py` `update_memo`)

- 売買戦略と同じ救済方針: 空 or 候補内 or 既存値は許可。新規のリスト外値は基本拒否だが、
  ステージ T は数値入力のため別途バリデーション (1〜9T 程度の範囲 or 空)
- 合成後の `stage`/`jukyu_chart` 文字列を保存。MEMO_FIELDS スキーマは**変更しない**

### D. マイグレーション

- スキーマ変更なし (既存フィールドに合成文字列を入れるだけ)。後方互換維持。
- 既存値は救済表示で温存。一括変換はしない (運用で徐々に選択式へ移行)

## 確定済み (ユーザー回答済み)

- **チャートパターンは3軸** (場+パターン+状態)。場は独立 select (上記 B)
- **推移選択時の T は推移の左側 S に付ける** (`2S~3S` + T=3 → `2S(3T)~3S`)

## 未確定事項 (codex レビュー / 実装時確定)

1. **ステージ T の入力 UI**: フリー数値 input か、1T〜5T の select か。実値上限は 5T。
   → 簡潔さで select (空,1T〜5T) を推す
2. **3軸チャート select のセル幅**: data-page="2" の狭いセルに3 select が収まるか。
   折返し or コンパクト化の CSS 調整が要る
3. **色付けの推移対応**: `1S~2S` など新推移候補が helpers.py:3606-3622 の `stage_hits`
   着色で想定通り動くか (現行は 2S/3S/4S のみ着色、1S は色なし)。回帰確認が必要
4. **合成⇔分解の可逆性**: `2S(3T)~3S` を分解 (S=推移 2S~3S, T=3) → 再合成して
   同値に戻ること。推移+T の往復が壊れないか要テスト

## 検証ポイント (Goal-Driven)

1. S 選択 + T 入力 → `stage` が `2S(3T)` 形に合成保存される (parametrize)
2. T 空 → `2S` (括弧なし) になる
3. 既存のリスト外値 (`2S(3T)~3S始？` 等) が救済表示され、保存で壊れない
4. パターン+状態 → `jukyu_chart` が `CWHブレイク` 形に合成される
5. ステージ色付け (helpers.py) が合成結果で従来通り動く (非回帰)
6. last_research_update 自動更新が維持される (一覧・チャート画面の両方)
7. `stage_s`/`stage_t`/`chart_*` の新規 POST キーが update_memo に届き合成される
   (form 抽出層の畳み込みテスト)
8. チャート画面 (`portfolio_charts.html`) でも選択式で保存でき、一覧と同じ結果になる
   (ブラウザ目視 + ルート保存テスト)
9. 救済値セル (`2S(4T)~3S始？` 等) は補助軸 disabled で、正規候補を選ぶまで元値が温存される
   (構造化保存に切替わるまで POST しない)

テストは parametrize で集約、1 PR 5本以下目安 (TESTING.md)。
テンプレJS/CSS のみの差分はブラウザ目視確認 (rules/testing.md)。

## スコープ外

- ステージ T 部分の**選択式化** (本プランは T は入力分離まで。select 化は後日、未確定3 と併せ別途)
- 既存自由記述値の一括正規化マイグレーション
- ステージ/チャートを使った自動判定・集計機能 (#341/#342 等は別)
