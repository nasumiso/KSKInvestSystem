# issue #366 実装プラン

## 目的

売買履歴ページのエピソード展開行に、そのラウンド専用の週足チャートを描き、実約定 (fill) の
IN / OUT を株価の形の上で確認できるようにする。往復明細・損益・振り返りメモと同じ視界に
並べることで、「どんな取引だったか」を figure と数字の往復で振り返れる状態にする。

## 前提 (調査で確定した事実)

1. **stock ページの詳細チャートには株価線が無い。**
   `build_price_rs_chart_full()` (webapp/helpers.py:3349) は RSライン (左軸) + RS(0〜99)履歴
   (右軸) の2軸パネルで、株価線は廃止済み (同3384行のコメント)。RSラインは基準週=0%起点の
   累積騰落率なので、約定単価をこの軸に打つことはできない。issue 本文の「stock ページの詳細
   チャートに IN/OUT を置く」は、既存チャートへの追記では実現できず、別チャートの新設になる。

2. **表示窓 20 週固定では取引期間を賄えない。**
   `_SPARK_LOOKBACK = 20` (helpers.py:2748)。一方 closed エピソード 398 件の保有日数は
   p50=15日 / p75=54日 / p90=123日(17.6週) / p95=179日 / max=394日。加えて「直近20週」窓の
   ため、2024年に決済したラウンドは窓に一切入らない (最古 open_date = 2024-09-13)。

3. **2年分の週足 OHLC は既にディスク上にある。**
   DB の `price_week_log` は25週だが、供給元の yfinance 週足キャッシュ
   (`stock_data/yahoo/price/yfinance_price_w_<code_s>.json`, `period="2y"`) は実測105週・
   2024-08-26 まで遡れる。3,595銘柄分が存在。**433 エピソード中 432 件が「open_date - 4週」
   までキャッシュで賄える** (不足1件・ファイル欠損0件)。新規のネットワーク取得は不要。

## 方針

### 1. 描画場所はエピソード展開行 (stock ページには足さない)

`trade_history.html` の `episode_rows()` マクロ (145行〜) が持つ展開行 `th-ep-detail` の中、
往復明細テーブルと振り返りメモの間にチャートを1枚置く。

stock ページを採らない理由:
- 上記前提1のとおり、既存チャートは RS 軸で約定価格を乗せられない。RSライン等との
  「切り替え」ではなく別物の新設になり、1銘柄1枚しか置けない制約も残る。
- 同一銘柄で複数ラウンドがある (6227 は closed 12 + open 1)。1枚に12ラウンド分の IN/OUT が
  重なると読めない。エピソード単位なら 1ラウンド 1枚で自然に解ける。

モーダル/ポップアップを採らない理由:
- 振り返りは「図を見る」ではなく「図と往復明細と振り返りメモを往復する」作業。モーダルは
  閉じないとメモを書けず、明細と見比べられないため目的に反する。

### 2. 表示窓はラウンド基準の可変窓

```
start = open_date - 4週
end   = (close_date or 直近確定週) + 4週
```

- 前4週 = どんな形のところを建てたか (ブレイク直後か押し目か)
- 後4週 = 売った後どう動いたか。issue #366 が列表示を廃した「売却後 N 営業日の騰落率」を、
  数字ではなく形で見せる部分にあたる
- 保有中エピソードは end = 直近確定週 (後4週の余白は取らない)
- 下限は設けない。p50=15日 (週足2本) + 前後4週 = 10本程度で、週足チャートとして成立する

### 3. 週足系列は yfinance 週足キャッシュから読む

`webapp/helpers.py` に週足キャッシュ読み出しヘルパを追加する。

- `price._load_yfinance_cache()` (price.py:1119) を再利用し、`YFINANCE_WEEKLY_CACHE_FNAME`
  を読む。`price_list` は株探形式 (`['2026年8月24日','5,700','6,080','5,590','5,750',...]`,
  日付降順) なので、既存の `price.parse_date_str()` で日付を、index 4 を終値として取る。
- **ネットワークアクセスは行わない** (webapp は yfinance を呼ばない既存方針を維持。
  helpers.py:5276 付近のコメントと同じ立場)。キャッシュが無い/古い場合は空を返す。
- DB の `price_week_log` は使わない (25週では窓を賄えないため)。

### 4. SVG 生成 `build_episode_chart(ep, weekly)`

`build_price_rs_chart_full` / `_mini` とは独立した新規関数として `helpers.py` に追加する。
**既存チャート関数には一切手を入れない。**

- 週足終値の折れ線 + Y軸に株価目盛り。X軸に月ラベル。
- **約定日 → 週足バーの対応づけ (実装を一意に固定する)。**
  yfinance 週足キャッシュの日付は**月曜アンカー**で (実測: 2026-08-24 / 08-17 / 08-10 … いずれも月曜)、
  fill の `trade_date` はその週の任意の営業日。**約定日は「その日を含む週の月曜バー」へ割り当てる**
  (`bar_date = trade_date - timedelta(days=trade_date.weekday())`)。
  「最近傍のバー」では週後半の約定が翌週バーへ吸われて位置がずれるため採らない。
  後述のズレ比判定も**同じバーの終値**を使う (マーカー位置と判定基準を一致させる)。
  該当バーがキャッシュに無い約定は、マーカーを打たない。
- IN マーカー: ラウンド開始の約定日に ▲ / OUT マーカー: クローズ日に ▼。
  空売り (`ep.is_short`) は上下反転。
- 現物 / 信用の色分けは既存バッジと同配色 (現物 `#80c0a0` / 信用 `#e0b070`)。
- 途中の買増・部分売りは**マーカーを増やさず小さな点のみ**打つ (issue 要件「初期実装では
  追加マーカーを増やさない」を守りつつ、分割約定した事実は形として見える)。
- 各マーカーに SVG `<title>` で 約定日・価格・株数・証券会社・損益 を出す。ホバーで読める。
- **マーカーの元データは `ep["fills"]` を (約定日, 売買方向) でまとめたもの。**
  1日に複数約定があっても1マーカーにし、株数は合算・価格は数量加重平均とする。

  `build_round_trips()` は使わない。往復行は表示用の再構成で、現物は1回の売り fill を
  FIFO で複数ロットへ分割し (helpers.py:5607 以降)、信用も返済1本を複数建玉へ按分しうる
  (helpers.py:5549 以降)。実例 285A (現物) は 2026-08-17 の売り fill 1本が同一価格
  59,508 の往復行 **4本**に化ける。同じ座標にマーカーが4個重なるため、打点源には使えない。
  約定日でまとめると 285A は 26点 → 23点になり、読みやすさも `1 fill = 1点` に勝る。

- **分割・併合をまたぐと、マーカーが株価線から外れる。初期実装では補正せず、
  外れた点は打たずに注記する。**

  チャートの週足は yfinance `auto_adjust=True` = **分割調整後**。一方 fill は約定当時の
  実価格で、`_apply_split_adjustments()` (helpers.py:4964) は
  **`split_adjustment` に登録済みのイベントがある銘柄しか換算しない** (さらに現物のみ対象で、
  信用は docstring 明記のとおり素通し)。登録が無ければ現物も未調整のまま残る。

  **実測 (全 fill の「約定価格 ÷ 同一週バーの終値」を集計。上記の月曜アンカー割り当てで算出):**

  | ズレ比 | エピソード数 |
  |---|---|
  | < 1.2 (正常) | 189 |
  | 1.2 – 1.5 | 12 |
  | 1.5 – 1.8 | 3 |
  | 1.8 – 2.2 | 19 |
  | ≥ 2.2 | 12 |

  **週足バーを引けた 235 エピソード中 34 件 (14%) がズレ比 1.5 以上**で、最大 5.47 倍 (247A)。
  9556 / 3465 / 247A / 5729 / 9984 / 7685 などが該当し、**現物・信用の両方**を含む。
  これらは `split_adjustment` 未登録のため `_apply_split_adjustments` が発火せず、
  `split_suspect` も付いていない。当初「3件のみ」と見積もったのは、
  返済 fill の `tate_price` を持つケースだけを数えた過小評価だった。

  補正はしない。`tate_price` による建値補正案は、`tate_price` が楽天・マネックスにしかなく
  (**SBI は 0/14 件**, portfolio_shelve.py:1087)、保有中エピソードには返済 fill 自体が無く、
  同日に別建値・別 broker の建てが複数ある場合の対応づけも一意に決まらない
  (helpers.py:5384 は `tate_date` + `tate_price` + broker でロットを区別している) ため、
  一部しか救えず新たな誤りを生む。

  **代わりの縮退**: 約定価格が近傍週足終値から **1.5 倍以上 / 1/1.5 以下**外れる点は
  マーカーを打たず、図に「分割・併合の可能性あり (未換算)」と注記する。
  閾値 1.5 は上表の分布から採る (正常側は 1.2 未満に 189 件が集中し、
  1.5〜1.8 の谷 3 件を挟んで 1.8〜2.2 に分割由来の山 19 件が立つ)。`_detect_price_jumps` の
  3倍閾値は 2.00 倍の実例 (7089 / 9556) を取り逃すため流用しない。

- ホバーの `<title>` に出す 約定日・価格・株数・証券会社・損益 は、まとめた fill 群から作る
  (複数約定を束ねた点はその旨を併記する)。
- **建て fill が無い決済 (`carry_over` や取込範囲外の建玉) は OUT のみ打ち、IN は打たない。**
  売った事実は実在するため、行ごと捨てると「いつ手仕舞ったか」が図から欠ける。

### 5. 遅延ロード (`/trade-history/chart`)

433 エピソード分の SVG を初期 HTML に埋めない。issue #406 で年折りたたみを入れて初期HTML量を
抑えた経緯と矛盾するため。

- `routes/trade_history.py` に `GET /trade-history/chart` を追加。`episode_key` は
  `code_s|kind|first_seq` 形式で `|` を含むので、パスセグメントではなく**クエリパラメータ**
  で受ける (既存の `save_fill_memo` が form パラメータで受けているのと同じ扱い)。
- **エンドポイント内で `build_fill_episodes()` を呼ばない。** 実測 0.5 秒 / 回で、全 fill 再走査 +
  全銘柄のエピソード再構成 + 保有中銘柄の価格ログ読みを含む (helpers.py:5236 以降)。一覧描画では
  routes/trade_history.py:288 で 1 回だけ実行している重い処理であり、1 行展開ごとに全履歴を
  再計算すると、初期HTML削減と引き換えに展開時レイテンシが悪化して目的が入れ替わる。
- 代わりに `episode_key` から**単一銘柄だけを再構成する軽量経路**を用意する。`episode_key` は
  `code_s|kind|first_seq` なので `code_s` を復元でき、`ps.list_fills()` を当該銘柄で絞って
  `_build_code_episodes()` に渡せば 1 銘柄分だけで済む。分割・併合の判定 (`split_adjustments` /
  `pending_review`) も銘柄単位で引ける。`build_fill_episodes()` の銘柄ループ本体を
  `_episodes_for_code(code_s)` として切り出し、全件版とエンドポイントの双方から呼ぶ
  (ロジックを二重化しない)。
- `trade_history.html` の既存の行展開ハンドラ (`th-ep-row` クリック) に、初回展開時のみ
  fetch してプレースホルダへ差し込む処理を足す。2回目以降は取得済み DOM を再利用。

### 6. 除外・縮退ケース

- `ep.split_suspect` : 価格軸が分割・併合未換算で壊れているため**チャートを描かない**。
  既存の「要確認」表示と同じ立場で、その旨だけ出す。
- `ep.carry_over` (期首持越し) : open_date が実際の建日ではないため **IN マーカーを打たない**。
  窓だけ確保して OUT のみ描く。
- 週足キャッシュが無い / 窓を賄えない (実測1件) : 「株価データなし」とだけ出して空表示。
  500 にしない (既存 detail.py:122 の「market_db が None でも 500 にしない」方針と同じ)。

## スコープ外 (issue 本文の「スコープ外」を踏襲)

- 売却後 N 営業日の騰落率を恒常列・サマリーとして出すこと
- 早売り / 遅売りの自動判定・通知
- 既存の保存済み売却後騰落データの削除・移行
- 日足への切り替え。**初期実装は週足のみ**とする。p50=15日保有だと週足では2本しか出ないが、
  短期ラウンドこそ前後4週の文脈が主役で、ラウンド内部の細かい値動きは往復明細テーブルの
  数字で足りる。不足を実際に感じてから別 issue で検討する。
- stock ページ側への IN/OUT 表示

## テストと確認

`.claude/rules/testing.md` のマッピングに従い、`helpers.py` 変更のため
`pytest tests/test_webapp_helpers.py tests/test_html_sanitizer.py -v`、
`routes/` 変更のため `pytest tests/test_webapp_routes.py -v` を実行する。

追加テストは CLAUDE.md の方針 (1 PR 5本以下・parametrize で集約) に従い、以下に絞る:

1. 窓算出 `(open_date, close_date, closed)` → `(start, end)` を parametrize で
   (クローズ済み / 保有中 / 短期ラウンド) の3ケース集約。あわせて約定日→週足バーの割り当てが
   週内のどの曜日でも同一の月曜バーを返すこと (週後半が翌週へ吸われない)。
2. 週足キャッシュ読み出しが、ファイル無し・壊れ JSON で例外を出さず空を返すこと。
3. `split_suspect` / `carry_over` でチャート要素が期待どおり縮退すること (parametrize 集約)。
4. `_episodes_for_code(code_s)` の結果が `build_fill_episodes()` の該当銘柄分と一致すること
   (切り出しによる挙動変化がないことの回帰テスト)。
5. マーカー生成を parametrize で集約 — (i) 同一日の複数約定が1マーカーに畳まれ株数が合算される
   (285A 相当)、(ii) 約定価格が近傍週足終値から 1.5 倍以上外れる場合にマーカーを打たず
   注記が出る (9556 / 7089 相当)、(iii) 建て fill 無しの決済で OUT のみ出て IN が出ない。

SVG の座標値そのものはテストしない (描画の見た目は目視確認の領分)。

## ユーザーが確認すべき点 (実装完了時に提示)

- 前後4週の窓が、実際の振り返りで狭すぎ / 広すぎないか
- 途中約定の「小さな点」が、IN/OUT マーカーと混同されず読めるか
- 展開のたびに fetch が走る体感速度 (既存の 7089 表示崩れ・描画速度の課題と併せて)
- **分割をまたぐラウンド (7089 / 247A / 9556 の信用) で、マーカーが株価線の上に正しく乗るか。**
  本プランで `round_trips` 基準を選んだ根拠そのものなので、実物で確認する
- 建値不明の往復行で OUT だけが打たれた図が、欠損として不自然に見えないか

## 派生して見つかった別件 (本 issue のスコープ外)

`split_suspect` の検知が現物のみを対象としており、**信用の分割・併合を捕捉していない**。
7089 / 247A / 9556 の信用エピソードは `tate_price` と実約定価格が 2.00 / 5.00 / 2.00 倍
ずれているが `split_suspect=None` のまま。本 issue では該当マーカーを「打たずに注記」するに留めるため、**`split_suspect` が付かないまま
損益・リターンが誤って集計されうる**問題は残る。**週足を引けた 235 エピソード中 34 件 (14%)** が
ズレ比 1.5 以上で、9556 / 3465 / 247A / 5729 / 9984 / 7685 など現物・信用の双方を含む。
原因は `split_adjustment` への分割イベント未登録 (登録が無いと `_apply_split_adjustments`
が発火しない) と、信用が換算対象外であること。チャートより先に集計値の正しさに効くため、
別 issue #435 として起票済み。
