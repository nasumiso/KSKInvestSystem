# feat(trade-history): エピソード明細を「買→売」の往復1行に畳む

## 目的

**実際の売買単位を可視化し、振り返りをしやすくする。**
後続対応で往復単位の振り返りメモ付与につなげることを見据えている。

現状、振り返りメモは **エピソード (建玉ラウンド) 単位** にしか付けられない。
4258 網屋は 2026-04-08 〜 08-25 の間ずっと建玉が0にならないため、14本の約定
(約7往復) が丸ごと1エピソードになり、メモは1つしか付けられない。
「07/06 に +54% で利確した判断」と「06/16 に -0.9% で損切りした判断」は
別の判断なのに、同じメモ欄に押し込むことになる。

往復行に分解すれば、その1行が実際に下した売買判断の単位になる。
メモを付ける対象として正しい粒度であり、**後続のメモ付与の前提条件**となる。

## 課題

売買履歴タブのエピソード行を展開すると、明細テーブルに約定 (fill) が時系列で
1本ずつ並ぶ。買いと売りが別行になっているため、「いくらで買っていくらで売れたのか」
という往復単位の成績が読み取れない。

4258 網屋の実データ (現行表示):

```
26/04/08  買  信用新規  200株  3,050円
26/05/14  買  信用新規  100株  2,975円
26/06/01  買  信用新規  100株  3,330円
26/06/16  売  信用返済  100株  3,300円  建2,975  26-05-14建 → 33日  +10.92%   +32,500円
26/06/16  売  信用返済  100株  3,300円  建3,330  26-06-01建 → 15日   -0.90%    -3,000円
26/06/19  買  信用新規  100株  3,160円
26/07/03  売  信用返済  100株  4,350円  建3,160  26-06-19建 → 14日  +37.66%  +119,000円
26/07/06  売  信用返済  100株  4,710円  建3,050  26-04-08建 → 89日  +54.43%  +166,000円
...
```

買いの行 (04/08 200株) と、それを決済した売りの行 (07/06 100株) が離れて並ぶ。
返済側には建単価・建日が入っているので情報としては揃っているが、対応する買いを
目で探す必要がある。

## やりたいこと

買いと売りを対応づけて **往復 (ラウンドトリップ) 1行** に畳む。

```
日付 (買→売)          株数   買単価 → 売単価   保有   リターン   損益
26/04/08 → 26/07/06   100株  3,050 → 4,710    89日   +54.43%   +166,000円   楽天
26/04/08 → 26/06/16   100株  3,050 → 3,300    69日    +8.20%    +25,000円   楽天
26/05/14 → 26/06/16   100株  2,975 → 3,300    33日   +10.92%    +32,500円   楽天
26/08/18 → (保有中)    100株  4,480 →   —       —        —         含み       楽天
```

## スコープ

対象は **売買履歴タブのエピソード行を展開した中の明細テーブル** のみ。

- エピソード行 (一覧の見出し行) の構成・列は変更しない
- 「エピソード単位 / 銘柄単位」のビュー切替は変更しない
- 成績サマリー (勝率・ペイオフ・実現損益) の集計ロジック・母数定義は変更しない
- アクションログタブは変更しない

**本 issue のスコープ外 (後続対応)**:

- 往復行への振り返りメモ付与。本 issue は往復行を作るところまでで、
  メモはエピソード単位の現行仕様を維持する。往復行にメモを持たせるには
  安定した行キー (エピソードキー + ロット識別子) の設計が必要であり、
  FIFO の充当結果は fill の追加取込で変わりうるため、キー設計を含めて
  別 issue で扱う

## 買↔売の対応ルール

### 信用: CSV の建玉情報をそのまま使う (推定しない)

信用返済 fill は証券会社CSV由来の `tate_date` / `tate_price` を持っている。
これが証券会社が実際に決済した建玉の対応そのものなので、FIFO 等で推定せず
そのまま使う。上の 07/06 売却が「04/08 建 → 89日 → +54.43%」になるのは
この情報による (FIFO で機械的に充当すると 06/16 の売却に当たり別の数字になる)。

実データ: 返済 fill 487本中 470本 (96.5%) が `tate_date` / `tate_price` を保持。

**建情報を持たない17本の扱い** (SBI 14本 / 楽天 3本、すべて2026年):
建玉を特定できないため、往復行を作らず **売りのみの行** として出す。
買単価・保有日数は `—` とし、損益は既存の計算結果があればそれを表示する。
推測でペアを作らない (誤った建値でリターンを出すほうが有害なため)。

### 現物: FIFO (先入先出) で古い買いから充当

現物の売り fill には建単価・建日が無く、対応する買いがCSVに存在しない。
FIFO で古い買いから順に充当する。

6479 ミネベアミツミの例:

```
買 26/02/26 100株 3,350円 / 26/03/04 100株 3,025円
売 26/06/12 100株 4,408円 / 26/08/21 100株 3,359円

FIFO:
26/02/26 → 26/06/12  100株  3,350 → 4,408  +31.58%  +105,800円
26/03/04 → 26/08/21  100株  3,025 → 3,359  +11.04%   +33,400円
```

FIFO を選ぶ理由: 税務・証券会社の考え方に近く、ロットごとのリターンが実際の
建値を反映する。現行の損益計算は平均取得単価法であり、**往復行の損益は
エピソード単位の損益と計算方法が異なる**点に注意 (下記「一貫性の要件」参照)。
エピソード行の損益額・サマリー集計は現行の平均取得単価法のまま変更しない。

### 買いの分割

1本の買い fill が複数の売りに分かれて決済される場合、買いを株数で分割して
それぞれの売りとペアにする (4258 の 04/08 200株 → 100株×2行)。
分割した各行の買単価・買付日は元の fill の値をそのまま引き継ぐ。

実データでの分割発生頻度: 信用の建玉キーごとの返済本数は
1本:397 / 2本:25 / 3本:5 / 4本:2。大半は1:1で、分割は少数。

### 未決済の残り

売りに充当されずに残った買いは `→ (保有中)` の行として出す。
売単価・保有日数・リターンは `—`、損益は含み損益を表示する
(エピソード行の含み損益と定義を揃える)。

### 現引

現引は信用建玉を現物へ振り替える取引で、信用側・現物側の両エピソードに同じ
約定が出る (現行実装のコメント参照)。往復行でも現行同様に両側へ出し、
信用側は「現引で決済 (→現物へ振替)」、現物側は取得として扱う。
信用側は損益を計上しない (現物へ持ち越すため)。

## 一貫性の要件 (重要)

### 信用: 完全一致する

返済 fill ごとの `fill_pl` を往復行に載せるだけなので、往復行の損益合計は
エピソードの実現損益と必ず一致する。

### 現物: クローズ済みは一致、未クローズは意図的に不一致を許容する

現行の実現損益は**平均取得単価法**で計算されているのに対し、往復行は**FIFO**で
ロット対応を作る。両者は **部分売却で建玉が残る場合に一致しない**。

反例 (実際に検証済み):

```
100株@100円 買 → 100株@200円 買 → 100株@150円 売 (100株残る)
  FIFO         : +5,000円  (100円の玉を150円で売った)
  平均取得単価法 :      0円  (平均150円の玉を150円で売った)
```

**方針: FIFO を優先し、保有中ラウンドの不一致は許容する。**
行ごとの損益が実際の建値を反映するほうが、振り返り・メモ付与という目的に合うため。

実データでの影響 (検証済み):

- クローズ済み現物ラウンドの実現損益合計:
  **FIFO = 平均取得単価法 = 3,953,405円 (差0円)** — 全株売却されると総額は一致する
- 不一致が生じうるのは「買い複数 × 売り交錯 または未クローズ」の
  **現物142ラウンド中8件** (285A, 6501, 7047, 4390, 6965, 6890, 7089, 1491)。
  いずれも保有中エピソードの途中経過であり、確定成績には影響しない

**したがってサマリー (勝率・ペイオフ・実現損益) は一切変わらない。**
母数はクローズ済みエピソードのみであり、そこでは両者が一致するため。

保有中ラウンドでは往復行の損益合計とエピソード行の実現損益が食い違いうるので、
**その旨をツールチップ等で明示する** (数値のズレを不具合と誤読させない)。

### その他

- `split_suspect` (分割・併合の疑い) のエピソードは現行どおり数値を隠す

## 表示仕様

### 列構成

| 列 | 内容 |
|---|---|
| 日付 | `26/04/08 → 26/07/06` (未決済は `→ (保有中)`) |
| 区分 | 信用新規買/信用返済売、現物、現引 など。売建は「売建」バッジ |
| 株数 | `100株` |
| 単価 | `3,050 → 4,710` |
| 保有 | `89日` |
| リターン | `+54.43%` |
| 損益 | `+166,000円` |
| 証券会社 | `楽天` |

現行の明細10列 (日付/売買/区分/株数/単価/建単価/建日・保有/損益率/損益額/証券会社)
から、買と売が1行に畳まれる分だけ列が減る。建単価は「単価」列の左辺に統合。

### 並び順

決済日の降順 (最新が上)。現行明細も最新が上なので踏襲する。
未決済 (保有中) の行は買付日の降順で末尾にまとめる。

### 空売り (信用売建)

新規売 → 返済買 の順になる。日付列は `建 → 決済` の時系列順のままとし、
単価列は `売単価 → 買単価` になる点をヘッダかツールチップで示す。
リターンの符号は現行の `fill_return_pct` の計算結果に従う。

## 実装方針

- `webapp/helpers.py` に往復行を組み立てる関数を追加
  (エピソードの `fills` を受け取り往復行リストを返す)。
  `build_fill_episodes()` の各エピソードに `round_trips` として付与する
- 損益・リターンは既存の `fill_pl` / `fill_return_pct` を再利用し、
  計算ロジックを二重化しない。現物のFIFO按分のみ新規計算
- `trade_history.html` の明細テーブル部分を往復行テーブルに差し替え
- エピソード行・サマリー・年アコーディオンには手を入れない

## テスト

`tests/test_webapp_helpers.py` に parametrize で集約 (5本以下):

1. 信用の1:1往復 (`tate_date`/`tate_price` から建値・保有日数が入る)
2. 買い1本が複数売りに分割される (4258 04/08 200株相当)
3. 現物のFIFO充当 (6479相当)。**クローズ済みラウンドでは** 往復行の損益合計が
   エピソード実現損益と一致すること
4. 現物の未クローズ部分売却で FIFO と平均取得単価法がずれること
   (100@100買→100@200買→100@150売100株 で FIFO +5,000 / 平均法 0 を固定)。
   意図的な差異なので、一致を期待するテストにしない
5. 未決済の残りが「保有中」行になる / 建情報なしの信用返済が売りのみ行になる
