## 再定義の理由

本文執筆時の技術的前提が2点崩れており、加えて事前検証 (2026-08-30 / 実データ60銘柄) と

## 確定済みの前提 (既存コメント2件で決着)

| 項目 | 結論 |
|---|---|
| PDFリンク抽出 | **不要**。URL の機械変換で直接取得できる |
| TDnet フォールバック | **不要**。株探だけで1年分揃う |
| 過去分の遡り | `disclosure_db.csv` には無い。`ir_docs.py` 側で `&b=disclose&page=N` を辿る |

| `doc_id` | TDnet ID (開示ごとに一意) |
| 保存形式 | ページ配列で保持 (#433 のページ範囲指定取得が前提とする) |

PDF URL の変換規則:

```
https://kabutan.jp/disclosures/pdf/20260828/140120260828527831/

```

`disclosures/pdf/...` を GET すると `text/html` (広告付きビューア) が返るため、
そちらを踏む実装にすると1リクエスト無駄になる。HTMLパース不要 = HTML変更で壊れる箇所もゼロ。

## スコープ

### 対象資料

| 種別 | `doc_type` | 判定 |
|---|---|---|
| 決算短信 | `tanshin` | 見出しに `決算短信` |
| 決算説明資料 | `setsumei` | 見出しに `決算(補足)?説明(会)?資料\|決算短信補足` |

**スコープ外**: 中期経営計画 (別issue)、有価証券報告書、修正リリース。

決算短信は **#139 では DL・テキスト化まで行い、`doc_type: "tanshin"` を付けて保存する**。
MCP (#433) が短信を返すかどうかは #433 側の判断に委ねる (データ構造はどちらでも対応可)。

### 収集深度

資料の価値は新しいほど高いため、**優先度を収集順序に落とす**。

| 段階 | 範囲 | 失敗時の扱い |
|---|---|---|
| 1 | **直近1件** | **ERROR**。これが取れないと #433 が成立しない |
| 2 | 直近1年 (4期) | WARNING のみ |
| 3 | 2年 (8期) | WARNING のみ。**初回スコープ外** |

CLI は `--depth latest|1y|2y` (既定 `1y`)。**初回運用は `1y` 固定**とし、`2y` は
株探 page 遡りのリクエスト数 (universe 300銘柄 × 最大16ページ ≒ 4,800req) を
実運用で見てから解禁する。

#### `collected_depth` は「検証済みの最大完全収集深度」

`collected_depth` は #433 の `partial_coverage` 判定の根拠になるため、
**「最後に要求した深度」ではなく「取りこぼしなく走査できた最大の深度」**とする。

- **完全走査できたときだけ更新する**。株探の page 遡り / PDF取得 / テキスト抽出のいずれかが
  1件でも失敗したら、その深度では `collected_depth` を更新しない
- **後退させない**。`1y` 収集済みの銘柄に `--depth latest` を実行しても、
  既存の `collected_depth: "1y"` は維持する (実データは消えないため)。
  深度は `max(既存, 今回の完全走査深度)` で単調増加させる
- 失敗は**試行深度ごとに** `collection_errors` に残し、次回実行時の再試行対象とする

```json
{
  "collected_depth": "1y",
  "last_requested_depth": "2y",
  "last_collected_at": "2026-09-22T20:00:00+09:00",
  "collection_errors": {
    "2y": [
      {"doc_id": "140120250812511234", "stage": "pdf_download",
       "reason": "HTTP 404", "at": "2026-09-22T20:00:00+09:00"}
    ]
  }
}
```

状態モデルの規則:

- **`collected_depth` は導出値ではなく実体**として持つ。「完全走査できた最大深度」を
  そこに書く。未試行の深度と成功した深度を `collection_errors` の有無から
  区別することはできない (`{}` は「全成功」でも「未試行」でもありうる) ため、
  **成功済み深度は `collection_errors` と独立に保持する**
- 更新規則: ある深度 `d` を完全走査できたら
  `collected_depth = max(collected_depth, d)` (深度の順序は `latest` < `1y` < `2y`)。
  失敗が1件でもあれば `collected_depth` は変更しない
- `collection_errors` は **深度をキーとする dict**。試行して失敗した深度のみキーを持つ。
  **未試行の深度はキーを持たない**
- ある深度 `d` を完全走査できたら、`d` 以下のすべての深度のエラーキーを消す
  (`2y` が成功すれば `1y` のエラーも解消済みのため)
- 3状態の判定: 深度 `d` は
  `d <= collected_depth` なら **完全**、
  `collection_errors` にキーがあれば **未達**、
  どちらでもなければ **未試行**
- 再試行は `collection_errors` に残っている深度に対してのみ行えばよい

上の例 (`collected_depth: "1y"` / `collection_errors: {"2y": [...]}`) は
「`latest`・`1y` は完全 / `2y` は未達」を表す。
`collected_depth: "1y"` / `collection_errors: {}` なら
「`latest`・`1y` は完全 / `2y` は**未試行**」となり、両者が区別できる。

`collected_months` は `collected_depth` から導出 (`latest`=0 / `1y`=12 / `2y`=24)。

### 見出しフィルタ

「決算説明」を含む開示の多くは資料そのものではない:

```
2026年12月期第２四半期決算説明会の書き起こしに関するお知らせ
2027年3月期 第1四半期決算説明会動画・AI要約版 公開について
```

これらは「動画を公開しました」という1枚の案内PDFで、除外しないと大量に掴む。

```python
INCLUDE = r'決算短信|決算(補足)?説明(会)?資料|決算短信補足'
EXCLUDE = r'お知らせ|訂正|書き起こし|動画|について|開催'
```

#### 訂正版・修正版の扱い

`訂正` を EXCLUDE に入れると訂正版を取り逃す。実データで原本と修正版が併存する例がある:

```
20260213  2025年12月期 決算短信補足資料              ← 原本
20260302  2025年12月期通期決算短信補足資料（修正版）  ← 修正版 (別開示・別ID)
```

- 見出しに `修正版` / `訂正` を含むものも**収集対象に含める** (EXCLUDE から外す)。
  ただし「〜の一部訂正に関するお知らせ」のような**案内文だけの開示は除外** (`について|お知らせ` との組み合わせ)
- `index.json` の各レコードに **`supersedes` / `superseded_by`** を持たせ、
  原本と修正版を関連付ける
- **`is_latest: true` を正本**とし、修正版が出たら原本の `is_latest` を `false` にする

#### 関連付けキー (誤 supersede の防止)

「同一会計期間」だけを条件にすると、**同じ期の `tanshin` と `setsumei` が互いを
supersede したり、四半期と通期が混ざったりして、正本が MCP から silent に消える**。
以下の3つが**すべて一致**する場合のみ関連付ける:

| キー | 例 | 抽出元 |
|---|---|---|
| `doc_type` | `setsumei` | 見出しフィルタの判定結果 |
| `fiscal_period` | `2025年12月期` | 見出しの `\d{4}年\d{1,2}月期` |
| `quarter` | `FY` / `Q1` / `Q2` / `Q3` | 見出しの `第[1-4１-４]四半期` / `通期`、無ければ `FY` |

`quarter` の正規化は「`第2四半期` → `Q2`」「`通期` または四半期表記なし → `FY`」とする。
`中間` は `Q2` に寄せる。全角数字 (`第１四半期`) と全角月 (`2026年９月期`) を正規化すること。

#### 3キー一致は必要条件であって十分条件ではない (実測)

`disclosure_db.csv` の開示1,821件で3キーが一致する組を数えると **6組**。
うち**訂正版と呼べるのは2組だけ**で、残り4組は別資料だった:

```
2304  20260812  2026年９月期 第３四半期決算説明資料            ← 本体
      20260812  2026年９月期 第３四半期決算説明資料（スクリプト付） ← 別資料 (同日)
7793  20260814  2026年12月期 第２四半期決算説明資料
      20260904  2026年12月期第２四半期 決算説明会資料          ← 別資料 (説明会資料)
7095  20260910  2027年4月期 第1四半期 決算説明資料
      20260911  2027年4月期第1四半期決算説明会資料（書き起こし）  ← EXCLUDE 対象
9509  20260730  2027年３月期 第１四半期決算短信〔日本基準〕（連結）
      20260807  …（公認会計士等による期中レビューの完了）        ← 実質の最終版
```

3キーのみを条件にすると **`2304` の本体が「スクリプト付」に隠される**。

→ **新しい側の見出しが訂正・改訂を示す場合のみ関連付ける**。追加条件:

```python
REVISION = r'訂正|修正版|再表示|期中レビューの完了'
```

`REVISION` にマッチしない組は **別資料として両方 `is_latest: true` のまま残す**。
`（スクリプト付）` `決算説明会資料` のような派生・別系列はここで弾かれる。

**上記いずれかの条件を満たさなければ関連付けを諦め、両方 `is_latest: true` のまま残す**
(誤って正本を隠すより、両方見える方が安全)。#433 は `is_latest` が複数立つ前提で実装する。

## テキスト品質判定

DL しただけでは LLM に渡せない資料が一定数ある。**保存時に品質を判定して記録する**。

### 実測 (60銘柄)

| 判定 | 件数 | 割合 |
|---|---:|---:|
| `ok` | 55 | 91.7% |
| `garbled` | 3 | 5.0% |
| `image_based` | 2 | 3.3% |

良好な資料は**グラフの数値ラベルまでテキストで取得できる** (PowerPoint 由来のベクター描画)。
例: 4011 P51 の営業利益推移は9四半期分の金額・利益率がすべて数値で抽出できた。

### 文字数だけでは不十分

`485A` パワーエックスは **41,434文字が抽出されるが全文が化けている**:

```
썛쎱쎯쎡쎤쎚쎜쎯쏀쎤쎏쎬썑쎏쎯쎚썑썻쎼쎱쎹쎼쎤쎜쏀...
```

PDF のフォントに ToUnicode マップが無く、グリフ番号が別領域の文字に化けるのが原因。
`5071` ヴィス・`9271` 和心は化け方が異なり (`ϰΟε` = ヴィス)、CJK がほぼ0%になる。

```python
avg           = 総文字数 / ページ数
garble_ratio  = ハングル領域文字 / (CJK文字 + ハングル領域文字)
cjk_ratio     = CJK文字 / 総文字数

if avg < 100:            "image_based"   # 4193(頁平均10), 4436(頁平均33)
elif garble_ratio > 0.3: "garbled"       # 485A(88.9%)
elif cjk_ratio < 0.06:   "garbled"       # 5071, 9271 (CJK率0%)
else:                    "ok"
```

60銘柄で誤検知・見逃しなしを確認済み。`ok` 判定55件のうち最小 CJK率は 27.3% で、
閾値 6% とは十分離れている。

**OCR は実装しない。** 画像主体資料は ChatGPT に PDF を直接添付すれば読めることを
実機確認済み (2026-08-30)。重い依存を持ち込む必要がない。

## 対象銘柄 (universe)

`update_disclosure_all()` と同じく **保有 + ウォッチ銘柄** (`portfolio.parse_my_portforio()` 由来)。
実測で約300銘柄。全銘柄を対象にすると数千銘柄 × PDF でディスク・帯域が現実的でない。

### 収集状態の記録

universe は時間とともに変動する (売却でウォッチ外になる / 新規にウォッチ入りする)。
「収集していないから資料が無い」のか「本当に資料が無い」のかを #433 が区別できるよう、
**銘柄単位で収集状態を記録する**。

- `index.json` が存在する = **一度は収集した銘柄**。現在の universe から外れていても
  過去の収集結果は保持し続ける (削除しない)
- `index.json` が無い = **未収集**。資料の有無は不明

これにより「現在ウォッチ中か」と「収集済みか」を分離でき、MCP 側は後者を基準に応答できる。

## 検証方法

1. `pytest tests/test_ir_docs.py -v` が通ること
2. `python ir_docs.py download 4011 --dry-run` で過去4四半期の短信・説明資料が拾えること
3. `--force` なしで既存ファイルがスキップされること
4. `text_quality` が実測どおり判定されること (`4011`=ok / `485A`=garbled / `4436`=image_based)
5. 訂正版がある `4011` の 2025年12月期で `is_latest` / `supersedes` が正しく付き、
   **同じ期の `tanshin` と `setsumei` が互いを supersede しない**こと。
   `2304` の「決算説明資料」と「決算説明資料（スクリプト付）」が**両方残る**こと
6. 段階1 (直近1件) が取れない銘柄で ERROR、段階2で取りこぼしても WARNING に留まること
7. `index.json` が universe 外の銘柄でも削除されないこと
8. **深度の単調性**: `--depth 1y` の後に `--depth latest` を実行しても
   `collected_depth` が `1y` のまま後退しないこと
9. **失敗時に深度を更新しない**: PDF取得を1件失敗させた状態で `--depth 1y` を実行し、
   `collected_depth` が更新されず `collection_errors` に記録されること

## 注意事項
