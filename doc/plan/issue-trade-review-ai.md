# review: 月次の売買振り返り `/trade-review` (#448)

> 2026-10-11 に、9月の実データで作った見本を節ごとにユーザーが確認して仕様を決めた。以前の版 (6軸の rubric を全軸判定する案) は Git 履歴にある。変えた点は末尾の「以前の計画から変えた点」。

## 何を作るか

月に1回、Claude Code のセッションで `/trade-review 2026-09` を実行すると、次が1回で終わる。

1. Python が数字を JSON で出す (LLM は DB を触らない)
2. AI が JSON・`doc/投資戦略.md`・当月の投資日記を読み、レポートを書く
3. AI が問いを選択肢で聞き、ルール候補から「翌月変えるルール1つ」をユーザーが選ぶ
4. レポートと JSON を保存し、選んだルールを `doc/投資戦略.md` のルール変更履歴に追記する

役割分担は [AI投資活用戦略.md](../AI投資活用戦略.md) のとおり: Shintakane = 数値、LLM = 照合と問い、人間 = ルールの決定。

### 2. 取引ごとの照合

対象は **当月に完全決済したエピソード** と **当月に新規に建てたエピソード** (9月は 9件 + 7件)。

- 決済: `closed` かつ `close_date` が当月
- 新規建て: `open_date` が当月。最初の約定が現引のもの (信用からの振り替え) と、当月中に決済したもの (決済側に出る) は除く
- 部分売却・買い増しだけのエピソードは対象外

全件を表に1行ずつ載せ、逸脱のあった取引だけ根拠を数行書く。

決済の列: 取引 (銘柄・戦略・保有日数・損益率) / 時間軸 / 売りの分類 (推定) / 損切り・利確の幅 / 判断 × 結果

新規建ての列: 取引 (銘柄・戦略・建てた日・株数と単価) / 建てた日の局面 / 再INか / 入口の理由

| 判定 | 出し方 |
|---|---|
| 時間軸 | Python。戦略の `time_horizon` と保有日数を `is_hold_days_consistent` で判定 |
| 損切り・利確の幅 | Python。損益率と、途中の部分売却の約定 |
| 建てた日の局面、再IN | Python。再IN = 同じ銘柄の直前の決済から30日以内。前回の決済日・損益率・最大株数を添える |
| 売りの分類、入口が買いルールを満たすか、判断 × 結果 | AI の推定。「推定」と明記し、根拠にしたメモ・日記の文言を引用する。メモも日記の記述も無ければ「判定不能」と書く |

### 3. 弱点仮説の検証 (年初来の累計 + 当月の内訳)

| 仮説 | 数字 | 2026年1〜9月の値 |
|---|---|---|
| 損切りの幅 | 損失で終わった決済のうち、損益率が −10% を下回った件数と損益。原則内の損失の損益 | 損失98件中36件、−454万円 (原則内 −243万円) |
| 売ってすぐ買い直す | 建てた日の前30日以内に同じ銘柄の決済があるエピソード (再IN) の件数。そのうち決済済みの勝敗と損益 | 見本は決済側から数えて54件、決済済み46件は18勝28敗、−34万円。実装は建てた側から数えるので値は変わる |

- 各行に「うち当月 n 件」を添える
- 母数は当年1月1日から当月末までに決済したエピソード。分割・併合の疑い (`split_suspect`) と、損益を持たないもの (取込期間より前の建玉の返済など) は除き、除いた件数を JSON に出す。`split_suspect` は `build_fill_episodes` が付けた値にそのまま従う (決済済みの信用には付かない。[株式分割併合の換算は現物のみ](../decisions/2026-08-10-株式分割併合の換算は現物のみ.md))
- 短期売買と戦略宣言なしは、サマリーに当月分があるのでここには載せない
- 損切りの遅れは保有日数ではなく幅で測る (負けの保有日数の中央値は14日、勝ちは34.5日で、日数では成り立たない)

### 4. 保有PFの点検 (レポートを作った日の状態)

| 項目 | 内容 | 10/9 の値 |
|---|---|---|
| 運用比率 | 直近の `exposure_log` の比率・局面・目安 | 94.5%、調整 (目安 65〜80%)、上限を 14.5pt 超過 |
| 銘柄数 | 1保 の数 (目安は実保有10 + 打診5) | 27 |
| 小口 | 評価額が建玉合計の3%未満の銘柄数と合計額 | 9銘柄、495万円 |
| 損切り原則を超えた含み損 | 含み損益率が −10% を下回る保有中エピソード (1保 の銘柄に限る) | 2780 −15.8%、7685 −14.6% |

- 過去の月末の保有は復元できないので、作った日の状態を書く
- 含み損益率は 含み損益 ÷ (平均取得単価 × 残株数)。部分売却の実現損益は混ぜない
- 防衛線の状態、テーマの集中、記録の不備 (入口の理由が空、戦略の食い違い) は載せない
- 指摘まで。売買の提案はしない

### 5. 問い (3件)

情報量の大きい取引 (逸脱、再IN、損切り原則超えの保有、局面と逆の売買) を指名し、**選択肢で**聞く。回答はレポートに書き込む。詳しい反省は日記に任せる (`doc/投資戦略.md` の「振り返りは短く・選ぶだけにする」)。

### 6. 翌月変えるルールの候補 (2〜3個)

候補ごとに 根拠の数字 / 翌月の確かめ方 を付ける。**翌月に JSON の数字で確かめられないものは候補にしない** (心構えは出さない)。ユーザーが1つ選び、スキルが `doc/投資戦略.md` のルール変更履歴に1行追記する。

## 実装

### Python: `scripts/trade_review.py` (新規)

`build_review_dataset(year_month, *, episodes, exposure_history, records, prices, trade_ideas, today)` は引数だけで計算する関数にし、DB を読むのは CLI 側の薄いラッパだけにする (テストで DB を使わない)。`prices` は 1保 の銘柄の現在値 (`{code_s: 終値}`) で、CLI 側が `helpers._bulk_get_stock_data` から作って渡す。

```text
{
  "year_month", "generated_at",
  "summary":   {"closed", "undeclared", "hold_bands", "by_state", "exposure"},
  "trades":    {"closed": [...], "opened": [...]},
  "hypotheses": {"stop_loss_width", "reentry", "excluded_count"},
  "portfolio": {"as_of", "exposure", "holding_count", "small", "over_stop_loss", "holdings": [...]}
}
```

- `trades` の各行: エピソードの既存項目 (キー、銘柄、区分、日付、損益、戦略、`strategy_drift`、振り返りメモ、`action_notes`) + 当月を含む全約定 (日付・売買・株数・単価・その日の局面) + `time_horizon` と整合 + 再INの情報
- `portfolio.holdings`: 1保 の銘柄ごとに 株数・評価額・比率・戦略・含み損益率。レポートには使わないが、月1回のスナップショットとして残す (保有の遷移を追う専用の仕組みは作らない。再検討は、約定からは出せない問いが実際に出たとき)
- CLI 側のラッパが呼ぶ既存の関数: `build_fill_episodes`、`ps.list_records("1保")`、`ps.list_trade_ideas`、`exposure_guide` のログ読み込み、`helpers._bulk_get_stock_data`。計算側は `ps.is_hold_days_consistent` だけを使う
- `list_portfolio_with_indicators` は呼ばない (表示のたびに防衛線のイベントを DB へ書くため)
- 閾値は定数: 損切り原則 −10%、再IN 30日、小口 3%、保有日数帯 3日 / 90日

CLI:

```bash
cd scripts && python trade_review.py json 2026-09          # 標準出力へ。保存しない
cd scripts && python trade_review.py save 2026-09 < report.md   # JSON を作り直し、md と一緒に保存
```

- 保存先は `$KS_DATA_DIR/trade_review/2026-09.json` と `2026-09.md`。どちらかが既にあればエラーで終わり、何も書かない (上書きの手段は作らない。やり直すときは人がファイルを消す)
- `save` は開発機 (`is_dev_data_dir()`) ではエラーにする (不変条件「開発機は正本データに書かない」)。開発機からは `deploy/macmini.sh run python trade_review.py save 2026-09 < report.md` で運用機に書く
- `save` は md を受け取った時点で JSON を作り直す。`json` を出してから日次バッチをまたぐと、分析した数字と保存した JSON がずれる。スキルの手順に「同じ日のうちに保存する」と書く

テスト (`tests/test_trade_review.py`、5本以内、parametrize):

1. 対象の選び方: 当月決済 / 当月新規建て / 現引で始まる現物 / 当月に建てて当月に決済 / 部分売却だけ
2. サマリー: 保有日数帯の境界 (3日・4日・90日・91日)、戦略なし、局面別の売買額から現引と空売りを除く
3. 弱点仮説: −10% ちょうどと超過、30日ちょうどと31日の再IN、`split_suspect` と損益なしの除外
4. PF: 含み損益率に実現損益を混ぜない、1保 でない銘柄の保有中エピソードを出さない
5. `save`: 既存ファイルがあると書かない、開発機では書かない

### スキル: `.claude/skills/trade-review/SKILL.md` (新規)

`disable-model-invocation: true`。手順:

1. 実行環境を判定する。開発機なら以降の Python は `deploy/macmini.sh run` 経由
2. `trade_review.py json YYYY-MM` を取る。前月の `YYYY-MM.md` があれば読む
3. `doc/投資戦略.md` を読む
4. Google Drive の「投資メモ」から当月分を読む (コネクタが無ければ飛ばし、レポートにその旨を書く)。レポートには日付と短い引用だけを残す。教訓Top10 との照合は初回は見送る
5. レポートの §0〜§4 と §6 の候補を書いて表示する
6. §5 の問いを選択肢で聞き、回答をレポートに入れる
7. ルールを1つ選んでもらう (選ばない、も可)
8. `save` で保存する。選んだルールを `doc/投資戦略.md` のルール変更履歴に追記する (コミットはユーザーに確認してから)

禁止事項: 銘柄の推奨・売買の提案をしない / メモも日記も無い取引の動機を断定しない / 月次の絶対額で人を評価しない / 数字を JSON 以外から作らない。

## 先に貯めておく必要があるデータの精査

「後から戻せないので、いま記録を始めないと将来のレビューで使えない」ものがあるかを、レポートの項目ごとに確かめた (2026-10-11)。

| レポートが使うデータ | 残り方 | 判定 |
|---|---|---|
| 約定、エピソード、損益 | fill は追記のみで全件残る | 足りている |
| 戦略と付け替え | エピソードに焼き付け + 有効日つきの変更履歴 | 足りている |
| 売買の理由 | action_log (追記のみ)、振り返りメモ、投資日記 (Drive) | 足りている |
| 約定日の局面、運用比率、目安、基準運用額 | `exposure_log.json` に日次で残る。件数の上限なし。2026-08-29 より前は無い | 足りている (8月以前の月を遡って作ることはできない) |
| 過去の日の銘柄別の株数・評価額・含み損益 | 株数は fill から、株価は yfinance から取り直せる | 足りている (必要になったら計算する) |
| 問いへの回答、選んだルール、その月の PF | どこにも無い | **この issue で月次の md / JSON として残す** |

レポートが使わないが、記録していないので戻せないもの:

| データ | 影響 | 扱い |
|---|---|---|
| 自己申告の感情スコア | `doc/投資戦略.md` はレバレッジを感情スコアで決めるとしているが、その日のスコアが残っていない。「調整局面で買い越したのは方針どおりか」を後から確かめられず、月次の問いで思い出して答えるしかない | #480 で判断する。進めるなら、入力を先に始める価値がある唯一の項目 |
| メモの過去の値 (stage、入口の理由、業態テーマ) | 上書きされる | レポートで使わない。月次 JSON にも入れない |
| 逆指値を置いたか | 「買い注文と同時に逆指値」のルールを確かめられない | レポートで使わない。ルール候補に選ばれたら考える |
| 見送った銘柄 | 不変条件「見送りも判断として残す」は未実装 | この issue の対象外 |
