# review: 売買履歴と保有PFのAI振り返り分析 — 投資原則を判定基準にした月次レビュー (#367 の具体化)

## 背景

### 数字は揃ったが、振り返りは動いていない

`/trade-history` は fill (証券会社CSV) 基準で建玉ラウンド=エピソードを再構成し、年別・戦略別の成績サマリーまで出せる。一方で「なぜ買い、なぜ売ったか」の記録は薄いまま (2026-09-19 時点の本番DB):

| 項目 | 実態 |
|---|---|
| fill エピソード | 454 (クローズ 421 / 保有中 33) |
| 振り返りメモ (fill memo) | 13 件 = クローズ済みの 3% |
| 売買戦略の付与 | 115 件 = 25% (うち seed 由来を含む) |
| 売却理由 (action_log 売却) | 44 件、自由記述 (「なんとなく」「損切り遅れ」等の率直な一言が多い) |
| エントリー宣言 (#363) | 戦略必須化のみ実装。無効化条件・サイズ根拠・想定保有期間・売却時の「該当した出口」は未実装 |

仕様レビュー0704 の「閉じるべき3ループ」の③ (システム→成績→改善) が #367 だが、#367 は「数字を眺めて翌月のルールを1つ変える場」を定義しただけで、**誰が・何を基準に・どう考察するか**は「実装時判断」のまま残っている。

### 判定基準が言語化できた

投資スタイルの自己分析と他己分析が下記の6軸にまとまった。これを **判定基準 (rubric)** として固定し、AI (claude -p) に売買履歴を照合させる形で #367 を具体化する。

役割分担は MCP 構想 (#426, `doc/plan/mcp-parent-concept.md`) と同じ:

```text
Shintakane = 数値・記録・集計 (データセットを作る)
LLM        = 原則との照合・解釈・反証・問いかけ
人間       = 「翌月変えるルール1つ」の決定
```

## 投資原則 (rubric の元になる自己分析・他己分析)

**自己分析**

- 中期モメンタム投資 (新高値ブレイク、オニール・ミネルヴィニ)
- 中長期 GARP グロース投資
- ファンダメンタル投資、テーマ追従 (半導体)
- ポジション管理: 1.2〜1.5倍レバレッジ。相場感情による調整 (暴落では拾いたい、挑戦中)
- 銘柄発見評価・市場考察・PF管理を行う個人システム (Shintakane) を開発運用、コーディングAI活用

**他己分析: 日本株中心の中期・中長期グロース投資**

| 軸 | 内容 |
|---|---|
| ① 銘柄選択 | 構造成長テーマや個別企業の変化から、大きな業績変化が起こりそうな企業をファンダで発掘 |
| ② リターン源泉 | 「業績変化 × 市場の未織り込み」。GARP 的に成長性とバリュエーションのバランスを見る |
| ③ タイミング | 新高値・相対強度・出来高などオニール/ミネルヴィニ的な中期モメンタム。ファンダで選び、モメンタムで確認 |
| ④ テーマ | AI・半導体などの構造成長テーマをサプライチェーンと利益波及まで掘る |
| ⑤ ポジション管理 | 通常 1.2〜1.5倍レバレッジ、相場環境に応じてエクスポージャー調整 |
| ⑥ 投資システム | 裁量投資の再現性を高めるため Shintakane を開発運用し、AI も分析・開発に組み込む |

SPI 由来の弱点仮説 (`doc/投資戦略.md`): 損切り遅れ・売り判断の遅れ、含み損での自責、場中の衝動判断、「なんとなく」の打診が堆積する。

## 各軸を売買履歴で検証する観点 (本 issue の中核)

AI に渡すのは「原則」と「データ」だけでなく、**軸ごとに何をどのデータで検証するか**を固定する。これが無いと感想文になる。

| 軸 | 検証する問い | 使うデータ (既存。欠損は null で渡す) |
|---|---|---|
| ① 銘柄選択 | 入口の根拠が書かれたエピソードと無いものの成績差。イナゴ元由来と自力発掘の成績差 | portfolio memo `watch_in_reason`、research レコード `inago_origin` (#420 で移設済み)、エピソード損益 |
| ② リターン源泉 | 決算またぎの成績 (戦略の `over_earnings` と実態の整合)。決算直後 IN の成績 | 保有期間と kessan 発表日の重なり、戦略マスター |
| ③ タイミング | 記録された型 (stage / 需給チャート) 別の成績。高値圏飛びつきの疑い | memo `stage` / `jukyu_chart`、建て日の price_proxy と直前高値 |
| ④ テーマ | 業態テーマ別の損益と集中度 (半導体偏重の効き方) | memo `gyoutai_themes`、損益 |
| ⑤ ポジション管理 | 市場ステート別の建て/決済の分布。調整相場で軽くしたか。損失側の最大建玉は勝ち側より大きくないか | market_db の `state_history` (遷移 30 件のみ保持、範囲外は null)、exposure_log (2026-08-29〜)、`qty_peak` × 価格 |
| ⑥ 規律 | 保有日数と戦略時間軸の整合 (`is_hold_days_consistent`、既存関数)。損切り幅 vs `stop_loss_pct`。同一銘柄の再IN回数 (回転過多)。売却理由のルール内/外 | 戦略の `exit_rule` / `time_horizon`、action_log 売却 reason、fill memo |
| 弱点仮説 | 損失エピソードの保有日数は勝ちより長いか (損切り遅れ)。「なんとなく」IN の頻度と損益 | hold_days の勝敗別分布、自由記述の分類 |

注意: 既存の `strategy_drift` は「遡り取込で fill 指紋が変わり戦略が別の取引を指している疑い」のフラグで、時間軸乖離ではない。データセットでは「要再確認」として母数から外す用途にだけ使う。

注意: 入口側の memo 項目 (`watch_in_reason` / `stage` / `gyoutai_themes` / `inago_origin`) は**銘柄単位の現在値**で、建て日時点の値ではない。6227 のように同一銘柄で 12 ラウンドあれば全ラウンドに同じ値が付く。v1 では「銘柄属性」として扱い、AI にもそう明記して渡す (§2 の月次 JSON 保存で以後は時点値が残る)。

**判断と結果は分けて採点する** (仕様レビュー0704 Part 5): ルール通りの売りで売却後に上がったのは正解のトレード。AI の採点は「良い判断×悪い結果 / 悪い判断×良い結果」の2軸で行い、結果だけで判断を断罪しない。

### 保有PF (portfolio ページ) も同じ rubric で照合する

売買履歴は「何を売ったか」(過去)、保有PFは「何を持ち続けているか」(現在) で、同じ原則の裏表。月末時点の保有PFを同じ6軸で照合し、**1つのレポートに両方を載せる**。portfolio ページには既に材料が揃っている (エクスポージャー評価 #362、出口ライン #386、業態テーマ集計 #283、戦略マスター、stage/需給チャート)。

| 軸 | 保有PFで検証する問い | 使うデータ (すべて既存) |
|---|---|---|
| ① 銘柄選択 | 入口の根拠 (`watch_in_reason`) が空のまま保有している銘柄はどれか | portfolio memo |
| ② リターン源泉 | 次の決算をまたぐ予定の銘柄と、その戦略の `over_earnings` は整合しているか | 次回決算日、戦略マスター |
| ③ タイミング | stage が 3S/4S (後期) のまま残っている銘柄はどれか。出口ライン接近・割れの銘柄 | memo `stage`、exit_line の状態 |
| ④ テーマ | テーマ別の評価額比率と集中度。半導体偏重がどの程度か。テーマ集計の momentum が落ちているテーマに乗り続けていないか | `build_portfolio_theme_summary`、評価額 |
| ⑤ ポジション管理 | 総建玉 / 基準運用額 (レバ実効値) と市場ステートの整合。exposure_log でこの1ヶ月「軽くする局面で軽くしたか」 | exposure 評価、exposure_log、market_db |
| ⑥ 規律 | 保有日数が戦略の時間軸を超えている銘柄 (`is_hold_days_consistent` を保有中に適用)。含み損が `stop_loss_pct` を超えて滞留している銘柄。打診サイズの小口が堆積していないか (#364 の問題意識) | 保有中エピソード、`open_pl`、戦略 `exit_rule`、評価額分布 |

PF 側の出力は「指摘」で止め、**売買提案にはしない**。「今日のアクションキュー」(#372) とは別物で、月1回の構成点検にとどめる。

## 要件

### 1. 投資原則ドキュメント `doc/投資原則.md`

- 上記の自己分析・他己分析・6軸の検証観点・弱点仮説を1ファイルに固定する
- 末尾に **ルール変更履歴** (月次レビューで決めた「変えるルール1つ」を1行ずつ追記)
- git 管理する。ルール変更の履歴が diff でそのまま残るため、#367 の「過去の変えたルールが次回参照できること」はこれで満たす
- 既存の `doc/投資戦略.md` (SPI 分析) は変更せず、原則ドキュメントから参照する

### 2. 振り返りデータセットの生成 (Python、集計のみ)

- `build_review_dataset(year_month)` を追加し JSON を返す。LLM には DB を触らせない (MCP 構想 §3「数値収集は Shintakane、解釈は LLM」と同じ境界)
- 対象: 指定月に決済したエピソード (`last_trade_date` の年月、`split_suspect` は除外) + **実行日時点**の保有中エピソード。過去の月末時点の PF は復元できない (portfolio / memo / 戦略 / 評価額 / 出口ラインはすべて現在値のみ) ので、月次レポートは**翌月初に走らせて当月分を確定する**運用にする。JSON には `generated_at` を持たせ、PF 節は「生成時点の値」と明記する
- 1エピソードの項目 = `build_fill_episodes()` の既存項目 + 判断側の結合:
  - 戦略: `trade_idea` / `time_horizon` / `exit_rule` / `strategy_source`、時間軸整合 (`is_hold_days_consistent`)、要再確認フラグ (`strategy_drift`)
  - 入口: portfolio memo の `watch_in_reason` / `stage` / `jukyu_chart` / `gyoutai_themes`、research レコードの `inago_origin`。**銘柄単位の現在値であり建て日時点の値ではない**ことを JSON に明記する (as_of を持たない)
  - 出口: fill memo (episode_key で一意) + action_log 売却 reason。結合規則: 同一銘柄で timestamp (売買日) が `open_date` 〜 `close_date + 3営業日` に入る売却ログをすべて `sell_logs` に日付付きで列挙する (途中の部分売却の理由も文脈として渡す)。そのうち **`close_date ± 3営業日` の窓に入るものが1件のときだけ `sell_reason` (最終決済の理由) に入れる**。0件は null、2件以上 (同一銘柄の短期再売買) も null にする (AI が誤結合したものを根拠にしないため。列挙は `sell_logs` に残る)
  - 文脈: 建て日・決済日の市場ステート (`state_history` の保持範囲内のみ、範囲外は null)、保有期間中の決算発表日、exposure_log の該当日 (2026-08-29 以降のみ)
- 欠損の扱い: 文脈データは null を許容し、集計の母数は「判定可能なエピソード数」を項目ごとに併記する。古いエピソードほど文脈が欠けるのは仕様で、初回レポートの重心は 2026 年分に置く
- 集計: 戦略別 / 現物・信用別 / 市場ステート別 / テーマ別の勝率・ペイオフ・平均保有日数、勝敗別の hold_days 分布、同一銘柄の再IN回数。月次実現損益 (円) には同月の TOPIX 騰落率を**文脈として併記**するだけで、PF 収益率は定義しない (月初運用額・入出金の記録が無く算出不能。月次絶対額で自分を評価しない、という原則の注意喚起が目的)
- **保有PFスナップショット** (同じ JSON の `portfolio` 節): 1保銘柄ごとに 評価額・PF比率・戦略と時間軸・保有日数・含み損益率・stage・需給チャート・業態テーマ・出口ラインの状態・次回決算日、PF全体として 総建玉/基準運用額・市場ステート・exposure 評価・テーマ別比率。portfolio ダッシュボードが表示に使っている集計関数 (`summarize_hold_positions` 等) をそのまま呼ぶ (表示と分析の数値を一致させる)
- **データセット JSON 自体も月次で保存する** (`$KS_DATA_DIR/trade_review/YYYY-MM.json`)。memo は現在値しか持たないが、翌月初に固めて残せば以後は「前月末近傍の stage/テーマ/戦略」が参照でき、as_of 問題が前向きに解消する。前月 JSON との差分 (新規建て・決済・戦略変更・stage 変化) を AI に渡せる
- 保存した JSON は不可逆資産として扱う: 同名ファイルがあれば**既定で上書きしない** (エラー終了)。再生成は明示の `--overwrite` 時のみ許し、その場合も旧ファイルを `YYYY-MM.json.bak` に退避する。同月内の試し実行は標準出力のみ (保存しない) を既定にする
- CLI: `show_fill_episodes.py --review-json 2026-09` で標準出力へ (既存CLIの拡張、DB非更新)
- テスト: 戦略・売却理由・メモが同じエピソードに結合される / split_suspect が除外される / 売却理由が無いとき null になる / PF 節の評価額合計がダッシュボードの total_value と一致する、を parametrize で 5本以内

### 3. AI 分析スキル `/trade-review` (claude -p、theme-news と同型)

- 入力: `doc/投資原則.md` + §2 の JSON + 前回レポート (あれば)
- 出力の固定構成:
  1. 数字サマリー (戦略別・ステート別。月次実現損益は同月 TOPIX 騰落率を文脈として併記)
  2. 6軸との照合: 各軸の出力状態は **遵守 / 逸脱 / 判定不能 (母数不足)** の3値。遵守・逸脱と判定した軸は **具体エピソード (episode_key) を引用して** 述べ、判定不能の軸は「判定可能 n 件 / 対象 m 件」と欠損の内訳だけを書く (根拠が無いのに判定・引用を強制しない。戦略付与 25%・メモ 3% の現状では初回は判定不能の軸が多くて正常)
  3. 判断×結果の2軸採点 (良判断×悪結果 / 悪判断×良結果 を各1〜3件)
  4. 弱点仮説の検証 (損切り遅れ・なんとなくIN・回転過多・決算またぎ)
  5. **保有PFの原則照合**: 上表の6軸で現在のPFを点検し、該当銘柄を名指しで挙げる (指摘まで。売買提案はしない)。前月 JSON があれば「前月の指摘がどうなったか」を先頭に置く
  6. **記録の空白を埋める問い 3〜5件**: 最も情報量の大きいエピソード (最大損失・戦略乖離・再IN) や、入口根拠が空の保有銘柄を指名し「当時/今の判断は?」と聞く。回答は fill memo / portfolio memo に書く
  7. 「翌月変えるルール1つ」の候補 2〜3個。決めるのは人間
- 禁止事項をスキルに明記: 銘柄推奨をしない / 自由記述が無いエピソードを「感情売り」と断定しない (分類は推定と明記) / 母数不足の軸で傾向を語らない / 月次絶対額で人を評価しない
- 保存: `$KS_DATA_DIR/trade_review/YYYY-MM.md` に不可逆保存 (#365 のバックアップ対象に含める)
- 呼び出しは手動・月1回。銘柄単位の「この取引を評価して」も同じスキルで `--code` 指定できると良いが、必須ではない

### 4. (後続・別issue) MCP tool `get_trade_episodes(code_s)`

§2 の関数の薄いラッパを #426 Phase 2 に載せる。銘柄分析時に LLM が「自分の過去の取引」を参照できる。本 issue では作らない (§2 が関数化されていれば数十行で足りる)。

## 記録側の空白についての方針

- **v1 では記録項目を増やさない**。空白は §3-5 の問いで埋め、ユーザーが fill memo に回答する。分析が記録を生む向きにする (振り返りメモ 3% の現状を、入力欄を増やして解決しようとしない)
- #363 未実装分 (無効化条件・該当した出口の構造化) は、レポートを 2〜3 回回して「自由記述を LLM が分類できない」と分かってから判断する。CSV 取込プレビューの OUT 行に出口種別 select を足す案が最小
