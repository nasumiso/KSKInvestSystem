# issue #419 仕様案: 売買履歴エピソードへの戦略ひもづけと戦略別成績集計

## 1. 目的

売買履歴の本来の目的である「**売買戦略ごとに成績を集計し、今後の投資戦略の参考にする**」
を実現する。現状、戦略 (`trade_idea`) はポートフォリオの銘柄レコードにしか無く、
売買履歴のエピソードとは結びついていない。

## 2. 事前調査でわかった前提 (重要)

実データ (2026-08-26 時点 DB, `build_fill_episodes()` 実測) で検証した。

### 2-1. 規模

| 項目 | 実測値 |
|---|---|
| 総エピソード | 429 (クローズ済 395 / 保有中 34) |
| 銘柄数 | 162 |
| 銘柄あたりエピソード数 | 1件=72銘柄, 2〜3件=52銘柄, 4件以上=38銘柄 (最大14件) |
| 保有日数 | 中央値 16日 / 90%tile 116日 / 最大 394日 / 1日以内が 65件 |
| 損益の偏り | 上位20エピソードで絶対損益の 19.8%、上位50で 36.2% |

### 2-2. PF の trade_idea をコピーするだけでは半分も埋まらない

| | 件数 |
|---|---|
| 売買履歴に出る銘柄 | 162 |
| うち `trade_idea` あり | 57 |
| うち `trade_idea` 無し | 105 (3監 44 / 2準 41 / **PFレコードごと無し 20**) |
| エピソード単位で継承可能 | 189 / 429 (44%) |

売り切った銘柄は 3監/2準 に落ちて `trade_idea` が空、または PF レコードごと消えている。

### 2-3. `trade_idea` は「現在の戦略」1個しか持てない (構造上の制約)

同一銘柄を別戦略で入り直すと後者で上書きされ、過去エピソードの戦略が壊れる。
**よってエピソード側に戦略をコピーして焼き付ける必要がある。参照ではダメ。**

### 2-4. 高回転銘柄は戦略が混在している (一括付与の危険性)

実例:

| 銘柄 | 現 trade_idea | 実際の売買 |
|---|---|---|
| 6227 AIメカテック | 中長期ファンダ | 14件中10件が **0〜7日**の回転。通算 +1,400万円 |
| 2980 SRE | 中期底値リバ | 0〜41日の短期7件 + **322日/184日の長期2件**(損益上位) |
| 4377 ワンキャリア | GARP | 179/185/206日の長期 と 0〜2日の回転が同居 |
| 3496 アズーム | GARP | 91/157/206日 と 0〜2日が同居 |

6227 に「中長期ファンダ」を14件シードすると、**中長期ファンダの平均保有日数が5日になり
戦略定義が崩壊する**。2980 の長期2件を「中期底値リバ」に計上すると、まさに知りたい
「底値リバは短期で刈るべきか」の答えが歪む。

**結論: 銘柄一括付与は、エピソード数が少ない銘柄には有効だが高回転銘柄には使えない。**
ただし 162銘柄中 124銘柄 (76%) はエピソード1〜3件なので、一括付与で安全に片付く。

## 3. 設計

### 3-1. データモデル: エピソードに戦略を焼き付ける

既存の `fill_memo` と同じ `episode_key` 機構 (`code_s|kind|first_seq`) に相乗りする。
`first_seq` は建玉開始時に確定し以後不変なので、保有中に付けた値が売却後も追える。

```
episode_strategy:<episode_key>  ->  {
    "episode_key": str,
    "trade_idea": str,          # 戦略名 (必ず非空。マスター登録済みの名前)
    "source": "seed" | "manual",  # 機械シードか人が確認したか
    "updated_at": iso8601,
}
```

**不変条件: 「未分類 = キーが存在しない」の1通りだけ。**
`trade_idea=""` のレコードは**保存しない**。`set_episode_strategy` に空文字を渡したら
保存ではなく**キー削除**とする (既存 `set_fill_memo` が空文字を削除扱いにするのと同じ形,
`portfolio_shelve.py:1247`)。

理由: 未分類の表現が「キーなし」と「`trade_idea=""` + `source="manual"`」の2通りあると、
後者はレイヤー2の一括付与 (未設定のみ埋める) から漏れ、**二度と一括付与で拾えない
エピソードが生まれる**。個別UIのクリア操作・マスター削除カスケードなど複数経路から
この状態を作れてしまうため、入口の `set_episode_strategy` で1通りに正規化する。

`source` を持つ理由: 「seed のまま = 機械が矛盾なしと判断しただけの値」と
「manual = 人が確認した値」を区別し、後から精度の議論をできるようにする。

`portfolio_shelve.py` に `get_episode_strategy` / `set_episode_strategy` /
`list_episode_strategies` を追加 (既存 fill_memo 3関数と同じ形)。

### 3-1-1. 値の検証: マスター登録済みのみ許可 (record と同じ厳しさ)

`set_episode_strategy` は `fill_memo` と同型の API だが、**値検証は fill_memo (自由文字列)
ではなく `update_memo` の `trade_idea` 検証に合わせる** (`portfolio_shelve.py:2916` 相当)。

- 空文字は「未分類に戻す」= **キー削除**として扱う (3-1 の不変条件。保存はしない)
- 空文字以外は**戦略マスター登録済みの名前のみ許可**。未登録値は `ValueError`
- ただし**現にそのエピソードに入っている値と同じなら許容** (旧値の救済。record 側と同じ考え方)

これを入れないと、移行スクリプトやルート経由で任意文字列が混入し、戦略別集計が
静かに汚染される。fill_memo が自由文字列なのは「振り返りメモ」だからであって、
`episode_strategy` は集計キーなので同列に扱ってはいけない。

### 3-1-2. 戦略マスターの rename / delete への追従

現行仕様では、戦略マスターのリネーム・削除は全 record の `memo[trade_idea]` を
追従・クリアする (`_rewrite_trade_idea_in_records`, `portfolio_shelve.py:2755`)。
`episode_strategy` も**同じ挙動に揃える**。

| マスター操作 | record (既存) | episode_strategy (新規) |
|---|---|---|
| rename (旧名→新名) | 全 record を新名に書き換え | **同様に全エピソードを新名に書き換え (cascade)** |
| delete | 全 record の trade_idea を空文字にリセット | **エピソードのキー自体を削除する** (下記) |

**rename を cascade する理由**: 戦略名は集計の表示ラベルであり、実体は「同じ戦略」。
旧名のまま残すと、戦略別テーブルに旧名と新名が別行で並び、成績が分断される。

**delete はキーごと削除する**: 3-1 の不変条件「未分類 = キーなし」の帰結。
`trade_idea=""` を残すとレイヤー2の一括付与から漏れ、削除後の再分類フローが壊れる。

**delete で未分類に落とす理由**: 「履歴は immutable に残す」案も検討したが、
削除された戦略が集計テーブルに残り続けると、マスターに無い戦略の成績が
表示され UI が不整合になる。record 側が既にリセット方式なので、そちらに揃えるのが
一貫性の面でも正しい。**削除は破壊的**なので、UI 側で
「この戦略が付いた N 件のエピソードが未分類に戻ります」と件数を出して確認する。

実装は `_rewrite_trade_idea_in_records` と対になる
`_rewrite_trade_idea_in_episodes(db, old_name, new_name)` を追加し、
`update_trade_idea` / `delete_trade_idea` の中で同じトランザクション内から呼ぶ。
**別トランザクションにすると record だけ書き換わってエピソードが取り残される**ので、
必ず同一の `_flock` 内で行う。

### 3-2. レイヤー1: 初回一括シード (time_horizon 足切りつき)

現在の `trade_idea` を、その銘柄の**未設定**エピソードにコピーする。
ただし**保有日数が戦略の `time_horizon` と矛盾するものはシードしない**。

| time_horizon | シードする保有日数 |
|---|---|
| 短期 | ≤ 20日 |
| 中期 | 10〜180日 |
| 中長期 / 長期 | ≥ 30日 |
| 恒常 | 制限なし |

保有中エピソード (close_date なし) は日数判定できないので素通しでシードする。

**足切りを入れる理由**: この機能の目的は「戦略ごとの成績を見て投資判断に使う」こと。
**汚れたデータで出した集計は空欄より有害**である。空欄なら「まだ分からない」と分かるが、
汚れた集計は誤った確信を生む。

**シード実効率 (実測シミュレーション済み)**:

| | 件数 |
|---|---|
| シード成立 | 115 (うち保有中素通し 33) |
| 足切りで却下 → 未分類のまま | 74 |
| そもそも戦略なし | 240 |
| **自動充填率** | **26.8%** |

却下内訳: GARP 21, 中期テーマ 18, 中長期ファンダ 14, 中期底値リバ 6, 他。
足切りなしなら 44% だが、却下された74件はまさに 2-4 の汚染源なので却下が正しい。

実行は一度きりの移行スクリプト (`migrate_seed_episode_strategy.py`) とし、
`--dry-run` で件数を確認してから流す。**未設定のみ対象**なので再実行安全。

### 3-3. レイヤー2: 銘柄単位の一括付与

銘柄行 (`build_stock_rollups`) に戦略コンボボックスを置き、
「この銘柄の**未設定**エピソード全部に戦略Xを付ける」を1操作で行う。

- **未設定のみ埋める**。個別設定済み (source=manual) は触らない → 再実行安全、手動修正が壊れない
- **保有日数のばらつき警告**: その銘柄のエピソードが「短期(≤10日)」と「中長期(≥30日)」に
  跨る場合、「保有期間が大きく異なるエピソードを含みます。個別付与を推奨」と表示する。
  **一括を禁止はせず注意を促すに留める** (判断はユーザー)

### 3-4. レイヤー3: 個別上書き

エピソード行の戦略コンボボックスで個別に設定 (`source="manual"`)。
同一銘柄で戦略を変えて入り直したケースはここで直す。

### 3-5. 埋める順序を機械が指示する (重要)

「未設定エピソードを**絶対損益の降順**で並べる」フィルタを用意する。
上位50件を潰せば分析精度の 36.2% が確保できる (2-1 の偏り実測より)。

ユーザーが「面倒」と感じた原因は件数そのものではなく、
**どれを埋めれば意味があるか分からないまま429件と向き合った**ことにある。ここが効く。

### 3-6. 戦略別成績テーブル

`calc_trade_summary` を戦略別に呼ぶ。表示仕様:

- 戦略行を上部に、**未分類は区切り線で分離して下部**に配置
- 未分類も**母数と損益合計は表示する** (集計に含める) が、勝率・平均損益など
  比較指標は薄いグレーにし「比較対象ではない」ことを示す
- 未分類の絶対損益シェアが 20% を超える間は、テーブル上部に
  「未分類が N件 / 損益シェア X% あります。戦略別比較の精度は限定的です」と警告

## 4. 実装順序と検証ポイント

| # | 内容 | 検証 |
|---|---|---|
| 1 | `portfolio_shelve` に episode_strategy の get/set/list + マスター登録値検証 + 空文字はキー削除 | `pytest tests/test_portfolio_shelve.py` |
| 1b | rename/delete の episode_strategy への cascade | 同上。rename後に旧名が残らないこと、delete後に一括付与で再分類できること |
| 2 | 移行スクリプト (足切りシード) + `--dry-run` | dry-run で 115件シード / 74件却下を確認 |
| 3 | エピソード行・銘柄行のコンボボックス (レイヤー2/3) | ブラウザ確認。一括→個別→一括で手動値が壊れないこと |
| 4 | 未設定を絶対損益降順で並べるフィルタ | ブラウザ確認 |
| 5 | 戦略別成績テーブル (未分類を下部に分離) | ブラウザ確認 |

テストは `episode_strategy` の CRUD + マスター未登録値の拒否 + 空文字でキーが消えること + rename cascade +
delete後に一括付与で再分類できること +
足切り判定 + 一括付与が manual を壊さないこと、を parametrize で 5本以内に集約する。

## 5. 副次的な価値 (実装外の気づき)

6227 は現 `trade_idea`「中長期ファンダ」でありながら実際は短期回転14件で
通算 +1,400万円ほど出ている。**戦略と実際の売買行動が乖離している典型例**で、
この機能が完成すると乖離自体が可視化される。おそらくそれが一番の価値になる。

## 6. スコープ外

- 保有日数からの戦略**自動推定** (16日以内なら短期、等)。
  戦略は「入る時の意図」であって「結果の保有期間」ではない。中期モメンタムで入って
  3日で損切りしたものを「短期」に分類すると、知りたい答えが歪む。
  未設定エピソードの**サジェスト初期値**としてなら害はないが、今回は入れない。
- `trade_idea` 自体の履歴管理 (いつ戦略を変えたかの記録)。
