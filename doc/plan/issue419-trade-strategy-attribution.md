# issue #419 仕様案: 売買履歴エピソードへの戦略ひもづけと戦略別成績集計

## 1. 目的

売買履歴の本来の目的である「**売買戦略ごとに成績を集計し、今後の投資戦略の参考にする**」
を実現する。現状、戦略 (`trade_idea`) はポートフォリオの銘柄レコードにしか無く、
売買履歴のエピソードとは結びついていない。

## 2. 事前調査でわかった前提 (重要)

実データで検証した。数値は 2026-08-31 時点 DB (`build_fill_episodes()` 実測)。

### 2-1. 規模

| 項目 | 実測値 |
|---|---|
| 総エピソード | 434 (クローズ済 399 / 保有中 35) |
| 銘柄数 | 162 |
| 銘柄あたりエピソード数 | 1件=72銘柄, 2〜3件=52銘柄, 4件以上=38銘柄 (最大14件) |
| 保有日数 | 中央値 16日 / 90%tile 116日 / 最大 394日 / 1日以内が 65件 |
| 損益の偏り | 上位20エピソードで絶対損益の 19.8%、上位50で 36.2% |

### 2-2. PF の trade_idea をコピーするだけでは半分も埋まらない

| | 件数 |
|---|---|
| 売買履歴に出る銘柄 | 162 |
| うち `trade_idea` あり | 57 |
| うち `trade_idea` 無し | 105 (3監 44 / 2準 41 / **PFレコードごと無し 20**) |
| エピソード単位で継承可能 | 194 / 434 (44.7%) |

売り切った銘柄は 3監/2準 に落ちて `trade_idea` が空、または PF レコードごと消えている。

### 2-3. `trade_idea` は「現在の戦略」1個しか持てない (構造上の制約)

同一銘柄を別戦略で入り直すと後者で上書きされ、過去エピソードの戦略が壊れる。
**よってエピソード側に戦略をコピーして焼き付ける必要がある。参照ではダメ。**

### 2-4. 高回転銘柄は戦略が混在している (一括付与の危険性)

実例:

| 銘柄 | 現 trade_idea | 実際の売買 |
|---|---|---|
| 6227 AIメカテック | 中長期ファンダ | 14件中10件が **0〜7日**の回転。通算 +1,400万円 |
| 2980 SRE | 中期底値リバ | 0〜41日の短期7件 + **322日/184日の長期2件**(損益上位) |
| 4377 ワンキャリア | GARP | 179/185/206日の長期 と 0〜2日の回転が同居 |
| 3496 アズーム | GARP | 91/157/206日 と 0〜2日が同居 |

6227 に「中長期ファンダ」を14件シードすると、**中長期ファンダの平均保有日数が5日になり
戦略定義が崩壊する**。2980 の長期2件を「中期底値リバ」に計上すると、まさに知りたい
「底値リバは短期で刈るべきか」の答えが歪む。

**結論: 銘柄一括付与は、エピソード数が少ない銘柄には有効だが高回転銘柄には使えない。**
ただし 162銘柄中 124銘柄 (76%) はエピソード1〜3件なので、一括付与で安全に片付く。

## 3. 設計

### 3-1. データモデル: エピソードに戦略を焼き付ける

既存の `fill_memo` と同じ `episode_key` 機構 (`code_s|kind|first_seq`) に相乗りする。
`first_seq` は建玉開始時に確定し以後不変なので、保有中に付けた値が売却後も追える。

```
episode_strategy:<episode_key>  ->  {
    "episode_key": str,
    "trade_idea": str,          # 戦略名 (必ず非空。マスター登録済みの名前)
    "source": "seed" | "manual",  # 機械シードか人が確認したか
    "updated_at": iso8601,
}
```

#### episode_key の安定性の限界 (既知の制約として明記する)

`first_seq` を「建玉開始時に確定し以後不変」と書いたが、**厳密には不変ではない**。
`seq` は約定日順ではなく**取込順**の追番であり (`_next_fill_seq`,
`portfolio_shelve.py:1118`)、エピソードは `trade_date` 昇順に並べ直したうえで
そのラウンドに属する fill の `min(seq)` を `first_seq` とする
(`helpers.py:5005`, `helpers.py:5737`)。

**実測: 434エピソード中 88件 (20.3%) で「約定日順の先頭 fill の seq」と
`min(seq)` が既に一致していない。** 遡り取込 (期首持越しの補完、証券会社CSVの
期間分割取込) が現に起きているため。

影響: 過去約定の後追い取込で**ラウンドの区切りが変わる**と、`first_seq` が変化し
既存の戦略ひもづけが別エピソードにずれる、または迷子になる。
これは既存の `fill_memo` が元から抱えている弱点だが、`episode_strategy` は
**成績集計の基礎データ**になるぶん影響が大きい。

ずれ方は2通りあり、**性質が違うので検出経路も分ける**:

| # | ずれ方 | 性質 | 検出経路 |
|---|---|---|---|
| A | 旧キーがどの現存エピソードにも対応しなくなる (orphan) | **保存レコード側の異常**。対応するエピソードが無いので、エピソードに印を立てられない | 保存レコードを全走査する**別スキャン** |
| B | 旧キーが生き残ったまま、別の中身のエピソードを指す | **エピソード側の属性**。現キーにレコードはあるが中身が変わった | 読み取り経路で指紋照合 |

B は「ラウンド分割が変わったが `min(seq)` はたまたま同じ」ケース。戦略が
静かに誤ったエピソードへ乗り換わり、集計が汚染されても検出されない。

**A を「エピソードの属性」として扱えない点に注意**: orphan は参照先のエピソードが
存在しないため `ep["strategy_drift"]` を立てる相手がいない。エピソード側から見ると
単に「未分類」に見えるだけで、要再確認バケットにも入らない。よって A は
**エピソード一覧とは別に、保存レコードを走査して件数を出す警告**として実装する
(下記)。

**今回の対処方針 (実装する)**: 保存時に**エピソードの指紋を一緒に焼き付ける**。

```
episode_strategy:<episode_key>  ->  {
    ...,
    "fingerprint": "<sha1(fill の seq 列)の先頭12桁>" | None,
}
```

指紋は**そのエピソードに属する fill の seq を約定日順に並べた列のハッシュ**とする。

`open_date|head_seq` では不十分。**1エピソードが backdated fill で2つに分裂した場合、
先頭側のエピソードは `open_date` も先頭 fill の seq も元のまま残りうる**ため、
中身が変わったのに指紋が一致してしまう。fill の seq 列なら、分裂で fill が抜ければ
必ず変化する。

**指紋はクローズ済みエピソードにのみ焼き付ける (保有中は `None`)。**

保有中エピソードは買い増し・部分利確のたびに seq 列が伸びるのが**正常動作**なので、
そこに指紋を突き合わせると次の約定で必ず不一致になり、要再確認が大量発生して
運用不能になる。保有中は「まだ姿が確定していない」ので同一性検査の対象外とする。

具体的な扱い:

| エピソードの状態 | 保存時 | 読み取り時の検査 |
|---|---|---|
| 保有中 | `fingerprint = None` | **検査しない** |
| クローズ済み | seq 列ハッシュを保存 | 保存値と再計算値を比較 |
| 保有中に付与 → 後でクローズ | `None` のまま | **初回クローズ時に指紋を確定保存** (不一致にはしない) |

3行目が要点: 保有中に戦略を付けたエピソードは、クローズが確定した時点で
初めて指紋を焼き付ける。`None` を「まだ確定していない」の意味で使うことで、
正常な進行と遡り取込によるズレを区別できる。

#### 指紋を「いつ・どこで」永続化するか (書き込み経路を1箇所に固定する)

判定は読み取り経路に置くが、**`build_fill_episodes()` に保存副作用を持たせない**。
これは UI・CLI・移行スクリプトから広く呼ばれる純粋な read helper であり、
ここで DB を書くと画面表示や集計が書き込みトリガーになる (並行アクセス・
`--dry-run` の副作用など、事故の温床)。

指紋が保存される経路は2つ。**付与時に確定できるならその場で焼く**のが基本で、
取込後の seal はそれを補完する。

**(1) 付与時 — `set_episode_strategy(episode_key, trade_idea, fingerprint=None)`**

呼び出し側 (UI ルート・移行スクリプト) は、対象エピソードが**クローズ済みなら
その時点の指紋を計算して渡す**。保有中なら `None` を渡す。

**この機能の主経路は「既にクローズ済みの過去エピソードへの後付け」** (レイヤー2/3の
UI 操作、レイヤー1の移行スクリプト) であり、その場合は付与時点で既に姿が確定して
いるのだから、その場で焼くのが素直。ここを取込待ちにすると、**その後たまたま新しい
fill が来なければ指紋が永久に `None` = drift 検知が永久に効かない**。

指紋の計算は呼び出し側が持つエピソード情報 (`ep["fills"]`) から行う。
`portfolio_shelve` 側にエピソード再構成を持ち込まない (依存の向きを保つ)。

**(2) 取込後 — `seal_episode_fingerprints()`**

(1) で取りこぼす「**保有中に付与 → 後でクローズ**」を埋める。

```
seal_episode_fingerprints(db_path=None) -> int   # portfolio_shelve に追加
```

- クローズ済み **かつ** `episode_strategy` が存在し **かつ** `fingerprint is None`
  のエピソードだけを対象に、指紋を計算して保存する
- 既に指紋があるレコードは**触らない** (上書きすると drift 検知が無効化される)
- 冪等。何度流しても結果は同じ

2経路あるが**書き込む条件は同じ** (「クローズ済み かつ 指紋が未設定」) なので、
どちらが先に走っても結果は変わらない。

呼び出し元は3つの fill 取込 CLI (`import_rakuten_fills.py` /
`import_sbi_fills.py` / `import_monex_fills.py`)。いずれも `append_fill` で
fill を書き込んだ直後に呼ぶ。**エピソードの姿が変わりうるのは fill が増えた時だけ**
なので、ここが唯一の適切なタイミングになる。

この2経路で、「クローズ済みへの後付け」(1) と「保有中に付与→後でクローズ」(2) の
両方が塞がる。取込を経ずに手で DB をいじった場合に備え、移行スクリプトの `--seal`
でも (2) を叩けるようにしておく。

**実測で クローズ済み399件全件、seq 列ハッシュは重複なし。**

**B の判定は読み取り経路で毎回行う** (手動 CLI 運用にはしない)。
`build_fill_episodes()` が戦略を紐付ける際、クローズ済みエピソードについて
その場で seq 列から指紋を再計算し、保存値と突き合わせて
`ep["strategy_drift"] = True/False` を立てる。指紋計算は既にメモリ上にある
fill 列の走査だけで、追加の DB アクセスは要らない。

**A (orphan) も同じ読み取り経路で数える。** `build_fill_episodes()` は
`list_episode_strategies()` で保存レコードを一括取得するので、
**現存エピソードのキー集合に含まれない保存キーを数える**だけで orphan 件数が出る
(追加コストなし)。これは個々のエピソードには紐付かないため、
**画面レベルの警告「対応先を失った戦略ひもづけが N件あります」**として出す。

**人が CLI を流し忘れた瞬間に汚染される設計にはしない。** 判定を読み取り側に置けば、
UI・集計・CLI のどの経路から来ても同じ結論になり、取込後の手作業に依存しない。

移行スクリプトの `--check-drift` は、この判定結果を**一覧で確認するための表示手段**
として用意する (判定そのものの置き場ではない)。orphan については、
どのキーが迷子かを表示して人が再付与の手がかりにできるようにする。

自動での付け替え・自動失効は**しない**。ずれた先が正しい対応かを機械が判定できず、
誤った付け替えは「気づけない汚染」になるため (#424 が案Dを退けたのと同じ理由)。
**検出して人に出すところまで**を実装し、再付与は人がレイヤー2/3で行う。

**drift 検出後の集計上の扱い**: 指紋不一致 (B) のエピソードは
**戦略別比較の母数から外し、「要再確認」バケットに退避する**。
orphan (A) はそもそも現存エピソードに紐付かないため、集計上は
該当エピソードが「未分類」に入るだけで、別途の退避は不要 (警告のみ)。
戦略がずれている可能性がある以上、その戦略の勝率・期待値・平均保有日数に
混ぜてはいけない (これは 3-2 の「汚れた集計は空欄より有害」と同じ判断)。

一方で**全体サマリーの損益合計・母数からは外さない**。エピソード自体は実在し
損益も正しいため、外すと既存サマリーと一致しなくなる。

つまり「全体 totals には含める / 戦略別比較からは外す」と分ける。未分類と同じく
テーブル下部に区切って件数と損益合計を出し、`--check-drift` が0でない間は
テーブル上部に「要再確認 N件」の警告を出す。

**不変条件: 「未分類 = キーが存在しない」の1通りだけ。**
`trade_idea=""` のレコードは**保存しない**。`set_episode_strategy` に空文字を渡したら
保存ではなく**キー削除**とする (既存 `set_fill_memo` が空文字を削除扱いにするのと同じ形,
`portfolio_shelve.py:1231`)。

理由: 未分類の表現が「キーなし」と「`trade_idea=""` + `source="manual"`」の2通りあると、
後者はレイヤー2の一括付与 (未設定のみ埋める) から漏れ、**二度と一括付与で拾えない
エピソードが生まれる**。個別UIのクリア操作・マスター削除カスケードなど複数経路から
この状態を作れてしまうため、入口の `set_episode_strategy` で1通りに正規化する。

`source` を持つ理由: 「seed のまま = 機械が矛盾なしと判断しただけの値」と
「manual = 人が確認した値」を区別し、後から精度の議論をできるようにする。

`portfolio_shelve.py` に `get_episode_strategy` / `set_episode_strategy` /
`list_episode_strategies` を追加 (既存 fill_memo 3関数と同じ形)。

### 3-1-1. 値の検証: マスター登録済みのみ許可 (record と同じ厳しさ)

`set_episode_strategy` は `fill_memo` と同型の API だが、**値検証は fill_memo (自由文字列)
ではなく `update_memo` の `trade_idea` 検証に合わせる** (`portfolio_shelve.py:3098` 相当)。

- 空文字は「未分類に戻す」= **キー削除**として扱う (3-1 の不変条件。保存はしない)
- 空文字以外は**戦略マスター登録済みの名前のみ許可**。未登録値は `ValueError`
- ただし**現にそのエピソードに入っている値と同じなら許容** (旧値の救済。record 側と同じ考え方)

これを入れないと、移行スクリプトやルート経由で任意文字列が混入し、戦略別集計が
静かに汚染される。fill_memo が自由文字列なのは「振り返りメモ」だからであって、
`episode_strategy` は集計キーなので同列に扱ってはいけない。

### 3-1-2. 戦略マスターの rename / delete への追従

現行仕様では、戦略マスターのリネーム・削除は全 record の `memo[trade_idea]` を
追従・クリアする (`_rewrite_trade_idea_in_records`, `portfolio_shelve.py:2937`)。
`episode_strategy` も**同じ挙動に揃える**。

| マスター操作 | record (既存) | episode_strategy (新規) |
|---|---|---|
| rename (旧名→新名) | 全 record を新名に書き換え | **同様に全エピソードを新名に書き換え (cascade)** |
| delete | 全 record の trade_idea を空文字にリセット | **エピソードのキー自体を削除する** (下記) |
| time_horizon 変更 | (影響なし) | **`source=seed` を再評価し、矛盾するものはキー削除** (3-2 参照) |

**rename を cascade する理由**: 戦略名は集計の表示ラベルであり、実体は「同じ戦略」。
旧名のまま残すと、戦略別テーブルに旧名と新名が別行で並び、成績が分断される。

**delete はキーごと削除する**: 3-1 の不変条件「未分類 = キーなし」の帰結。
`trade_idea=""` を残すとレイヤー2の一括付与から漏れ、削除後の再分類フローが壊れる。

**delete で未分類に落とす理由**: 「履歴は immutable に残す」案も検討したが、
削除された戦略が集計テーブルに残り続けると、マスターに無い戦略の成績が
表示され UI が不整合になる。record 側が既にリセット方式なので、そちらに揃えるのが
一貫性の面でも正しい。**削除は破壊的**なので、UI 側で
「この戦略が付いた N 件のエピソードが未分類に戻ります」と件数を出して確認する。

実装は `_rewrite_trade_idea_in_records` と対になる
`_rewrite_trade_idea_in_episodes(db, old_name, new_name)` を追加し、
`update_trade_idea` / `delete_trade_idea` の中で同じトランザクション内から呼ぶ。
**別トランザクションにすると record だけ書き換わってエピソードが取り残される**ので、
必ず同一の `_flock` 内で行う。

### 3-2. レイヤー1: 初回一括シード (time_horizon 足切りつき)

現在の `trade_idea` を、その銘柄の**未設定**エピソードにコピーする。
ただし**保有日数が戦略の `time_horizon` と矛盾するものはシードしない**。

| time_horizon | シードする保有日数 |
|---|---|
| 短期 | ≤ 20日 |
| 中期 | 10〜180日 |
| 中長期 / 長期 | ≥ 30日 |
| 恒常 | 制限なし |

保有中エピソード (close_date なし) は日数判定できないので素通しでシードする
(実測 34件)。ただし**素通しは「保留」であって「合格」ではない** — 下記のとおり
クローズ時に足切りを再評価する。

#### 保有中に素通しシードした分は、クローズ時に足切りを再評価する

素通しのまま放置すると、「今は判定できない」34件が 2日で閉じても 200日で閉じても
無条件に戦略別成績へ入る。これは**足切りを入れた理由そのものと矛盾する**
(汚れた集計は空欄より有害)。

そこで `seal_episode_fingerprints()` (指紋確定と同じタイミング = クローズ確定時) で、
`source == "seed"` のレコードに限り **time_horizon 足切りを再評価**する:

- 保有日数が矛盾しなければ → そのまま維持し、指紋を確定
- 矛盾したら → **キーを削除して未分類に戻す** (3-1 の不変条件どおり)。
  レイヤー2/3 で人が付け直せる状態になる

`source == "manual"` は**再評価しない**。人が確認して付けた値を機械が覆さない
(レイヤー2/3 が一括付与で manual を壊さないのと同じ原則)。

#### time_horizon 自体が変更されたときも再評価する

足切りの基準である `time_horizon` は、戦略マスター編集 (`update_trade_idea`) で
**後から変更できる**。「中期 (10〜180日)」を「短期 (≤20日)」に直すと、既に確定済みの
`source=seed` が新しい定義と矛盾するが、シード時・クローズ時のどちらの経路も
通らないため再評価されない。

そこで **`update_trade_idea` で `time_horizon` が変わった場合、その戦略が付いた
`source == "seed"` のエピソードを再評価し、矛盾するものはキー削除して未分類に戻す**。
rename/delete のカスケード (3-1-2) と**同じトランザクション内**で行う。

`source == "manual"` は変更しない (人が確認した値を機械が覆さない、の原則)。
UI では削除時と同様に「N件が未分類に戻ります」と件数を出して確認する。

これで `source=seed` の値は、シード時・クローズ時・戦略定義の変更時の3経路すべてで
time_horizon と整合していることが保証される。

**足切りを入れる理由**: この機能の目的は「戦略ごとの成績を見て投資判断に使う」こと。
**汚れたデータで出した集計は空欄より有害**である。空欄なら「まだ分からない」と分かるが、
汚れた集計は誤った確信を生む。

**シード実効率 (実測シミュレーション済み)**:

| | 件数 |
|---|---|
| シード成立 | 119 (うち保有中素通し 34) |
| 足切りで却下 → 未分類のまま | 75 |
| そもそも戦略なし | 240 |
| **自動充填率** | **27.4%** |

却下内訳: GARP 21, 中長期ファンダ 19, 中期テーマ 14, 中期底値リバ 6, 短期イベント 5, 中期モメンタム 5, 他。
足切りなしなら 44.7% だが、却下された75件はまさに 2-4 の汚染源なので却下が正しい。

実行は一度きりの移行スクリプト (`migrate_seed_episode_strategy.py`) とし、
`--dry-run` で件数を確認してから流す。**未設定のみ対象**なので再実行安全。

### 3-3. レイヤー2: 銘柄単位の一括付与

銘柄行 (`build_stock_rollups`) に戦略コンボボックスを置き、
「この銘柄の**未設定**エピソード全部に戦略Xを付ける」を1操作で行う。

- **未設定のみ埋める**。個別設定済み (source=manual) は触らない → 再実行安全、手動修正が壊れない
- **保有日数のばらつき警告**: その銘柄のエピソードが「短期(≤10日)」と「中長期(≥30日)」に
  跨る場合、「保有期間が大きく異なるエピソードを含みます。個別付与を推奨」と表示する。
  **一括を禁止はせず注意を促すに留める** (判断はユーザー)

### 3-4. レイヤー3: 個別上書き

エピソード行の戦略コンボボックスで個別に設定 (`source="manual"`)。
同一銘柄で戦略を変えて入り直したケースはここで直す。

### 3-5. 埋める順序を機械が指示する (重要)

「未設定エピソードを**絶対損益の降順**で並べる」フィルタを用意する。
上位50件を潰せば分析精度の 36.2% が確保できる (2-1 の偏り実測より)。

ユーザーが「面倒」と感じた原因は件数そのものではなく、
**どれを埋めれば意味があるか分からないまま434件と向き合った**ことにある。ここが効く。

### 3-6. 戦略別成績テーブル

`calc_trade_summary` を戦略別に呼ぶ。

**母数定義は既存 `_summarize_fill_episodes` と完全に揃える** — すなわち
`split_suspect` (分割・併合の疑いだが未換算, issue #398) のエピソードを
**戦略別集計からも除外する** (`trade_history.py:154`)。除外を継承しないと、
損益が壊れていると既知のエピソードが戦略成績に再混入し、比較表が壊れる。
実装上は `_summarize_fill_episodes` と同じ「先に `split_suspect` を落として
から戦略でグループ化する」順序にし、母数定義を二重に持たない。

表示仕様:

- 戦略行を上部に、**未分類と「要再確認」(drift 検出分, 3-1 参照) は区切り線で
  分離して下部**に配置。どちらも戦略別比較の母数には入れない
- 未分類も**母数と損益合計は表示する** (集計に含める) が、勝率・平均損益など
  比較指標は薄いグレーにし「比較対象ではない」ことを示す
- 未分類の絶対損益シェアが 20% を超える間は、テーブル上部に
  「未分類が N件 / 損益シェア X% あります。戦略別比較の精度は限定的です」と警告

## 4. 実装順序と検証ポイント

| # | 内容 | 検証 |
|---|---|---|
| 1 | `portfolio_shelve` に episode_strategy の get/set/list + マスター登録値検証 + 空文字はキー削除 + `set_episode_strategy(..., fingerprint=)` | `pytest tests/test_portfolio_shelve.py` |

| 2 | 移行スクリプト (足切りシード) + `--dry-run` + `--check-drift` | dry-run で 119件シード / 75件却下を確認。orphan・指紋不一致の両方を一覧表示できること |

テストは `episode_strategy` の CRUD + マスター未登録値の拒否 + 空文字でキーが消えること + rename cascade +
delete後に一括付与で再分類できること + 足切り判定 + 一括付与が manual を壊さないこと +

## 7. issue #424 (往復行メモ) とのキー設計競合の検討 (2026-08-31 追記)

issue #419 のコメントで「#424 と行キー・保存レイヤーが競合するので着手前に決めよ」との
指摘があった。実データで検証した結果、**競合しない**と結論する。以下が根拠。

### 7-1. 往復行は集計母数になれない (実測)

戦略別成績は「戦略ごとの損益を合算する」機能なので、付与先は損益を漏れなく持つ粒度で
なければならない。往復行はこれを満たさない。

| | 実測値 (2026-08-31 DB) |
|---|---|
| 決済済み往復行 | 780 |
| うち **pl が算出できない行** | **72 (9.2%)** — うち現引 48 |
| pl 欠損行を含むエピソード | 11 |
| その11エピソードの損益 | **3,095,044円** (実現損益合計 8,686,085円の **35.6%**) |

往復行の pl を単純合算するとエピソード単位の実現損益と **3,095,044円ずれる**。
建玉を特定できない決済 (期首持越し・建情報なしの信用返済) と現引は、行としては
存在するが損益を持てないため。

対してエピソード単位の pl は `settle_pl` ベースで欠損なく積まれており、
`_summarize_fill_episodes` / `build_stock_rollups` の既存集計 (実現損益・勝率・期待値) と
**厳密に一致する**ことがコード上保証されている (helpers.py:5634 のコメント)。

**よって戦略はエピソードに付ける。往復行に付けると成績集計が 35.6% ずれる。**

### 7-2. 「往復行単位なら混在問題が解ける」は 6.9% にしか効かない

コメントは「高回転銘柄の戦略混在は往復行と同じ粒度の話」とするが、実測すると
混在が起きるエピソードは限定的。

| | 実測値 |
|---|---|
| 全エピソード | 434 |
| エピソード内に決済往復行が2件以上 | 157 |
| うち短期(≤10日)と中長期(≥30日)が**同居** | **30 (全体の 6.9%)** |

issue 本文が挙げた 6227 / 2980 / 4377 の混在は、**エピソード内**ではなく
**エピソード間** (同じ銘柄で建玉が0に戻ってから入り直した別ラウンド) の混在である。
これはエピソード単位の付与で解ける — レイヤー3の個別上書きがまさにその手当て。

残る 6.9% は「1ラウンド内で短期回転と長期保有が混ざる」ケースだが、これは
**そもそも1つの建玉ラウンドで複数の意図が動いた**ケースで、往復行に戦略を付けても
「どの往復行がどの意図だったか」を人が判定する作業量は変わらない。

### 7-3. キーは競合しない (レイヤーが別)

- `episode_strategy:<episode_key>` — **エピソード単位** (`code_s|kind|first_seq`)
- #424 の往復行メモ — **往復行単位** (#424 側でキー設計を決める)

両者は別プレフィックスの別レコードで、共有も相互参照もしない。#424 が A/B/C 案の
どれを選んでも `episode_strategy` に影響しない。**#424 のキー設計を待つ必要はない。**

なお #424 が難航している「遡り取込でキーがずれる」問題は、程度の差はあれ
**エピソードキーにも存在する** (3-1 の安定性の限界を参照。実測 20.3%)。
ただし往復行では「FIFO の充当先が変わって別の取引になる」= 誤対応に気づけないのに対し、
エピソードでは指紋 (fill の seq 列ハッシュ) を焼き付けることで機械的に気づけるため、
実装可能な手当てがある。
これが「#419 は先行できるが #424 は設計を決めきる必要がある」の差。
#419 を #424 に従属させると、解く必要のない問題の解決を待つことになる。

### 7-4. 結論

**#419 はエピソード単位で先行実装してよい。** 3〜6節の設計を変更しない。
