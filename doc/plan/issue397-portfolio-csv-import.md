# issue #397 仕様案: ポートフォリオCSV取込による qty / 保有ステータス自動反映

## 1. 目的

保有ステータス・保有株数の手入力をやめ、証券会社のポートフォリオCSV (残高一覧) を
真実源として差分を自動反映する。issue #397 の当初案 (案2: ズレ検知して警告表示) を
「検知して人が直す」から「取り込んで機械が直す」へ格上げする。

## 2. 事前調査でわかった前提 (重要)

実データ (`assetbalance(all)_20260809_170105.csv`, 2026-08-09 時点 DB) で検証した結果、
**当初イメージした「CSV = 全保有の真実源」は成立しない。**

### 2-0. 楽天は現物・信用の2ファイルで揃う (2026-08-10 検証済み)

楽天は **現物と信用で別CSV**。2ファイル揃えれば楽天分の保有は完全に再現できる。

| ファイル | 内容 | 出力元 |
|---|---|---|
| `assetbalance(all)_*.csv` | 現物 (国内株/米国株/預り金) | マイメニュー > 保有商品一覧（すべて）> CSVで保存 |
| `marginbalance(JP)_*.csv` | 信用建玉 | 信用建玉一覧 > CSV出力 |

`marginbalance(JP)` の構造 (ヘッダは6行目、Shift-JIS):

```
口座区分, 銘柄コード, 銘柄名, 市場名称, 売買, 信用区分, 弁済期限,
建玉数量［株］, 執行中［株］, 建単価[円], 現在値［円］, ..., 建日, 最終返済日, ...
```

- **建玉単位の行**なので、同一銘柄が複数行に分かれる (215A が2行、2681 が3行など)
  → 銘柄ごとに `建玉数量` を合算して position 化する
- `建日` があるので、fill の `tate_date` との突合にも使える

**`売買` 列 (`買建` / `売建`) の扱い — 売建は自動更新に流さない。**
現データは全36行が `買建` だが、仕様としては以下に固定する:

- 売建行も `position` には `kind="信用売建"` として**保存する** (実態の記録として)
- ただし **`merged_qty` の算出からは除外**し、record 更新ロジックには流さない
- 売建を持つ銘柄は covered 判定を**強制的に偽**にし、要確認リストに
  「売建あり (自動更新対象外)」と出す

理由: 既存の `qty` は `_validate_qty` で 0以上のみ許容 (`portfolio_shelve.py:330`) で、
`1保` もロング保有を前提としたモデル。売建を負数で合算すると `merged_qty` が
負になり得るが、それをどの status / qty に落とすかは既存モデルに定義が無い。
空売りの保有管理は #397 のスコープ外なので、**検出のみして人に委ねる**のが安全。

### 2-1. 楽天の残高CSVには信用建玉が載っていない

| うち載っていない | 19 |

### 2-1b. SBI も現物・信用の2ファイルで揃う (2026-08-10 検証済み)

SBI も楽天と同様、**現物と信用で別CSV**。どちらも `SaveFile*.csv` という
同じファイル名で降ってくるので、ファイル名では判別できず**中身で判別する**。

| ファイル | 見出し行 | ヘッダ |
|---|---|---|
| 現物 | `保有証券一覧` | `銘柄コード, 銘柄名称, 保有株数, 売却注文中, 取得単価, 現在値, 取得金額, 評価額, 評価損益` |
| 信用 | `信用建玉一覧` | `銘柄コード, 銘柄名称, 売/買建, 市場, 期限, 建日, 返済期限, 預り, 建株数, 注文中, 建単価, ...` |

- 判別は **2行目の見出し** (`保有証券一覧` / `信用建玉一覧`) で行う
- 信用は楽天同様**建玉単位**の行 (`建株数` を銘柄ごとに合算)。`売/買建` 列あり
- 現物CSVには **ETF が混在する** (実データで 1681 上場ＭＳエマ / 2515 ＮＦ外ＲＥＩＴヘ無)。
  `is_etf_code()` で除外必須 (既存 fill 取込と同じ方針)
- SBI 現物CSVには**口座区分の列が無く、セクション見出し** (`株式（特定預り）`)
  で表現される。`account` は見出しから取る (`特定預り` → `特定`)。
  信用CSVは `預り` 列を持つ (実データは全て `特定`)
- **セクションが複数 (特定/NISA/一般等) あり得る前提で実装する。**
  実装初版は最初のヘッダ行しか見ておらず、2セクション目のデータ行を
  1セクション目に誤って合算するバグがあった (2026-08-10 の実装時に発見・
  修正)。全ヘッダ行を走査し、それぞれ直前のセクション見出しから account を
  紐付ける。実データは `特定預り` のみの1セクションだが、SBIでNISA/一般の
  保有が発生した場合にこの経路が効く

**account 網羅性は両社とも前提OK** (§5-2 の表):

- 楽天現物は1ファイルに `特定` と `NISA成長投資枠` が同居することを確認済み
  (米国株行に NISA成長投資枠 が出現)
- SBI 現物は `株式（特定預り）` セクションのみだが、**SBI に NISA/一般 の
  国内株保有は無く今後も予定なし** (ユーザー確認済み 2026-08-10) なので
  これで網羅。前提が崩れたときの検知として、`特定預り` 以外のセクションを
  見つけたら warning を出す

### 2-2. SBI の「ポートフォリオ一覧」CSV は残高として使えない

ユーザー提供の `New_file.csv` (SBI ポートフォリオ一覧) を検証したが、
**残高CSVではなくウォッチリスト出力**だった。以下が根拠:

- ヘッダは `銘柄（コード）, 買付日, 数量, 参考単価, 現在値, ...` と残高風だが、
  **`買付日` が全行 `----/--/--`、`数量`・`参考単価`・`損益`・`評価額` が全行 `--`**
- 実値が入っているのは `現在値` `前日比` `前日比（％）` の株価3列のみ
- 合計行 (`株式(現物/一般預り)合計`) も `評価額 = --`、`含み損益 = 0`
- 掲載10銘柄のうち DB 1保 は4銘柄のみ。残り6銘柄は 2準/3監/未登録
  (8035 は未登録・fill 実績ゼロ = 保有したことがない銘柄)
- 逆に DB の 1保 29銘柄のうち **25銘柄がこのファイルに載っていない**

つまり「SBI のポートフォリオ機能に登録した監視銘柄リスト」であり、
保有数量の情報を持たない。**このファイルからは qty を1件も導出できない。**

### 2-2b. パーサ実装上の注意 (実データで判明)

`assetbalance(all)` は**冒頭の資産サマリー部にも「1列目=種別っぽい文字列」の行**が
あり、素朴に列位置だけで拾うと `国内株式, 7,899,850, ...` (サマリー行) を
銘柄行として誤読する。実際に検証スクリプトで銘柄コード列に `7,899,850` が
混入した。

対策: `■ 保有商品詳細` セクション以降に限定し、かつヘッダ行
(`種別, 銘柄コード・ティッカー, ...`) を検出してからデータ行を読む
(`import_sbi_fills._find_header_row()` と同じ方式)。
加えて `validate_code_s()` を通らない行は RowSkip する二重防御を入れる。

SBI で必要なのは別画面のCSV — 「口座管理 > 保有証券」(現物) と
「信用建玉一覧」(信用) の出力 (§11-1)。

## 3. 基本方針

**ポートフォリオCSV (4ソース合算) を保有株数・保有ステータスの真実源とする。**
手入力の qty / ステータスは**CSV取込で上書きされる前提**とする
(ユーザー方針、2026-08-10 確認)。

- 4ソースが揃った銘柄 → CSV合算値が**正**。DB を CSV に合わせる
- 合算が 0 になった銘柄 → **売却済みとして 2準 に落とす**
- CSVに載っていて DB が非1保 → **保有として 1保 に上げる**
- ソースが欠けている銘柄 → 判定不能なので触らない (§5-2 の covered)

「人が管理し機械が検算する」ではなく **「機械が同期し、人は理由を書く」** の
関係にする。action_log は「なぜそうしたか」を残す場であって、
「何株持っているか」の真実源ではない。

### 3-1. 上書きしてよいもの / いけないもの

CSV が真実源なのは**数量とステータスという「事実」の部分だけ**。
人が入力した**判断・理由は上書きしない**。

| 対象 | CSV取込の扱い |
|---|---|
| `qty` (保有株数) | ✅ 上書き |
| `status` (1保/2準/3監) | ✅ 上書き |
| `memo.trade_idea` (売買戦略) | ❌ 保持 (§6) |
| `memo.*` (watch_in_reason 等) | ❌ 保持 |
| action_log の既存エントリ | ❌ **不変** (追記のみ) |
| action_log の `review_memo` | ❌ 保持 |

action_log は追記専用レイヤーなので「上書き」は起きない。
CSV取込による変更は `source="csv_import"` の**新しいログとして積まれる**。
過去の手入力ログはそのまま残り、履歴として参照できる。

## 4. データモデル

### 4-1. 反映元 (source) の導入

action_log に反映元を持たせ、手入力と自動反映を区別する。

```python
# portfolio_shelve.py
VALID_ACTION_SOURCES = frozenset({"manual", "csv_import"})
```

`ACTION_LOG_FIELDS` に以下を追加 (物理スキーマ変更なし・`list_action_logs` で
`setdefault("source", "manual")` 補完。既存ログは全て manual 扱い):

| フィールド | 内容 |
|---|---|
| `source` | `"manual"` (既定) / `"csv_import"` |
| `source_detail` | 取込元の識別子。例 `"楽天/残高/2026-08-09"` |

`append_action_log` / `update_qty` / `transition_status` / `add_to_watch` に
`source="manual"`, `source_detail=""` のキーワード引数を追加して素通しする。
既定値が manual なので既存呼び出しは無変更で動く。

### 4-2. 保有スナップショット (position) レイヤー

fill (約定の事実) とは別に、CSV由来の残高スナップショットを保存する。

```
position:<broker>:<account>:<kind>:<code_s>
    -> {code_s, broker, account, kind, qty, avg_price, as_of, imported_at}
```

- `kind`: `"現物"` / `"信用"` (CSVのセクション由来)
- `account`: 口座区分 (`"特定"` / `"NISA成長投資枠"` 等。CSVの `口座` 列)
- `as_of`: CSV の基準日
- 同一キー (broker, account, kind, code_s) は最新で**上書き** (fill と違い
  履歴を持たない。スナップショットなので最新だけで足りる)

キーに `account` と `kind` まで含めるのは、同一銘柄を
「特定/現物」と「特定/信用」の両方で持つケース (実データで 4970・6965・7047 等)
があり、これらが衝突すると §3 の「全口座・全区分が揃ったか」判定が
成立しなくなるため。銘柄の合計株数は前方一致スキャンで合算する。

取込済み判定用に、ソース単位の取込メタも別途持つ:

```
position_source:<broker>:<account>:<kind> -> {as_of, imported_at, row_count}
```

「そのソースが当日分揃っているか」はこのキーだけ見れば判定でき、
銘柄が0件になったソース (全部売った口座) も検出できる。

これを持つ理由は2つ。

1. 「どの口座のCSVが、いつ時点で取り込まれているか」を残さないと §3 の
   「全ソース揃ったか」判定ができない
2. 取得単価 (`avg_price`) が入るので、将来 fill 由来の計算値との突合に使える

## 5. 取込フロー

### 5-1. パース → 差分算出 → プレビュー → 適用

```
import_portfolio_csv.py <csv_path> [--dry-run] [--apply]
```

1. **パース**: 渡された各ファイルを §5-2 の判別表でソース特定し、
   それぞれの形式で銘柄別数量を取る。共通の除外規則:
   - 国内株式のみ (楽天現物は `種別=国内株式` の行だけ。米国株式/外貨預り金を除外)
   - ETF (`is_etf_code()`) を除外 — SBI現物CSVに実際に混在する (§2-1b)
   - `validate_code_s()` を通らない行は RowSkip (サマリー行の誤読防止、§2-2b)
   - 信用は建玉単位なので銘柄ごとに合算。売建は除外し covered を偽にする (§2-0)
2. **差分算出**: パース結果 (メモリ上) の銘柄別合計 `csv_qty` と、DB の
   `status` / `qty` / 既存 `position` を比較し、下表の判定に落とす
3. **プレビュー**: 差分一覧を表示 (dry-run 既定)
4. **適用**: `--apply` 指定時のみ永続化する。書き込む範囲は Phase による:

   | | Phase 1 | Phase 2 以降 |
   |---|---|---|
   | `position` / `position_source` upsert | ✅ | ✅ |
   | `update_qty` + action_log 追記 | ❌ **行わない** | ✅ (covered のみ) |

   **Phase 1 の `--apply` は position の保存までで、record は一切触らない。**
   まず全ソースのCSVを揃えて covered 率と差分の妥当性を目視確認するのが
   Phase 1 の目的だから (§10)。qty の自動更新は Phase 2 で解禁する。

**dry-run は Phase を問わず一切の書き込みを行わない。** `position` の更新も
apply 時のみ。dry-run で position だけ書くと「反映していないのに取込済みの
痕跡が残る」状態になり、§5-4 の自動OUT判定 (全ソース揃ったか) が誤作動するため。

### 5-2. 比較に使う数量の定義 (重要)

比較対象は「今回のCSVの数量」ではなく、**全ソース合算後の数量**。

```
merged_qty(code_s) = Σ  position[broker][account][kind][code_s].qty
                     (今回のCSVに該当する source は今回の値で差し替えた上で合算)
```

今回のCSVが担当するのは (broker, account, kind) の組だけで、それ以外の
ソースの position は据え置いて合算する。楽天現物CSVだけを取り込んだ時点で
402A を 1500→600 に落とすような過小更新を防ぐための定義。

**`qty` は現物と信用を合算した総保有株数** (ユーザー確定 2026-08-10)。
現行DBの値とも整合する (402A: 現物600 + 信用900 = 1500 = DB qty)。
現物/信用の内訳は `position` レイヤーに残るので、必要になれば後から
UI に出せる (今回は出さない)。

さらに、合算値が全保有を表しているとは限らないので **カバレッジ判定**を併用する:

```
covered(code_s) = その銘柄に関係する全ソースの position が揃っており、
                  かつ全ソースの as_of が同一日である
```

`as_of` の一致まで必須にするのは、古い基準日の残高を混ぜないため。
楽天現物を 08-09 で取り込んだのに信用側の position が 08-08 のままだと、
その間の売買が反映されず `merged_qty` が誤った値になる。
**基準日が揃っていないソースがある銘柄は `covered=false`** として
自動更新の対象外にし、要確認リストに「基準日不一致 (楽天現物 08-09 /
信用 08-08)」と理由付きで出す。

**`covered` は実CSVで確認できたソースだけで判定する。fill で穴埋めしない。**

「fill 上の信用残がゼロだから信用建玉は無いはず」という補完は行わない。
fill は約定履歴であって現在残高の保証ではなく、その信頼性のズレ自体が
#397 の出発点だから。fill を根拠に covered を立てると、避けたい誤更新が
別経路で復活する。

したがって、期待するソース一式 (§11-1) のうち**1つでも未取込の間は
自動更新を行わない**。楽天現物CSVだけの段階では covered は常に偽で、
出力は要確認リストのみ (＝差分の可視化に留まる)。

「期待するソース一式」は設定で明示的に宣言する:

```python
# 単位は (broker, kind)。1ファイル = 1ソース、全 account を網羅する前提 (下記)
EXPECTED_POSITION_SOURCES = [
    ("楽天", "現物"),   # assetbalance(all)_*.csv
    ("楽天", "信用"),   # marginbalance(JP)_*.csv
    ("SBI",  "現物"),   # SaveFile*.csv (見出し「保有証券一覧」)
    ("SBI",  "信用"),   # SaveFile*.csv (見出し「信用建玉一覧」)
]
```

**4ソース全て「1ファイル = 1ソース」**であることを実データで確認済み。
`kind` はCSVの種別から一意に決まるので、ファイル判別と同時に確定する。

ファイル判別ロジック (ファイル名に依存しないこと。SBI は現物・信用とも
`SaveFile*.csv` で同名):

| 判定順 | 条件 | ソース |
|---|---|---|
| 1 | 2行目が `保有証券一覧` | SBI/現物 |
| 2 | 2行目が `信用建玉一覧` | SBI/信用 |
| 3 | `■ 保有商品詳細` セクションを持つ | 楽天/現物 |
| 4 | 1行目が `■表示形式` かつ `建玉数量［株］` 列を持つ | 楽天/信用 |

宣言したソースの `position_source` が全て同一 `as_of` で揃って初めて covered=true。
ソースを増やす/減らすときはこの定数だけ変える。

**前提: 1つのCSVは、その (broker, kind) の全口座区分を網羅していること。**

| ソース | 網羅性 | 根拠 |
|---|---|---|
| 楽天/現物 | ✅ 確認済み | 1ファイルに `特定` と `NISA成長投資枠` が同居 |
| 楽天/信用 | ✅ 前提OK | 信用に NISA は無い (制度上) |
| SBI/信用 | ✅ 前提OK | 同上。`預り` 列で確認可能 |
| SBI/現物 | ✅ 前提OK | **SBI に NISA/一般 の国内株保有は無く、今後も予定なし** (ユーザー確認済み 2026-08-10)。`株式（特定預り）` セクションのみで網羅 |

**保険**: 取込時に SBI 現物CSVで `特定預り` 以外のセクションを検出したら
warning を出す。前提が崩れた (NISA で買った) ことにその場で気付けるようにし、
その場合は `EXPECTED_POSITION_SOURCES` を `(broker, account, kind)` の
3次元に拡張する。

なお未取込 account があった場合の影響は**過小合算の方向にしか効かない**。
`merged_qty` が実際より小さくなり「差分あり」として現れるので、
誤って一致判定されることはない。

`position_source` のキーを `(broker, account, kind)` の3次元で持つのは、
CSVに実際に現れた口座区分を記録するため。covered 判定は
「宣言した (broker, kind) それぞれについて、`position_source` が
1件以上・同一 as_of で存在するか」で行う。
取込時に想定外の `account` が現れたら warning ログを出し、
上記前提が崩れていないか気付けるようにする。

### 5-3. 差分判定表

`merged_qty` = 上記の合算値、`db_qty` = レコードの qty。

| DB status | covered | merged_qty | 判定 | 動作 |
|---|---|---|---|---|
| 1保 | ✅ | = db_qty | 一致 | no-op |
| 1保 | ✅ | ≠ db_qty (>0) | **株数変更** | `update_qty` + ログ |
| 1保 | ✅ | 0 | **売却** | `transition_status(2準)` + ログ (§5-4) |
| 2準 | ✅ | > 0 | **新規IN** | 戦略あり→自動 / 無し→保留 (§6) |
| 3監 | ✅ | > 0 | **新規IN** | 保留 (戦略の有無を問わず、§6) |
| 未登録 | ✅ | > 0 | **登録 + 新規IN** | `add_to_watch()` で3監登録 → 保留 (§5-3b) |
| 2準/3監 | ✅ | 0 | 一致 | no-op |
| いずれか | ❌ | - | 判定不能 | **no-op** + 要確認リスト (登録もしない) |

**`covered` が偽なら一切触らない。** 部分情報で更新すると過小合算による
誤更新になるため (§5-2)。covered が真なら CSV を正として qty も status も
同期する。

### 5-3b. 未登録銘柄の扱い (銘柄DBへの登録)

「DB に無い銘柄が CSV に出てきた」ケースの手順を明示する。

**登録は必ず 3監 から。いきなり 1保 のレコードは作らない。**
`ALLOWED_TRANSITIONS` が `(None, "3監")` のみ許可しているため。

**既存の `add_to_watch()` をそのまま使う** (自前で `create_record` +
`append_action_log` を書かない)。この関数は 3監 での登録と「初回登録」ログを
まとめて行い、さらに**ユニバース除外済みレコードの復活**にも対応している。

```python
# 1. まず 3監 で登録 (covered が真のときのみ)
ps.add_to_watch(code_s,
                reason="CSV取込で保有を検出 (as_of=YYYY-MM-DD)",
                action_date=as_of,
                source="csv_import")
# 2. その上で保留キューに積む (戦略入力を待つ)
```

`add_to_watch` の分岐は3つあり、CSV取込ではそれぞれこう扱う:

| 既存レコード | `add_to_watch` の挙動 | CSV取込での意味 |
|---|---|---|
| 無し | 3監 で新規登録 + 「初回登録」ログ | 想定ケース |
| あり + `excluded=True` | 除外解除 (復活) + ログ | **ユニバース除外した銘柄を買った**ケース。復活が正しい |
| あり + `excluded=False` | `ValueError` (重複登録) | 未登録判定と矛盾するので発生しない。例外はそのまま上げて気付けるようにする |

`source="csv_import"` を渡せるよう `add_to_watch` にも引数を追加する
(§4-1 の素通し対象に含める)。

つまり **「登録」と「1保への遷移」を2段階に分ける**。
登録自体は情報の追加でしかなく破壊的でないので自動で行い、
出口ルール (戦略) の宣言を伴う 1保 遷移だけ人に委ねる。

**なお `covered` が偽の場合は登録もしない。** ソースが欠けている状態では
その銘柄を本当に保有しているのか自体が確定しないため、
要確認リストに「未登録 + 判定不能」として出すに留める
(実運用では §5-1 の4ソース必須チェックにより、covered が偽になるのは
売建検出時などの例外的ケースに限られる)。

**現データでの該当はゼロ。** 4CSVに登場する28銘柄 (ETF除く) は
すべて DB に登録済みだった。将来 SBI/楽天で新規に買った銘柄が
ウォッチリスト未登録だった場合に効く経路。

なお `1保 → 2準` は既存実装で `action_type="売却"` として記録され、
直前の1保ログから `review_memo` を引き継ぐ (`transition_status` の仕様)。
CSV 由来でもこの挙動をそのまま使う。

なお **Phase 1 ではこの表の「株数変更」も実行されない** (可視化のみ、§5-1)。
covered と判定された銘柄は「Phase 2 で自動更新される候補」として
プレビューに出るだけで、DB は position 以外変更されない。
本表の動作が実際に走るのは Phase 2 以降。

### 5-4. 売却 (1保 → 2準) の扱い

4ソースが揃っている前提では「全CSVに無い = 保有ゼロ = 売却済み」と断定でき、
**自動で 2準 に落とす**。CSV を真実源とする方針 (§3) の当然の帰結。

ただし **`covered` が真であることが絶対条件**。ソースが1つでも欠けた状態で
これを走らせると、単に取り込み漏れた銘柄を全部売却扱いにしてしまう。
§5-1 の「4ソース揃わない実行はエラー停止」がこの事故を防ぐ最終防衛線。

現データでの該当は 4980 / 5578 / 5599 の3銘柄 (§2-3)。
**ユーザー確認済み: 3銘柄とも実際に売却済み** (2026-08-10)。
初回取込でそのまま自動 OUT してよい。

**落とし先は 2準** (ユーザー確定 2026-08-10)。既存の売却フローと同じで、
`action_type="売却"` として記録され振り返りメモも引き継がれる。
3監 に落とすと「ステータス変更」扱いになり売買履歴の集計から漏れるため使わない。

**売却日のズレは許容する** (ユーザー確定)。取込頻度は週次想定なので
action_log の timestamp は最大1週間ズレるが、**損益分析は fill 由来の
売買履歴タブで行う**ため実害がない。実際 `webapp/routes/trade_history.py:203`
のコメント通り「成績サマリー・概算損益は fill 側に一本化」済み (#387 Phase4b)
で、action_log 側は損益を計算していない。

ただし action_log の日付が実売却日とズレることは記録に残す:

- `reason` に `"CSV取込 (as_of=YYYY-MM-DD)"` を入れ、CSV由来であることを明示
- `source="csv_import"` で機械的にも判別可能
- 初回同期分は `reason` に「初期同期 (実売却日不明)」と付記

**`post_sell_returns` (売却後5/20営業日の騰落率、#366) は廃止する**
(ユーザー確定 2026-08-10)。売却日がズレると起点もズレて精度が落ちるが、
そもそも**この振り返りは売買履歴タブ (fill 側) で行う方針**になったため
機能自体が不要。削除範囲は §12 を参照。

## 6. 保有ステータス変更と戦略必須問題

### 6-1. 問題

issue #363 で「非1保 → 1保 の遷移は `trade_idea` (売買戦略) 必須」にしている
(`webapp/routes/portfolio.py:520-531`)。理由は「出口ルール未宣言のポジションを
作らせない」ため。CSV取込で機械的に 1保 にすると、この宣言が飛ぶ。

### 6-2. 推奨案: 戦略が既にあれば自動IN、無ければ保留キュー

CSV が真実源 (§3) でも、**戦略だけは人が宣言する**という #363 の設計は残す。
ただし現実には、新規INの多くは既に `trade_idea` を持っている
(実データの新規IN候補 2980 / 9337 はどちらも `GARP` 設定済み。
2準 = 「準保有」で買う前から戦略を決めている運用のため)。

そこで**元ステータスと戦略の有無で分岐**する:

| 元 status | `trade_idea` | 動作 |
|---|---|---|
| **2準** | 設定済み | **自動で 1保 に遷移** |
| **2準** | 空 | 保留キュー |
| **3監** | (問わず) | **保留キュー** |
| 未登録 | - | `add_to_watch()` で3監登録 → 保留キュー (§5-3b) |

**3監 は戦略があっても自動INしない。** 「準保有 = 買う準備ができている」
という宣言を経ていないため、3監 の `trade_idea` は過去の保有の名残や
単なる監視メモの可能性がある。それを根拠に出口ルールを自動適用するのは
#363 の趣旨に反する。

実データ上もこの線引きに無理がない:

| status | 件数 | `trade_idea` あり |
|---|---|---|
| 2準 | 85 | 24 (28%) |
| 3監 | 206 | **3 (1%)** |

3監 で戦略が入っているのは3件だけなので、3監 を保留キュー行きにしても
実運用の手間はほぼ増えない。

```
pending_in:<code_s> -> {code_s, qty, as_of, detected_at}
```

保有銘柄タブに「CSVで検出された新規保有 (N件)」を出し、各行で
戦略を選んで「確定」を押すと、既存の遷移処理と**同じ順序**で
`source="csv_import"` 付きで走る。

この分岐なら、実データでは**保留キューに何も溜まらず全自動で回る**。
戦略未設定の銘柄をいきなり買った場合だけ、人の入力を1回求める形になる。

```python
# webapp/routes/portfolio.py:520-537 と同じ順序を踏襲すること
ps.seed_trade_ideas()
ps.update_memo(code_s, {"trade_idea": trade_idea})   # 1. 戦略を先に保存
ps.transition_status(code_s, "1保", qty=qty, ...)     # 2. 遷移
ps.update_qty(code_s, qty, log_action=False, ...)    # 3. record の qty を更新
```

**3 の `update_qty` は必須。** `transition_status` は action_log に qty を
載せるだけで record 本体の `qty` は書き換えないため、これを省くと
`status=1保` なのに `qty` が 0 のままになる。
未登録銘柄は取込時点で既に `add_to_watch()` により 3監 で登録されている
(§5-3b) ので、この手順の入口では常にレコードが存在する。

- ✅ 「未分類のまま保有にはできない」という #363 の不変条件を壊さない
- ✅ 実運用ではほぼ全自動 (戦略は 2準 の段階で決まっているため)
- ✅ 戦略未設定という例外だけ人に回るので、止まる頻度が低い

### 6-3. 代替案 (不採用)

- **案A: 戦略を "未分類" で自動IN** — #363 の目的を無効化する。却下。
  なお `update_memo` はマスター未登録値を ValueError で弾くため、
  空戦略のまま 1保 にすると「1保かつ未分類」の不正状態が生まれる
- **案B: 直近の action_log から戦略を推測** — 過去の戦略と今回のINが同じ
  保証がない。誤った出口ルールが付く方が無宣言より悪い。却下
- **案C: 取込時に対話的に戦略を聞く** — CLI が対話的になると cron 化できず、
  WebApp からの取込に統一できない。却下

### 6-4. 売却 (OUT) 側は戦略チェック不要

`1保 → 2準` は `ALLOWED_TRANSITIONS` に含まれ、戦略の宣言も不要。
CSV で残高ゼロになったら**無条件で自動 OUT** してよい (§5-4)。
入口 (IN) だけを厳しくするのが #363 の設計意図。

## 7. 自動で埋める項目

CSVから取れる値のうち、どこまで自動で書くか。

| 項目 | CSV | 方針 |
|---|---|---|
| `qty` | 保有数量 | **自動反映** (covered のみ、Phase 2 以降) |
| `avg_price` | 平均取得価額 | `position` に保存するのみ。record には書かない (fill 由来の計算と二重管理になる) |
| `status` | (残高の有無) | **自動反映** — OUT は無条件、IN は戦略があれば自動 (§6) |
| `trade_idea` | - | **上書きしない**。空のときだけ人に入力を求める (§6) |
| 銘柄名 | 銘柄 | 使わない (既存方針: 表示時に stocks_shelve から解決) |
| action_log `reason` | - | `"CSV取込 (楽天/残高/2026-08-09)"` を自動生成 |
| action_log `timestamp` | 基準日 | CSV の `as_of` を JST 12:00 に変換 (既存 `action_date` と同じ扱い) |

## 8. 冪等性

同じCSVを2回取り込んでも差分ゼロになる (qty が既に一致 → `update_qty` が
no-op で early return)。`position` は上書きなので重複しない。
fill のような `dedup_key` は不要。

## 9. UI

- **取込**: 保有銘柄タブに「ポートフォリオCSV取込」ボタン → **4ファイルを選択**
  (複数選択) → 差分プレビュー画面 → 「反映」。
  ソースが揃っていなければプレビュー画面で警告し、反映ボタンを無効化する
- **プレビュー**: 変更内容を種別ごとに色分け (株数変更 / IN / OUT)。
  特に **OUT は「保有から外す」破壊的操作なので明示的に強調**する
- **保留キュー**: 同タブ上部に「戦略未設定の新規保有 (N件)」を出す
- **要確認**: 「covered でない銘柄 (N件)」を理由付きで出す
  (売建あり / ソース欠落など)
- **ログ表示**: アクションログの反映元を出し分け (手入力 / CSV)。
  売買履歴タブのフィルタにも `source` を追加

## 10. 段階導入

| Phase | 内容 | 自動更新 |
|---|---|---|
| **1** | `source` フィールド + `position` レイヤー + 4CSVパーサ + CLI (dry-run/apply)。差分の**可視化のみ** | ❌ 無し |
| **2** | covered 銘柄の qty 自動反映 + **自動OUT** (§5-4) + 戦略ありの**自動IN** (§6-2) | ✅ qty / status |
| **3** | WebApp 取込UI + 差分プレビュー + 要確認リスト | - |
| **4** | 保留キュー (戦略未設定の新規IN) | ✅ IN (人が戦略入力) |

Phase 1 と 2 を分けるのは、**まず「CSVを全部読んだら本当に辻褄が合うのか」を
書き込み無しで確認するため**。実データで検証した通り、ソースが欠けた状態での
自動更新は誤更新に直結する (§5-2)。特に**初回の自動OUTは3銘柄を
一気に 2準 に落とす**ので、その3銘柄が本当に売却済みかを
Phase 1 の出力で人が確認してから Phase 2 に進む。

qty と status を Phase 2 でまとめて解禁するのは、CSV を真実源とする方針 (§3)
では両者を分ける意味が無いため (どちらも「CSVに合わせる」同じ操作)。
Phase 4 の保留キューだけは、実データで該当ゼロなので後回しにできる。

### 11-1b. CSVを一括取得できるか (Web調査結果 2026-08-10)

**結論: ブラウザからの手動DLでは一括取得できない。現物と信用は別画面・別出力。**

| 手段 | 一括可否 | 備考 |
|---|---|---|
| 楽天Web (マイメニュー) | ❌ | 保有商品一覧 と 信用建玉一覧 が別画面。それぞれ「CSVで保存」 |
| SBI Web (口座管理) | ❌ | 保有証券 と 信用建玉一覧 が別画面。**どちらも `SaveFile*.csv` という同名**で降ってくるので中身で判別が必要 (§2-1b) |
| **マーケットスピード (リスト情報出力機能)** | △ | 保有銘柄一覧・信用建玉一覧の**両方をCSV出力できる**が、リストごとに「ファイル出力」を押す方式。同時出力の記載は無し |
| **マーケットスピード II RSS** | ✅ | Excel関数 `=RssPositionList()` (保有一覧) と `=RssMarginPositionList()` (信用建玉一覧) で**両方を1つのExcelシートに常時取得**できる。要 Windows + Excel |

現実的な選択肢は2つ:

- **案X (推奨・現状維持): 手動で2〜4ファイルDLして取り込む**
  月数回の運用なら許容範囲。実装は複数ファイルを1コマンドに渡せるようにするだけ。

  ```bash
  # 4ファイル全てを渡す (SBI は現物・信用が同名で連番になる)
  python import_portfolio_csv.py \
      "assetbalance(all)_20260810_153355.csv" \
      "marginbalance(JP)_20260810_151923.csv" \
      "SaveFile.csv" "SaveFile (1).csv" --apply
  ```

  **`EXPECTED_POSITION_SOURCES` の4ソースが揃わない実行はエラーで停止する**
  (`--allow-partial` を明示したときのみ続行)。3ファイルだけ渡して
  position が中途半端に更新される事故を防ぐため。
  同一ソースのファイルが2つ渡された場合もエラー (取り違え検出)。

  ファイル種別はヘッダ構造から自動判別する (§5-2 の判別表)。
  **SBI の現物・信用は同名 `SaveFile.csv` / `SaveFile (1).csv` なので
  ファイル名では判別できない**点に注意 (ブラウザの連番付与順は保証されない)。
  取込後に「宣言したソースのうち未取込のもの」を警告表示すれば、
  DL漏れにその場で気付ける。

- **案Y: マーケットスピード II RSS で自動化** — Windows + Excel 常駐が前提。
  本システムは macOS 運用なので**現状では非現実的**。将来の選択肢として記録に留める。

なお楽天のファイル名は `assetbalance(all)_<日付>_<時刻>.csv` /
`marginbalance(JP)_<日付>_<時刻>.csv` と規則的なので、
`~/Downloads` から最新のものを自動検出する補助は入れられる (実装時の小さな utility)。
