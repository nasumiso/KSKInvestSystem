# feat(trade-history): 往復行に振り返りメモを付けられるようにする

## 背景

issue #421 (PR #422, マージ済み) で、売買履歴の明細を「買→売」の往復1行に畳んだ。
これで**1行 = 実際に下した1つの売買判断**という粒度になった。

しかし振り返りメモは依然として**エピソード (建玉ラウンド) 単位**にしか付けられない。
4258 網屋は 2026-04-08 〜 08-25 の間ずっと建玉が0にならないため、14本の約定
(7往復) が1エピソードになり、メモは1つだけ。

```
26-08-18 → 保有中     100株  4,480 → —      +4.46%   +20,000円
26-07-17 → 26-08-05   100株  4,390 → 4,720   +7.52%   +33,000円
26-04-08 → 26-07-06   100株  3,050 → 4,710  +54.43%  +166,000円   ← 利確の判断
26-06-01 → 26-06-16   100株  3,330 → 3,300   -0.90%    -3,000円   ← 損切りの判断
```

「+54% で利確した判断」と「-0.9% で損切りした判断」は別物なのに、同じメモ欄に
押し込むことになる。issue #421 のスコープ外として後続に回した部分。

## やりたいこと

往復行ごとに振り返りメモを付けられるようにする。
既存のエピソード単位メモ (`fill_memo`) は残す (ラウンド全体の総括に使う)。

## 最大の論点: 行キーの設計

**往復行は fill の追加取込で対応が変わりうる。** 単純な (銘柄, 買日, 売日) では
メモが別の取引に付いてしまう。

### 実データでの裏付け

- **162銘柄中80銘柄で遡り取込が発生している** (seq 順と約定日順がずれている)。
  期首持越しの補完や、証券会社CSVの期間分割取込で古い約定が後から入る
- **842往復行のうち61行が (決済日, 決済単価) の組で重複**している。
  日付+単価では一意にならない

### 実際に対応が変わる例 (検証済み)

```
取込前:  2026-02-01 (2,000) → 2026-03-01   pl= +50,000
         ↓ 01-05 の買い (1,000円) が後から取り込まれる
取込後:  2026-02-01 (2,000) → 保有中
         2026-01-05 (1,000) → 2026-03-01   pl= +150,000
```

FIFO の充当先が変わり、「2/1 に買った玉を 3/1 に売った」という行が消えて
別の行になる。ここにメモが付いていたら、**別の取引のメモとして表示される**。

### 現行のエピソードキーが安定な理由

`fill_episode_key(code_s, kind, first_seq)` は**ラウンド先頭 fill の seq** を使う。
seq は `append_fill` が採番する銘柄内の固有値で、建玉開始時に確定し不変。
買い増し・部分売り・返済で fill が増えても変わらない。

往復行にも同じ性質のアンカーが要る。現状の往復行 dict は
`open_date / close_date / qty / open_price / close_price / broker / ...` を持つが、
**seq を持っていない**。

### 保有中行を先に決める (キー設計と一体の論点)

**保有中の往復行は60件あり、決済 fill を持たない。** そのため
「決済 fill の seq を起点にするキー」は保有中行に対して原理的に作れない。

保有中にメモを許可するなら、決済時にキーが変わるため**付け替え処理が必要**になり、
「後から対応が変わって別の取引にメモが付く」という避けたい問題を別の形で
再導入する。**保有中メモを許可するかどうかは、キー設計と同時に決める** (後段の
未確定事項に回さない)。

### 検討すべき案

| 案 | キー | 保有中行 | 遡り取込への耐性 |
|---|---|---|---|
| A | 決済 fill の seq | **不可** | 決済側は動かないので○。ただし1決済が複数ロットに分割されると複数行が同じ seq になる (4258: 200株建→100株返済)。ロット連番の併用が要る |
| B | (決済fill seq, 建玉fill seq) | **不可** | 組が変われば別キーになる=メモが消える (誤対応はしない)。建玉不明 (17本)・現引の行には付けられない |
| C | 決済fill seq + 行内連番 | **不可** | FIFO の充当順が変われば連番の意味も変わる |
| D | 建玉 fill の seq + ロット連番 | 可 | **不可 — 要件を満たさない** (下記) |

#### 案 D は成立しない

建玉起点なら保有中行にも付けられるが、**キーが残ったまま指す行の意味が変わる**。
本文の検証例で言うと:

```
取込前:  2026-02-01 (2,000) → 2026-03-01      ← ここに「3/1 に利確した理由」を書く
取込後:  2026-02-01 (2,000) → 保有中          ← 同じ建玉 seq。メモがこちらに付く
         2026-01-05 (1,000) → 2026-03-01      ← 実際に 3/1 に利確した行
```

「3/1 に利確した理由」が保有中行のメモとして表示される。キーが消えないぶん
かえって誤対応に気づけない。**D は「キーが生き残る」だけで、往復行メモとしては
要件 (別の取引に移らない) を満たさない。**

#### この表から言えること

- 保有中メモを**許可しない**なら A/B/C が候補 (決済側は遡り取込で動かない)
- 保有中メモを**許可する**なら、上記4案では解けない。
  「保有中メモは往復行ではなくエピソード単位/建玉単位の別レイヤーに置く」など、
  **往復行キーとは分けた設計**が要る

**実装前にどの案を採るか決める。** 少なくとも「遡り取込でメモが別の取引に
移らないこと」をテストで固定できる設計にする。

## スコープ

- 往復行ごとの振り返りメモの保存・表示・編集
- 既存のエピソード単位メモは残す (併存させるか、UI 上どう見せるかは要検討)
- メモが付いている往復行の一覧性 (どこにメモを書いたか探せること)

### スコープ外

- メモの全文検索・タグ付け
- 戦略ひもづけ (issue #419 で別途扱う)

## 未確定事項

### 着手ブロッカー (これを決めないと実装に入れない)

1. **#419 とキー・保存レイヤーを共有するか** (上記「issue #419 との関係」参照)。
   共有しないと、DBスキーマと移行方針を二度固定することになる
2. **保有中行にメモを付けられるか** + **行キーの設計** — この2つは一体。
   保有中行 (60件) は決済 fill を持たないため、決済起点のキー (案 A/B/C) では
   原理的に扱えない。かといって建玉起点 (案 D) は遡り取込でメモが別の行に
   ぶら下がるため成立しない。
   **「許可しない → A/B/C から選ぶ」「許可する → 往復行キーとは別レイヤーを設計する」**
   と選択肢が連動するので、分けて決められない

### 実装方針を決める段階で潰す

3. **エピソード単位メモとの関係** — 併存させるか、往復行へ移行するか。
   **既存の `fill_memo` は現在3件のみ**なので、移行するなら手作業で移せる範囲。
   後方互換のための実装コストをかける必要はなさそう
4. **メモを付けられない行の扱い** — 建玉不明の行 (17本)、現引の振替行、
   分割疑い (split_suspect) のエピソードの行

### issue #419 との関係 — **本issueの着手ブロッカー**

#419 は**エピソード単位**で戦略を焼き付ける設計だが、そこで挙がっている
「高回転銘柄は戦略が混在する」問題は、往復行と同じ粒度の話。

> 6227 AIメカテック: 14件中10件が 0〜7日の回転 (現 trade_idea は「中長期ファンダ」)
> 4377 ワンキャリア: 179/185/206日 と 0〜2日 が同居

**メモも戦略も同じ「往復行キー」に載る可能性が高い。** この状態で本issueだけ先に
実装すると、直後の #419 で別キー・別保存形式を足すか、再移行するしかなくなる。
**DBスキーマと移行方針を二度固定することになる**ため、単なる後回しではなく
着手前に潰すべき依存関係。

したがって、本issueに着手する前に次を確定させる:

1. **メモと戦略で行キー・保存レイヤーを共有するか**
2. 共有するなら、**どちらの issue でキーを定義するか** (先に実装する側)
3. 戦略もエピソード単位ではなく往復行単位にするのか
   (#419 の「高回転銘柄で戦略が混在する」問題は往復行単位なら解ける)
