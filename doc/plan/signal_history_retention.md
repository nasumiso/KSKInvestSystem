# 実装プラン: ブレイク/ポケットシグナル履歴の保持と詳細チャート長期表示

## 背景・課題

現状、ポケットピボット (`pocket_pivot`) / ブレイクアウト (`breakout` / `breakout_extended`)
シグナルは以下の仕組みで、**履歴が保持されず毎回再計算・上書き**されている。

- 算出: `price.py` `parse_price_text_from_list()` が日足から **直近10営業日** を走査
  (`for ind in range(10)`, price.py:1693/1745)
- 保存: `stocks_shelve` の `pocket_pivot`/`breakout`/`breakout_extended` に格納 (price.py:1739/1807-1808)
- 上書き: これらは `_PROTECTED_LIST_KEYS` 外なので毎回 `stock[k] = new_val` で全置換
  (make_stock_db.py:751)
- 表示: 詳細チャートは `extract_signals(stock, max_delta_days=None)` で算出済み全件を
  チャート窓内に描く (helpers.py:2679) が、元データが10営業日窓ぶんしか無いため
  **古いシグナルは日々の更新で脱落**する

加えて、**デイリーの株価取得〜シグナル計算は必ず毎日走るとは限らない** (cron 失敗・休日・
手動運用)。更新が10営業日以上飛ぶと、窓外に落ちた日のシグナルは永久欠測になる。

### 関連 issue

- #341 (PERベースカウント) / #342 (クライマックス/配給検知) は「過去ブレイクアウト履歴」を
  暗黙の前提にしており、本対応はその水源インフラにあたる。
  ただし #341/#342 着手は別 issue。本プランは **詳細チャートでの過去シグナル表示** に閉じる。

## ゴール

1. ブレイク/ポケットシグナルを `stocks_shelve` に **履歴として追記保持** する
   (毎回の上書きで脱落させない)
2. 詳細チャートで、保持された **過去シグナル (保持日数ぶん)** を描画する
3. 更新が飛んで欠測した日のシグナルを、次回更新時に **自動でバックフィル** する
4. 現在の売買判断用の「直近10日」用途は現状どおり維持する (回帰させない)

## 確定した設計方針 (ユーザー合意済み)

- **欠測対応**: 案C (自動バックフィル)。保持を主軸にし、欠測検知時のみ `period` を広げて
  遡及再計算しマージする。人手不要で「確実に計算」を担保する。手動トリガーは設けない
- **保存先**: `stocks_shelve` に **履歴専用フィールドを新設** (折衷案)。
  既存の揮発フィールド (`breakout` 等 = 直近10日・毎回上書き) はそのまま残し、
  履歴は別フィールドに分離する。算出と保存が同じ `price.py` で完結しデータフローが素直、
  かつ揮発/不変をフィールドで分離できる
- **保持日数**: 固定60日ではなく、**現在の株価ログ (`price_log`/取得 `period`) で対応できる
  再計算日数** に合わせる (下記「保持日数の決定」参照)

## 保持日数の決定

「現在の株価ログで対応できる日数」の制約:

| 要素 | 現状値 | 場所 |
|---|---|---|
| 日足取得 period | `"2mo"` ≒ 40営業日 | price.py:1083 |
| price_log 保持件数 | `LOG_DAY = 30` | price.py:1813 |
| シグナル算出窓 | 直近10営業日 | price.py:1693/1745 |

- シグナル算出は前日比較・MA10/MA25 を使うため、ある日のシグナルを算出するには
  その日より過去側に MA 算出ぶん (最大25日) のデータが要る。
- よって、取得 `period="2mo"` (≒40営業日) で **安全に遡及計算できるのは概ね 40 - 25 ≒ 15
  営業日** が素朴な上限。MA25 が揃わない日は MA10 のみで判定する既存ロジック (price.py:1716)
  があるため、MA10 (10日) 基準なら 40 - 10 ≒ 30 営業日まで算出可能。
- **本プランの保持日数 = 30営業日** とする。根拠: `price_log` の `LOG_DAY=30` と一致し、
  「現在の株価ログで対応できる日数」というユーザー指示に合致する。
  - 表示窓の上限は既存 `_SIGNAL_STALE_DAYS=30` (暦日) とも整合的。
  - 将来 #341/#342 でベースを跨ぐ1〜2年履歴が必要になったら、`period` 拡大と保持件数
    引き上げを別途検討する (本プラン外)。

> 注: 「保持日数」は新規フィールドに貯める履歴の truncate 上限。「再計算日数 (=遡及計算
> できる日数)」は取得 period に依存。両者を 30営業日で揃え、矛盾を作らない。

## 実装内容

### A. データ層: 履歴フィールド新設と追記マージ (price.py / make_stock_db.py)

1. **シグナル走査日数のパラメータ化** (codex 指摘2 / 必須):
   現行 `parse_price_text_from_list()` はポケット/ブレイクとも `for ind in range(10)` で
   **走査対象が10営業日に固定**されている。`period` を広げて取得日数を増やしても、この
   ループが10で止まる限り古い日のシグナルは生成されない。
   → 走査日数を引数化 (例: `scan_days=10` をデフォルトにし、履歴/バックフィル経路では
   保持日数 (30) ぶん走査する)。`price_log` の長さや取得 period に応じて、安全に算出できる
   範囲 (MA算出ぶんを差し引いた手前側) に clamp する。
2. `price.py` `parse_price_text_from_list()` で、既存の `pocket_pivot`/`breakout`/
   `breakout_extended` 算出結果 (直近10日窓) に加え、新規フィールドを生成:
   - `pocket_pivot_history` / `breakout_history` / `breakout_extended_history`
   - 内容形式は既存と同じ `["mm/dd,num", ...]` を踏襲 (年補完は既存 `_signal_recent_delta`
     ロジックを再利用)
3. **評価済み watermark の保存** (codex 指摘1 / 必須):
   履歴フィールドは「シグナルが出た日だけ」の疎なリストのため、最新シグナル日と price_log
   最古日の比較では「更新が飛んで未計算の日」と「シグナルが無かった日」を区別できず、
   案C の欠測検知が成立しない。
   → 「**どの日まで評価 (走査) 済みか**」を表す watermark を別フィールドで保存する:
   - `signals_evaluated_through` (date): 今回の走査でカバーした最古日
   - 欠測検知は「watermark が price_log でカバーできる日付より新しい (= 間に未評価日がある)」
     で判定する。シグナルの有無とは独立した密な指標になる
2. `make_stock_db.py` `update_db()` のマージ処理に、**履歴フィールド専用のマージ分岐**を追加:
   - 既存保持リスト + 今回算出ぶんを、**年補完済みの絶対日付をキーに dedup マージ**
     (mm/dd だけだと年跨ぎ衝突するため)
   - 保持日数 (30営業日) を超える古いエントリを truncate
   - `_PROTECTED_LIST_KEYS` の「空リストで上書き防止」とは挙動が違う (追記が要る) ため、
     新しい定数 `_HISTORY_MERGE_KEYS` 等で分岐するか、専用マージ関数を切り出す
   - **冪等性**: 同一絶対日付のエントリは1件に正規化 (重複追記しない)
   - **遡及調整 (株式分割/配当) の扱い**: 既存保持エントリは固定とし、再算出で num が
     変わっても**上書きしない** (一度確定した過去シグナルを普遍とみなす)。
     ※ ここは codex レビューで「固定 vs 上書き」の妥当性を確認する論点

### B. 欠測バックフィル (案C, price.py / make_stock_db.py)

1. 更新時、**watermark (`signals_evaluated_through`)** と、保持日数 (30営業日) ぶん遡った
   目標日を突き合わせ、**未評価の gap があるか検知**する (codex 指摘1 反映)。
   - シグナルの疎なリストではなく watermark で判定するため、「シグナル無し」と「未評価」を
     正しく区別できる
2. gap があり、かつ通常取得 (`period="2mo"`) では埋まらない場合のみ、
   その回だけ `period` を広げて (例: `"3mo"`) 再取得し、**走査日数も保持日数ぶんに拡張して
   (A-1)** 遡及算出・マージする
   - 普段の更新ではコスト不変 (gap 無しなら拡大取得・拡張走査しない)
   - 拡大取得でも遡及計算できるのは period 範囲内まで。range 外の欠測は埋められない旨を
     log_print で明示 (silent に取りこぼさない)。埋められた範囲ぶん watermark を更新する
3. **yfinance キャッシュのバイパス** (codex 指摘 / 必須):
   現行は日足取得時、`upd < UPD_FORCE` かつキャッシュファイル
   (`yfinance_price_%s.json`, price.py:1055-1058) が TTL 内なら **直前バッチで作られた
   2ヶ月ぶんキャッシュをそのまま返す**。さらに通常取得の `period` は `"2mo"` 固定
   (price.py:1083)。したがって「その回だけ period を広げて再取得」と書いても、
   キャッシュ命中で 2ヶ月データが再利用され、gap を埋める追加データが取れない。
   → バックフィル経路では以下の両方を満たす取得をする:
     a. **キャッシュをバイパス** (`UPD_FORCE` 相当でキャッシュを使わない、または
        period 別キャッシュキー `yfinance_price_3mo_%s.json` を使う)
     b. **period を拡張** (`"2mo"` → `"3mo"` 等) して取得日数を増やす
   - a/b のどちらの方式 (force vs period別キー) を採るかは実装時に確定。force 方式が単純だが
     通常キャッシュを汚さないか確認する。バックフィルは gap 検知時のみ発火するため頻度は低い

### C. 表示層: 詳細チャートを履歴フィールドから描画 (helpers.py / make_stock_db.py)

1. `extract_signals()` に履歴ソースを選択する引数を追加 (例: `use_history=False`)。
   - デフォルト (一覧 tooltip/背景色・現在の売買用) は **従来の揮発フィールド + 10日窓** を維持
     → 既存挙動を回帰させない
   - 詳細チャート (`helpers.py:2679`) のみ `use_history=True` で履歴フィールドを参照し、
     `max_delta_days=保持日数` でチャート窓内に描く
2. **表示件数制限の解除** (codex 指摘3 / 必須・「検討」ではない):
   現行 `extract_signals()` は用途に関係なく `pocket_pivot[:3]` / `breakout[:1]` で切るため、
   詳細チャートが履歴フィールドを見ても窓内の過去シグナルが大半描画されない。
   → `use_history=True` の経路では件数制限を外し、**窓内 (保持日数ぶん) の全シグナルを描く**。
   一覧用途 (`use_history=False`) の `[:3]`/`[:1]` 制限は現状維持。

### D. マイグレーション (make_stock_db.py)

- 新規フィールドは存在しなければ空リストで初期化。既存 DB はマイグレーション不要
  (初回更新時に履歴が貯まり始める)。後方互換性を維持。
- CLAUDE.md「shelve DBスキーマの後方互換性を維持」に準拠。

## 検証ポイント (Goal-Driven)

1. **履歴蓄積**: 連続更新で `breakout_history` が10日窓を越えて貯まり、30営業日で truncate
   されることをテストで確認 (parametrize)
2. **冪等性**: 同じ日に2回更新しても履歴が重複しないことを確認
3. **欠測バックフィル**: 履歴に gap を作った状態で更新 → gap が埋まることを確認
4. **既存挙動の非回帰**: 一覧 tooltip/背景色・シグナル列が従来どおり (10日窓・揮発フィールド)
   であることを確認 (`test_make_stock_db.py` `TestExtractSignals` の既存ケース維持)
5. **詳細チャート**: 履歴フィールドから30営業日ぶんのマーカーが描かれることをブラウザ確認

テストは parametrize で集約し、1 PR で5本以下を目安 (TESTING.md 方針)。
