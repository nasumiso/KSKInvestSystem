# issue #566: 月次の振り返りで含み損益の増減も反省の材料にする (月末の保有を終値から復元、4〜10月分に追補)

## 目的

月次の振り返り (/trade-review) で、完了した売買だけでなく、含み損益の増減も踏まえて反省する。10月のように、月をまたいで持ち続けた銘柄の含み損が大きく膨らんだ月は、今の §2 (当月に決済 / 当月に新規建て) のどちらの表にも出ず、反省にならない。

- 総額だけでなく、どの取引でどれだけ含み損益が動いたかを出し、決済と同じ基準 (損切り幅・時間軸・判断 × 結果) で照合する
- 含み損益の日次ログは 2026-11-02 からしかない。過去の月末 (2025-12 末〜2026-10 末) は約定と終値から復元する。11月以降も同じ復元で数える (数え方を月で変えない)
- 保存済みのレポート (4〜10月分) は上書きしない。各月に「追補」を別ファイルで付け、レポート画面で並べて読めるようにする (ユーザー決定)

## 現状

- `summary.trend.unrealized` は日次ログ (`exposure_log.json` の `unrealized_total`、証券会社の残高 CSV 由来) の月初 → 月末。11/2 以降しかない。CSV の取り込みが遅れると古い (11/6 時点で SBI は 10/23 の CSV)
- `summary.month_pl` (7e717a3) = 当月の売りの実現損益 (往復行の決済日が当月) + 上記ログの増減
- §4 保有PFの点検は「過去の月末の保有は復元できない」ため、レポートを作った日の保有で書いている。10月下旬にさかのぼって作った4月分は、10月の保有を点検していた
- 往復行 (`trade_episodes.build_round_trips`) は建て→決済の対応を持つ。信用は証券会社 CSV の建玉対応、現物は先入先出
- 保存は `trade_review.py save YYYY-MM < report.md`。既にあれば書かない。開発用コピーには書かない
- レポート画面 `/trade-history/reviews/<YYYY-MM>` は `trade_review/YYYY-MM.md` を読む

## 設計

役割分担は変えない: 数字は Python が出し、LLM (スキル) は照合と問いかけ、決めるのは人。

### 1. ある日の保有と含み損益を往復行から復元する (`webapp/trade_episodes.py`)

`open_lots_at(ep, day, close)` を足す。往復行を持つモジュールに置き、売買履歴の画面からも使えるようにする (今回は画面には出さない)。純粋関数。

- 対象: エピソードの往復行のうち、`day` の時点で建っている行
  - 建っている = 建てた日 ≤ day かつ (決済日が無い または 決済日 > day)
  - **現引の二重計上を防ぐ**: 現物側の行で `genbiki_date` があるものは、建てた日の代わりに `genbiki_date` を使う (現物側の `open_date` は信用の建日なので、そのままだと現引までの間、信用側の行と二重に数える)
- 戻り値: 建っている株数、建値の合計 (取得額)、含み損益 = (終値 − 建値) × 株数 の合計。売建は符号を逆にする (`_set_unrealized` と同じ定義)
- 建値の無い行 (期首持越しで建玉不明) があれば、そのエピソードは計算不能として理由を返す

### 2. 過去の終値を取る (`trade_review._load_inputs`、CLI 側)

- 前月末または当月末に建っている往復行がある銘柄について、yfinance で日足の終値を取る (期間は前月末の 7 日前〜当月末。`history(end=...)` は end 当日を含まないので、end には月末の翌日を渡す。月末の足が取れたかを確かめ、取れなければ前の足で評価せず計算不能にする)
- **配当調整なしの終値を使う** (`auto_adjust=False` の `Close`)。既存の `price.py` は `auto_adjust=True` (配当も遡って調整) なので流用しない。約定単価は配当調整されないため、調整済みの値だと権利落ちをまたぐ月の含み損益がずれる
- **分割**: yfinance の過去の終値は、後から起きた分割で遡って調整される。約定の単価は分割前のまま。その日より後に分割 (`Ticker.splits`) がある銘柄は、終値を戻さず計算不能に回す (理由つき)。件数は実データで確かめ、多ければ再検討
- `build_review_dataset` には `closes: {code_s: {日付: 終値}}` を引数で渡す (計算側は DB・ネットワークを読まない方針を守る)

### 3. JSON に足す項目 (`trade_review.py`)

基準日: 月初 = 前月の最終平日、月末 = 当月の最終平日 (当月が終わっていなければ JSON を作った日の前営業日)。終値はその日以前の最後の値。

`summary.holdings_unrealized`:

```
{
  "start_date": ..., "end_date": ...,
  "start_total": ..., "end_total": ..., "change": ...,     # 計算できたエピソードだけの合計
  "excluded": [{"episode_key", "code_s", "stock_name", "reason"}],   # 月初・月末のどちらかで計算不能
  "episodes": [ {"episode_key", "code_s", "stock_name", "kind", "trade_idea", "stop_loss_pct",
                 "open_date", "start", "end", "change", "end_pct", "status"} ],
      # status: carried (月初・月末とも保有) / opened (月中に建てて月末も保有) / closed (月初に保有し月中に決済)
      # change の小さい順 (含み損が増えた順)。全件
  "month_end_over_stop_loss": [episode_key...]   # 月末の含み損益率が戦略の損切り幅を超えていた取引
}
```

- **保有していない側は 0 円**: 月中に決済した取引 (`closed`) は月末 0 円、月中に建てた取引 (`opened`) は月初 0 円として増減に入れる。これは計算不能ではない。月初に保有して月中に決済した取引は、実現損益 (建値から) と月初の含み損益 (建値から) の差で、月内の値動きだけが月の損益に残る
- **計算不能の扱い (Codex 指摘)**: 保有している側で計算できない (月初・月末のどちらか) エピソード (`split_suspect`、建値不明、終値なし、後の分割) は、月初・月末の両方から外し、`excluded` に理由つきで載せる。片側だけ数えて値動きが黙って 0 円扱いになるのを防ぐ。合計を null にはしない (分割1銘柄で月全体が出なくなるため)
- `summary.month_pl` を復元値で出す: 当月の売りの実現損益 + `holdings_unrealized.change`。日次ログ (`trend.unrealized`) は参考として残す
  - 実現損益は約定から確定しているので、`excluded` のエピソードでも数える (`split_suspect` だけは既存どおり外す)。消すと、確定した売却損益が月の損益から抜ける (Codex 指摘)
  - ただし月初の評価が無いエピソードの実現損益には、前月以前の値動きも含まれる。その金額を `month_pl.excluded_realized` (エピソードごとの内訳つき) として別に出し、スキルは「うち n円は月初の評価が無く、前月以前の値動きを含む」と添える
- `end_pct` = 月末の含み損益 ÷ 月末に建っている分の取得額。`month_end_over_stop_loss` は `stop_loss_pct` がある取引だけ判定する (既存の幅の当て方 `_stop_loss_widths` を使う)

### 4. スキル `/trade-review` の反省の軸を広げる

レポート (11月分以降):

- §1 月の結果: `month_pl` で「当月の売りの実現損益 + 含み損益の増減 (月初 → 月末、日付つき) = 月の損益」。`excluded` があれば件数と理由
- §2 取引ごとの照合に **3つ目の表「持ち越し」** を足す: `status=carried` のうち含み損益の増減の大きいもの (上位5件と、月末に損切り幅を超えていたもの全件)。列は決済の表に合わせる (取引 / 時間軸 / 損切り幅 / 持ち続けた理由 (推定) / 判断 × 結果 (推定))。推定の書き方は既存の決済と同じ (メモ・日記が無ければ判定不能)
- §4 保有PFの点検の「損切り幅を超えた含み損」を **月末時点** (`month_end_over_stop_loss`) にする。運用総額・銘柄数・小口は今どおり作成日の値で、その旨を書く
- §5 の問いの優先順に「損切り幅を超えたまま月をまたいで持ち続けた取引」を足す
- してはいけないことに変更なし (含み損の大きさで人を評価しない)

追補モード (`/trade-review addendum YYYY-MM`、4〜10月分):

- 書くのは §1 の月の損益と、§2 の持ち越しの表、月末時点の損切り幅超え、問い 1 件 (含み損が最も増えた持ち越しについて、持ち続けた理由を選択肢で)、気づき 1〜3 行
- 本レポートで選んだルールや §0 の判定には触れない (ルールの履歴を崩さない)
- 保存: `trade_review.py save-addendum YYYY-MM < addendum.md` → `trade_review/YYYY-MM.addendum.md` と、そのとき作った JSON を `YYYY-MM.addendum.json`。既にあれば書かない・開発用コピーに書かない (既存の `save` と同じ)

### 5. レポート画面

`review_reports` で、`YYYY-MM.addendum.md` があれば本レポートの下に「追補」として表示する。月の一覧は従来どおり `YYYY-MM.md` から作る (追補のファイル名は月の正規表現に当たらない)。

## 検証

- 単体テスト (5本以内、parametrize で集約):
  - `open_lots_at`: 現引をまたぐ日に二重計上しない / 売建の符号 / 建値なしは計算不能
  - `holdings_unrealized`: 片側だけ計算不能なエピソードは両側から外れ excluded に載る / status の振り分け / 後の分割は計算不能
  - `month_pl` が復元値で出る (既存テストを置き換え)
  - `save-addendum` が上書きせず開発用コピーに書かない (既存の保存テストの parametrize に足す)
- 実データ (運用機):
  - **ベースラインとの対**: 11/2〜11/6 の各日で、復元した含み損益の合計と日次ログの `unrealized_total` を並べる。残高 CSV が新しい楽天分は銘柄ごとにも並べる。ずれが大きければ、原因 (先入先出 vs 平均取得単価、CSV の古さ、復元漏れ) を切り分けてから先へ進む
  - 2025-12 末〜2026-10 末の各月末の合計と `excluded` の件数を表にしてユーザーに見せる
- レポート画面で追補が本レポートの下に出ること (開発用コピーにダミーの追補を置いて確かめ、消す)

## 対象外

- 保存済みレポート (4〜10月分) の書き換え・作り直し
- 運用総額・銘柄数の過去分の復元 (含み損益だけ)
- 手数料・金利の反映 (現物の先入先出と平均取得単価の差も受け入れる)
- 分割をまたぐ銘柄の終値の戻し (計算不能に出すだけ)
- 売買履歴の画面への月末の含み損益の表示

## レビューの経過

Codex (gpt-5.6-terra) で3巡レビューし、指摘はすべて計画に反映した: 計算不能の取引を片側だけ数えない (1巡目)、配当調整なしの終値・計算不能でも実現損益は消さない (2巡目)、yfinance の end の扱い・保有していない側は 0 円 (3巡目)。3巡目の指摘は実装の細部だったため、ここで打ち切った。
