## 優先度の付け方

その四半期に何を進めるかは、下の「いま強化する領域」に当たるものから選ぶ。issue に決まった書式は求めない。**なぜ今これをやるのかを1行**書けば足りる (どの領域の話か、どの数字や出来事がきっかけか)。

迷ったときの目安:

- [方向性メモ.md](方向性メモ.md) §7 の避ける方向 (候補を増やすだけ、買いシグナルを増やすだけ、指標を並べるだけ) に寄っていないか
- 作った後に、使ったか・効いたかを自分で言えそうか

効いたかどうかは、issue に先に書かせず、四半期末の仕様レビューでまとめて振り返る。

## 四半期と Milestone

その四半期に進める issue は、GitHub の Milestone に入れる。名前は `2026-Q4` の形で、期限は四半期末。

- Milestone に入れるのは、その四半期のうちに終えるつもりのもの。入れないものは Milestone なしで置く
- 四半期の途中で足してよい
- 四半期末に終わらなかったものは、次の四半期に持ち越すか、外すかを仕様レビューで決める。黙って持ち越さない
- issue の一覧と状態は GitHub が正で、この文書には書き写さない。重要度は `priority` ラベル、時期は Milestone で示す

## 新規実装と振り返りのバランス

- **月初めに、前月分の `/trade-review` を先に回す。** 済むまで、その月の新機能には着手しない
- **振り返りで「守れていない」と数字で出たルールを仕組みにする作業は、新機能より先にやる**
- 作った機能は、四半期末の仕様レビューで、使ったか・効いたかを振り返る。効いていなければ、直すか外すかを決める

## 着手前の確認

新機能の実装を始める前に、人も AI も次を確かめる。

1. 前月分の振り返りが済んでいるか (運用機の `trade_review/YYYY-MM.md`)
2. その四半期の Milestone に入っているか。入っていなければ、入れるかを先に決める

不可逆データと日次運用の保全、バグ修正、日々の手作業を減らすもの、文書の変更は、この確認の対象外。
